# Retrieval-only: manual CI for 20 SWE-QA questions

Updated September 20, 2026. See the [benchmark README](../benchmarks/zg-retrieval/README.md) for usage and the [Retrieval-only workflow](../.github/workflows/retrieval-only.yml) for execution.

## Running the benchmark

The workflow accepts manual `workflow_dispatch` events only; it does not run on pushes, pull requests, or a schedule. Both the original actor and the actor requesting a rerun must have the repository's maintain or admin role. Every job rechecks authorization, including when a failed job is rerun independently. A failed permission lookup stops execution; the checked-in authorization action rejects write, triage, and read roles. This check is not a permission boundary against contributors who can modify the workflow or its local action on another branch; that boundary requires repository- or organization-level Actions execution policies.

ZG runs by default. Setting `run_semble=true` adds Semble to the same workflow. The `modes` input defaults to hybrid and also accepts hybrid,fts,vector. Each enabled ZG mode retains both short and full preview arms.

The **Retrieval results** job's Summary is the single overview for a run. Its table presents all enabled arms together. When Semble is disabled, the table explicitly shows its disabled status and —. Repository shards do not publish separate long summaries. Missing results, invalid experiments, product failures, and complete successful runs have distinct statuses; an invalid experiment must never appear as a completed run with zero scores.

## Dataset and retrieval protocol

The questions come from [Actions run 35206585943](https://github.com/Cuiyus/zvec-grep/actions/runs/35206585943). The complete original questions, their UTF-8 hashes, 11 repository commits, and provenance fingerprints are frozen in [source.lock.json](../benchmarks/zg-retrieval/data/source.lock.json). The 20 questions include five each of what, where, how, and why. There is no query rewriting, subquery generation, answer agent, or LLM judge.

Each run installs the candidate npm tarball outside the corpus and invokes the product through the stdio MCP configuration generated by the official installation. Every repository gets a fresh index; only model downloads are cached. Source, model, and index identities are verified before and after retrieval. Questions, labels, and reports are excluded from the retrieval corpus.

ZG uses the original query, Top-10, autoUpdate=false, and freshness=eventual. Within the same index and MCP session, each question runs five consecutive short calls followed by five consecutive full calls. Only the fifth call in each arm contributes a quality observation, so each arm still has 20 quality samples. The default hybrid run makes 200 calls; enabling all three modes makes 600. Full preview returns the complete content already available for the retrieved unit, plus its outline; it does not expand the result by reading the entire file.

The optional Semble arm pins source commit `0051e000fcaac69a9c5d081ebbc8d4cb8508160b`, the model revision, and Python dependencies. Its native MCP uses top_k=10, content=code, and max_snippet_lines=null, retaining default hybrid retrieval and heuristic reranking. It makes 100 MCP calls, then executes 20 `index.search()` calls against the same persisted indexes. Each SDK result is checked against the fifth MCP response for paths, ranges, ranks, scores, and complete content. SDK replay contributes neither quality samples nor MCP latency samples.

## Results table

| Metric | Definition and denominator |
| --- | --- |
| File Hit@1 | Fraction of the 20 questions whose first result matches any annotated relevant file |
| File Hit@5 | Fraction with at least one annotated file among the first five native results |
| File Hit@10 | Fraction with at least one annotated file among the first ten native results |
| File MRR@10 | 1/r for the first matching rank r, or zero for a miss; equal-weight mean across all 20 questions |
| nDCG@10 | Exact port of the pinned upstream algorithm's first-target ranks, binary gains, and target-count IDCG; macro-averaged across the 11 repositories |
| Mean output (KiB) | Mean UTF-8 byte length of public response text from each question's successful fifth call, divided by 1024; not model tokens |
| Latency P50 (ms) | Median duration of all valid successful MCP search calls; excludes indexing and SDK replay |

Output and latency include their valid sample counts. A fully successful arm normally has 20 output samples and 100 latency samples. Product failures are excluded from these two operational measurements, but failed quality observations remain in the quality denominator as zeros. The fixed short-before-full order and differences in machines and engine environments affect latency, so these measurements do not establish a controlled speed comparison.

Strict source-anchor Hit/RR/MRR, complementary-group nDCG, nDCG@5, the separate file-presence rate, and category scores have been removed from the current scorer or reports. Public ranks, per-question RR, target ranks, and paired-result consistency remain as calculation or integrity evidence; they do not produce additional score tables. Raw execution timings and indexing records remain available for audit without being mixed into the main results table.

## Labels and matching

All five quality metrics share [39 frozen file targets](../benchmarks/zg-retrieval/gold/semble-file-v1.json). These are a deduplicated projection of the original accepted paths; bridge-only files receive no credit. The original labels, proposed and cross-checked by two AI agents against fixed source revisions, remain as provenance records. Declaration anchors no longer determine retrieval hits.

Matching uses Semble's path rules and preserves native result positions. Repeated files are neither collapsed nor renumbered. Snippet length, outlines, and whether a complete function declaration is visible do not affect these five quality metrics. The JavaScript nDCG port is checked by a differential oracle using the original Python functions from the pinned upstream source.

These are public development questions with partial positive labels, without an independent blind human review. A file hit does not establish sufficient answer evidence or complete recall. A single Hit change among 20 questions is five percentage points. See the [metric validity review](./zg-retrieval-metric-review.md) for the label assessment.

## Integrity and failure handling

Each task/mode/preview/repetition must have its own raw response and hash. Offline aggregation reparses public results and checks request parameters, root paths, original queries, repetition counts, source/model/index inventories, and Semble SDK parity. Saved derived scores are not accepted as scoring inputs.

Installation, indexing, and product-call failures fail the workflow. For reviewed questions, undelivered results receive zero quality credit. Incompatible formats, identity drift, missing or duplicate calls, altered parameters, and evaluator errors invalidate the experiment; complete aggregate scores are then N/A. Integrity and measurement-sample validation are CI gates. Quality scores do not currently have arbitrary pass/fail thresholds.

## Reports and artifacts

- `retrieval-results`: the single overview, `summary.md` and `summary.json`, plus `comparison.json` when both engines have valid results.
- `retrieval-zg-report`: the complete ZG `report.json`, per-call `scores.jsonl`, and a concise report.
- `retrieval-data-<owner>__<repo>`: each ZG repository's raw responses, requests, installation evidence, and index evidence.
- `retrieval-semble-evidence`: generated only when Semble is enabled; contains all raw responses, inventories, and SDK parity evidence.

The unified `summary.json` uses schema 2. Its `quality_metrics` list and each result row’s `metrics` object use `ndcg_at_10`; the displayed metric label is nDCG@10. The name change does not alter the formula or weighting.

ZG reports use schema 3 and Semble reports use schema 2. `file_retrieval` stores file metrics, `semble_official` retains only nDCG@10 and its supporting target evidence, and `measurements` stores the two operational measurements and sample counts. Each quality observation includes five `measurement_observations` for recomputation. Legacy top-level anchor scores, summaries, and category scores are no longer emitted.

Offline comparison can still read ZG schema 1/2 reports, but recomputes current metrics from public items. Missing complete measurement evidence produces N/A rather than trusting old caches. Replaying saved raw data must always be distinguished from a new product or CI execution.
