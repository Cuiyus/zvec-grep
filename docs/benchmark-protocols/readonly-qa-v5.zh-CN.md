# reflex-6：真实请求主回归与按需三模式诊断 v5

v5 将固定请求回放分成三份独立报告：**Agent 真实完整请求承担主回归，原始问题使用预先规定的默认配置，三模式对照仅作辅助诊断。** 每次运行不合并三类成绩，也不从三模式中挑最优结果作为 zg 的成绩。

本版本改变执行计划与报告主次，沿用 [v4](readonly-qa-v4.zh-CN.md) 的语料、请求抽取、源码标注、评分及只读完整性规则。已有 [v4 实测结果](../benchmark-results/readonly-qa-v4-reflex-6.zh-CN.md) 保持历史原样；**v5 目前没有新的检索实测结果或 E2E 样本**。离线计划生成、旧输出重评分与单元测试均不算新检索实测。

## 1. 固定数据与比较对象

- QA：SWE-QA `reflex-6`，源码为 Reflex commit `fe0f946dc0c240c6c1e513318c21db407e191c78`。
- 运行时：发布包 `@zvec/zvec-grep@0.2.2`，embedding `local/potion-code-16m-v2`，依赖锁与镜像身份写入产物。
- 请求：原 E2E run `34255587426` 中 OpenCode + GLM-5.2、OpenCode + Qwen3.8-Max、QoderCLI + Qwen3.8-Max 三组的首次 zg 决策轮。原有 baseline / zg 各 5 次，30 个计划试验及其失败状态不变。
- 标注：`reflex-6.query-intents.json` 和 `reflex-6.entries.json`，以固定源码中的事实和入口为依据，不绑定某种切分的 chunk ID。

当前计划有 12 种不同的完整后端请求，以及原题 1 条加实际字符串 11 条组成的 12 条文本。它们全部来自一道 QA，不是 12 道独立任务。源码标注由开发 Agent 在看过旧结果后制定，是冻结的开发标签，不是独立人工 Gold 或 held-out 验收集。

**目前 runtime 仍运行已发布的 zg 0.2.2，不会自动使用分支中的源码改造。** 后续比较 chunking 或 embedding 版本时，必须明确接入候选构建、记录版本和配置并重建对应索引；只修改本仓库源码后跑当前镜像不能证明改造有效。本协议未将尚未实现的片段审计、实际索引输入与逐路候选追踪描述为已有能力。

## 2. 三类回放与执行数量

| 类型                     | 固定请求                                                                            | 运行时机           |                                                          当前执行量 |
| ------------------------ | ----------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------: |
| **主回归：真实完整请求** | 保留实际 `query` / `queries` / `routes`、`fuse`、`limit` 及其他记录字段，缺省仍缺省 | 每次回归           |                                               12 个单元 × 5 = 60 次 |
| **原题默认配置**         | 原始问题固定为 hybrid，`limit=10`                                                   | 每次回归，单独报告 |                                                 1 个单元 × 5 = 5 次 |
| **辅助诊断：三模式对照** | 全部 12 条文本分别跑 FTS / vector / hybrid，`limit=10`                              | 显式启用时         | 36 个对照单元，其中原题 hybrid 复用前一类结果；新增 35 × 5 = 175 次 |

因此默认是 **13 个不同单元、65 次检索**；启用辅助诊断后是 **48 个不同单元、240 次检索**。辅助表引用原题 hybrid 的同一单元和结果，不重复运行，也不把它计成额外样本。数量来自当前冻结材料，实际计划及其哈希写入 `replay-plan.json`；数据变更必须作为新的数据版本审查，不能在执行时删去失败或难查的请求。

原题默认请求固定为以下 API 字段；在 zg 0.2.2 中 `query` 使用默认的全文与向量混合路由：

```json
{
  "root": "/app",
  "query": "<固定原始问题全文>",
  "limit": 10,
  "autoUpdate": false,
  "trace": true
}
```

此处原题的 query 是 case 文件的完整字符串，不是人工缩写。默认配置属于评测协议，不能根据本轮三模式成绩改变；后续若更改，需发布新协议并让比较双方重跑。

主回归按完整请求的规范化 JSON 去重，忽略对象键顺序但保留数组顺序、字段取值和缺省状态，并保留所有原试验来源。首轮多次 zg 调用分别保留，不把联合请求拆成单条文字后替代真实路径。主评分对象是该完整请求的联合输出；其中命中不能分别归功于每条 route。

## 3. 固定抽取与 GroundTruth

从原生工具日志和关联的 zg 后端事件抽取首次出现 zg 的完整模型决策轮，包括该轮全部 zg 调用、原始 query 字符串、返回文本与调用来源。抽取依赖日志和输出哈希关联，不重新让 Agent 生成或修正 query。数组样式字符串保持一个字符串；多路请求中的各 query 也保留所在参数位置。

首次 zg 不一定出现在第一轮会话。保留此前已经返回的工具反馈及其边界，同轮工具的执行先后不构成“模型看过前一个结果”的证据。无 zg 调用的试验保留未采用状态，不生成虚拟请求。

标注区分完整原题、等价改写、合法子目标、歧义和偏离；不同检索目的使用各自可接受入口的 OR 集合，桥接入口单列。源码事实用于确认 query 与任务的关联，不要求 getter 子目标一次找齐完整原题的所有证据。公开输出必须包含可核验的路径与定义锚点，仅父类范围包含目标或正文提到函数名不算目标定义命中。

未知 query、未审查的联合请求、歧义或无法评分的执行保留 `unknown`，不替换成零分，也不删除。旧 task 依赖入口另列观察，不自动取代 query 条件评分。未被标注的其他结果是未审查，不能据此宣称它们无关。

## 4. 执行与重复性

每次 CI 从固定源码重新准备索引，不跨 CI 复用已有索引。源码只读挂载，每个不同回放单元从本轮不可变种子获得独立工作副本；检索容器禁网、不注入生成模型凭据、不运行 daemon 或增量索引。索引准备耗时与检索耗时分开记录。

同一单元 5 次调用串行复用同一引擎和工作副本。预先使用第 1 次作为质量观察，其余 4 次用于检查一致性，不能挑选较好的一次替代第 1 次。第 1 次不等于严格机器冷启动；5 次也不是独立 Agent 样本或 5 次重建索引实验。

运行前后校验源码、种子、全部索引文档与向量的身份和哈希。工作副本的物理存储字节另行记录，不将物理变化未经调查解释成无害元数据，也不将它直接等同于文档或向量变化。

## 5. 分别报告，不取最优

`replay-report.json` 与 `replay-report.md` 应明确区分主回归、原题默认配置和辅助诊断。未启用辅助诊断时明确显示“未运行”，不能把它当成失败或零分。

每一类都保留 query 目标和旧 task 入口两列，并报告：

- Hit@1 / @5 / @10、首次目标排名、RR@10：观察入口是否出现及位置变化。
- 原生输出与 4 / 8 KiB 前缀内的目标可见性：观察有限输出预算下是否能定位目标。
- 总输出字节、到首次命中块末尾的累计字节：输出长度与定位入口的成本代理，不换算为模型 input token。
- 每次输出哈希与耗时、重复一致性、错误和完整性状态：固定请求下的执行稳定性。

主回归以完整请求为比较单位，保留所属 Agent/Model 和全部原始出现位置。原题默认配置不混入真实 Agent 请求均分；三模式不与主回归合并，也不选择其中最好的模式替代真实请求的成绩。辅助诊断回答“为什么有差异”，不承担主成绩。多道 QA 扩展后的汇总应先按 QA 统计，不能让改写数量多的题自动获得更大权重。

这些是已标注入口的命中与排名，尚非穷尽相关性的 Recall、Precision 或 nDCG。5 次输出一致也不证明 Agent 会稳定生成同样的改写。最终答案质量、实际 input token 和 tool call 的收益继续由 E2E 测量；v5 不新建 E2E、不生成新答案、不调用自动 judge。

## 6. 运行与产物

从 run `34255587426` 下载三个完整 artifact，解压为同一目录下的 `opencode-glm52/`、`opencode-qwen38max/`、`qoder-qwen38max/`。使用 Python 3.12 的锁定环境，在仓库根目录生成默认计划：

```sh
uv sync --project benchmarks/swe-qa-bench --frozen
uv run --project benchmarks/swe-qa-bench python -m zg_bench.swe_qa.retrieval_replay analyze \
  --recorded-runs /absolute/path/to/recorded-qa \
  --case benchmarks/swe-qa-bench/cases/reflex-6.json \
  --entries benchmarks/swe-qa-bench/cases/reflex-6.entries.json \
  --labels benchmarks/swe-qa-bench/cases/reflex-6.query-intents.json \
  --output benchmarks/swe-qa-bench/runs/v5-new-analysis
```

`analyze` 仅读取旧轨迹、生成计划和旧返回的离线评分，不执行检索。运行真实检索时，先按 [v5 workflow](../../.github/workflows/readonly-qa-v5.yml) 构建固定镜像，将子命令改为 `run`，使用另一新输出目录，并添加 `--image zg-readonly-qa:0.2.2`。需要三模式对照时，在 `analyze` 或 `run` 命令中显式添加 `--include-mode-diagnostics`。

输出目录必须新建。产物保留原始轨迹抽取、标注和计划哈希、旧输出评分、runtime manifest、索引准备与完整性记录、每单元请求和 5 次公开返回、错误及分组报告。`new_model_calls=0` 表示没有新增生成式模型调用；本地 embedding 仍会运行。

GitHub Actions 默认 push 仅执行 65 次检索。手动触发时，布尔输入 `include_mode_diagnostics` 默认 `false`；设为 `true` 才增加辅助诊断。该输入通过环境变量和 Bash 参数数组传入 CLI，未启用时不传该 flag。

本分支已有 `swe-qa-bench.yml` 的 job 条件排除付费 E2E；`readonly-qa.yml` 使用提交信息中的 `[retrieval-only]` 跳过 E2E。回放实现提交继续保留此标记。需要完全跳过 CI 的纯文档提交使用 `[skip ci]`。历史 v4 workflow 的复现需检出旧提交，v5 不覆盖旧 artifact 或旧报告。
