# SWE-QA 任务分析：ZG 能否替代检索型子 Agent

**现有结果支持：ZG 可以承担部分 `explore` 子 Agent 的定位、证据收集工作；尚不能证明它在跨模块任务上普遍可替代子 Agent，或在相同 token 预算下总体检索质量更高。** 最强正例是多条件目标定位；真正跨模块的任务需要单独看，不能由总分代替。

范围为本轮 GLM5.2 的原生允许委派、原生禁用委派、Rust ZG 禁用委派三组，20 题、每题每组 10 次，共 600 个最终答案。本次只分析既有数据，没有新增模型实验。文中的“评分”均为原 GLM 裁判评分；另列的目标定位、代码事实检查不等同于整份答案质量。完整组均值及区间见[主报告](zg-glm52-subagent-ablation.zh-CN.md)。

## 1. 两种工具实际承担了什么工作

| 观察 | 子 Agent：原生允许组 | ZG：Rust 禁用委派组 |
|---|---|---|
| 使用情况 | 54/200 次执行使用，涉及 11/20 题 | 192/200 次执行使用；19 题全用，Pylint 14 为 2/10 |
| 调用形态 | 54 次全部为 `explore`，以定位、阅读、解释为主 | 267 次调用，包含 284 条查询；后续 75 次调用均有查询改写或问题拆分 |
| 触发时点 | 53/54 在首个工具步骤委派；只有 Pylint 9 的一次是在原生搜索后追加委派 | 191/192 在首次工具决策中调用 ZG |
| 返回后主 Agent 做什么 | 48/54 没有后续工具调用；6/54 又读取源码核验 | 189/192 在后续步骤读取源码，102/192 又用 grep |
| 消耗与职责 | 子会话占允许组总输入的 40.40%；被委派的 54 次中占 88.03% | ZG 返回候选代码；问题分解、选择证据、补充读取和最终综合仍由主 Agent 完成 |

这表明两者的**检索职责有重叠，但返回的产物与工作分工不同**：子 Agent 通常返回已经组织过的解释，ZG 返回候选证据，仍需主 Agent 核验与综合。因此应检验“能否替代一次检索委派所完成的工作”，而不是把工具调用次数视为等价工作量。

当前 Rust 组被权限层禁止委派，并带有 ZG 工具引导。其 96% 采用率说明工具被使用，**不能证明模型在同时可用时会自主用 ZG 替代子 Agent**。允许组 53 次开场就委派，也表明多数调用发生在看到检索结果之前，不能都解释成“主 Agent 检索失败后遇到难题”。

## 2. 跨模块、复杂任务是否更容易触发

本次先独立阅读题面与冻结参考，再合入实验数值。这里区分“解释多个实现模块的协作”与“用复杂线索找到一个局部目标”；这是本次事后分析的分类，不是原实验预注册分组，也不以 token 或工具次数定义复杂度。

| 按题面／参考分类 | 题数 | 子 Agent 使用次数 | ZG 使用次数 |
|---|---:|---:|---:|
| 按参考完整解释要求的跨模块组 | 10 | 32/100（32%） | 100/100 |
| 局部定位、局部机制或协议知识 | 7 | 10/70（14.3%） | 62/70（88.6%） |
| 参考不足以可靠确定范围 | 3 | 12/30（40%） | 30/30 |

跨模块组中，Conan 39 和 Requests 16 有边界：参考的完整解释涉及其他模块，但题目的主要目标也可以集中在一个测试或一个编排函数。将这两题单列后，**核心 8 题为 22/80 次委派、80/80 次使用 ZG**。

几个直接影响判断的例子：

- **Xarray 46** 涉及 Dataset 聚合、dtype 筛选、NaN 分支和底层数值操作；原生允许组 0/10 委派，平均输入仍达 27.44 万。复杂且昂贵，并不意味着本轮一定触发子 Agent。
- **Conan 39** 为 10/10 委派、10/10 使用 ZG，但最明确验证到的是“多条件定位正确测试”，不能仅凭此推出跨模块理解能力已被替代。
- **Pylint 9** 主要定位一个特定语法测试，却也发生过委派；**Pylint 14** 主要涉及 `__deepcopy__` 协议，原生两组均无工具调用，Rust 仅 2/10 使用 ZG。
- Reflex 6、Streamlink 14/43 的参考存在路径不明确、目标歧义或推测性解释，应单列，避免当成已确认的复杂检索任务。

因此，现有数据只能说明**一部分跨模块任务会触发委派，ZG 在多类任务中都会被采用**。ZG 的高采用率没有表现出同等的复杂度选择性；“是否调用”还受工具可用性和提示影响。这里的 0/10 仅表示未观察到调用，不代表模型永远不会调用。

## 3. 哪些任务支持“检索平替”，哪些不支持

### 正例：Conan 39 的目标定位

核验目标为 `test/integration/remote/multi_remote_test.py:test_conan_install_update`，检查时间间隔、上传到 local、`--update -r default` 与 `Newer` 状态之间的关系。检查了三组全部 30 个答案，没有只挑代表轨迹。

| 指标 | 原生允许 | 原生禁用 | Rust ZG |
|---|---:|---:|---:|
| 正确定位参考目标并说明关键流程 | 9/10 | 3/10 | **10/10** |
| 平均输入 token | 92,733 | 79,576 | **64,564** |
| GLM 评分 | 80.0 | 39.2 | 92.8 |

Rust 的 9/10 首次召回包含正确测试，10/10 后续读取了目标文件；有一次仍需多轮改写和原生检索。它给出了可核验的“候选命中 → 阅读验证 → 正确目标说明”链，支持 ZG 承担这类检索委派，而且本题实际输入更低。

这里衡量的是**参考目标定位率**，不是完整实现链的正确率。Rust 有两条答案没写测试函数名，但文件、行号和控制流正确，所以同时做了字符串检查和语义核验。本次核验由分析 Agent 完成，尚未经专家盲审。

### Pylint 9：收益不应都归因于避免委派

三组最终答案出现参考目标文件或符号 `nested_class_as_return_annotation` 的次数为 **3/10、6/10、10/10**，主 Agent 读取目标文件的次数也分别为 3、6、10。它衡量定位覆盖，不代表整份答案正确。允许组仅一次委派；该次在多次原生搜索后，将子任务限定到 `/app/pylint`，并把目标描述成“类属性或类中嵌套类”，而实际目标在 `/app/tests/functional/`，是函数内嵌套类。

这次执行消耗 435,761 输入 token，子会话用了 35 次工具，仍返回“没有精确匹配”，主 Agent 后续也未读到目标测试。它说明**错误的定位假设和路径约束会使委派探索偏离目标**。但允许组第 9、10 次执行均未委派，却贡献本题该组 69.16% 的输入；子会话仅占该组整题输入的 7.87%。因此，ZG 的整题收益不能全解释成“省掉子 Agent”；它也改善了主 Agent 自己的定位路径。

### 真正跨模块：有替代信号，但收益更温和

Conan 19 要解释 host/build context、依赖身份与聚合。Rust 通常需要改写查询并读取 `requires.py`、`graph.py`、`graph_builder.py` 等；10 次共 19 次 ZG 调用。输入均值为原生允许 211,727、原生禁用 168,365、Rust 190,488，评分为 93.2、92.6、93.6。ZG 能提供跨模块线索，但比原生禁用仍用了更多输入，不能说检索成本被消除。

核心 8 个跨模块任务的均值如下。总 token 定义见下一节。

| 指标 | 原生允许 | 原生禁用 | Rust ZG |
|---|---:|---:|---:|
| 总 token | 138,061 | **120,535** | 129,069 |
| GLM 评分 | 92.55 | 91.74 | **93.31** |

这个分层中，Rust 处于“比原生允许消耗低、比原生禁用消耗高”的位置，评分略高。这支持继续验证，但没有形成相同预算的比较，也不能用评分的小幅变化代替完整证据链审查。

### 反例：Requests 16 命中相关代码仍漏关键证据

Rust 的 10 次首次查询都命中 `SessionRedirectMixin`，但只有 3 次可见工具输出覆盖向 `self.cookies` 写回的 `sessions.py:276`；**6/10 个最终答案明确错误声称重定向循环不写 session cookie jar，另 1 次省略写回**。其中一条 `read` 止于 259 行，刚好漏掉下一跳请求更新与后续写回；还把 dict 分支的 `overwrite=False` 错套到 CookieJar 分支。

本题原生禁用与 Rust 的输入为 35,148 与 57,596，评分为 90.7 与 82.1。这里不仅是评分回退，还能核验具体代码错误：**找到相关类，不等于覆盖关键状态变化**。原生允许组本题也未使用子 Agent，所以这是 Rust ZG 方案未保证证据完整和正确综合的反例，不能拿来估计子 Agent 的替代效果，也不能把主模型漏读、误解代码都归因于 ZG 召回引擎。

Django 32 和 Xarray 46 的案例还显示，读取相关模块后仍可能错误综合事务语义或忽略分支例外。后续优化需要同时检查召回覆盖、读取完整性和证据到结论的推导。

## 4. 同 token 下，质量是否提高

为避免只对齐输入却漏掉子 Agent 的生成，本节用**总 token = 含缓存的全部主／子会话输入 + 非推理输出 + 推理输出**。它仍是 token 计量，不是价格加权账单；主表不含缺失计量的失败尝试。

| 全部 20 题均值 | 原生允许 | 原生禁用 | Rust ZG |
|---|---:|---:|---:|
| 总 token | 115,233 | 87,014 | 86,468 |
| GLM 评分 | 79.77 | 77.00 | 82.52 |

按统一方向“原生禁用 − Rust”，总 token 为 **+0.63%**、评分为 **−5.53 分**。这支持“固定题集上，平均消耗接近时出现了更高回答评分”的观察。

但目前不能直接写成“同预算下检索质量提高”：

1. **逐题消耗没有对齐。** 按事后总 token 均值变化在 ±10% 内诊断，原生禁用与 Rust 仅 4/20 题接近；将阈值改为 ±5%／±20%，分别为 2／9 题。变化统一按 `原生禁用 / Rust − 1` 计算，不据此筛选样本或估计因果收益。
2. **当前全量指标是答案评分。** 本次只对部分任务补做目标定位、状态更新等代码核验，尚无覆盖全部 20 题的独立检索质量标注。裁判参考本身也有歧义或简化，分数高不保证关键事实都正确。
3. **缺少相同预算下的策略对照。** 三组自由消耗，且 Rust 不允许委派；没有观察“同样预算、两工具同时可用”时的选择与组合效果。子 Agent 内部完整读取轨迹也未保留，不能用主会话文件数比较两者的有效证据覆盖。

Conan 39 提供了“实际更低消耗、目标定位更好”的局部正例；Requests 16 提供了相反证据。当前最稳妥的说法是：**存在提高检索质量的任务级证据，整体等预算优势仍需验证。**

## 5. 下一步应怎样验证与改进

建议先复核已有答案，再做小范围预算实验；本次没有启动这些新增实验。

| 要验证的问题 | 做法与判据 |
|---|---|
| 是否承担相同检索职责 | 对每题列出必要证据：目标符号、跨模块调用关系、关键分支和状态更新；同时接受等价的有效实现，避免只匹配参考字符串。 |
| 同预算是否更好 | 预先固定每题预算及预算档位，主／子会话、工具指令、缓存输入和推理输出统一计入；接近预算时预留作答额度。比较必要证据覆盖、错误事实率、正确证据支持的答案，而不是比较调用次数。 |
| 是替代还是互补 | 保持原生工具一致，做四组：两者均禁用、仅允许 `explore`、仅允许 ZG、两者同时可用。两者同时可用组使用中性选择指令，另行说明产品提示策略，记录实际委派目标和 ZG 使用。 |
| 如何提高 ZG 证据质量 | 命中后检查关键函数／分支是否完整，按缺失证据定向扩展上下文；Requests 16 应核对 cookie 提取、合并、下一跳与 session 写回。把减少搜索轮次节省的预算用于这些核验，而不是无条件扩大所有预览。 |
| 如何提高委派质量 | 委派前验证定位假设与搜索目录，明确允许搜索测试目录；返回后由主 Agent 核验关键代码。避免 Pylint 9 中把错误前提和错误目录一起交给子 Agent。 |

优先样本可选 Conan 39、Pylint 9 的多条件定位，Conan 19、Django 32、Xarray 46 的跨模块理解，以及 Requests 16 的状态链完整性；先修正或单列歧义题。事先约定质量非劣／改进判据，避免实验后只保留支持“平替”的任务。

可向专家咨询的表述：

> 本轮 GLM 实验显示，检索型 explore 与 ZG 的职责重叠。ZG 在 Conan 39、Pylint 9 上提高了目标定位，但在 Requests 16 上虽召回相关类仍漏掉关键写回；跨模块核心任务的收益也比整体均分更温和。我们拟把“平替”限定为相同预算下完成同一组必要证据收集与验证，并通过独立证据标注和工具可用性对照判断替代／互补。这个定义和验证方案是否合理？哪些跨模块关系、分支覆盖或证据错误是必须单独评估的？
