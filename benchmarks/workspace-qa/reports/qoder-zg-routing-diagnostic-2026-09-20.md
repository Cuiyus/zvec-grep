独立诊断镜像对固定 SHA 的 Qoder npm bundle 加入两个被动观察点：

1. `MemoryContextManager.getUserContext`：检查 Qoder 实际加载的指导上下文。
2. `U3e` 请求归一化入口：检查已组装的客户端模型请求是否含指导全文和 zg 工具定义。

观察器只记录存在性、字符/行数、哈希、角色、模型、工具名及输出参数等元数据，不记录提示正文、密钥或模型隐藏推理。
它不改写请求和响应；诊断 CLI 加过观察代码，不能称作未经修改的原版二进制。
这不是服务端抓包，也不独立证明托管模型服务内部收到或如何处理请求。

zg 返回 `freshness: fresh`，三个结果均有 `matchedBy=fts+vector`，且原文内容对应合成材料。
未发现调用失败后退回 Grep 的情况。这里只核验执行和检索，不判定答案质量。

`natural` 的实际参数（保留模型原样）：

```json
{
  "limit": 30,
  "query": "公司 收入 利润 同比变化 经营业绩",
  "root": "/app",
  "vector": "[\"revenue profit year over year change annual report financial results\", \"经营情况 营业收入 净利润 毛利率 下滑 增长\"]"
}
```

注意：这里 `vector` 是一个包含 JSON 数组文本的**字符串**，并非两个数组元素。
zg 返回中它整体成为一个 supplemental query group，而 `query` 是 primary group。
提醒组同样把四条看似分开的 `queries` 序列化为一个字符串，实际返回一个 primary group，另加一个 FTS supplemental group。
因此不能按字符串里看见的条目数量统计为多条独立语义查询。
两次检索仍成功，但这反映出参数表达与预期多 query 结构可能存在偏差；本轮没有修正或重抽样。

## 附带发现：输出上限未按 CLI 值进入观察到的请求

两次实际 argv 均有 `--max-output-tokens 2048`，但观察到的 **全部六个客户端请求均为
`parameters.max_tokens = 32000`**。因此不能把诊断 README 原先写的 2,048 当作已生效硬上限。
会话级请求数、工具数、累计输入和时间限制仍由 harness 控制，两次会话都在其内完成。

静态发布包审计显示：CLI 参数写入运行时 `generateContentConfig.maxOutputTokens`；
headless `driveQuery` 将查询 options 的 `maxOutputTokens` 传入主 agent loop；
请求组装函数 `$UA` 在没有显式覆盖时取模型的默认上限。
`x4` 会原样接受合法正整数，并非将 2,048 强制抬高到 32,000。
这些代码与此次观测相符，指向参数传递路径的问题；本次没有改上游实现，也没有验证服务端最终执行值。

历史 Task 192 的 CLI 值是 16,384，历史请求未观测，不能直接断言它也一定是 32,000。
此前 `max_output_tokens_wire_verified=false` 仍成立，旧配置说明已增加该发现的链接。
该问题影响预算可信度，但没有证据表明它是 Task 192 零 zg 调用的原因。
