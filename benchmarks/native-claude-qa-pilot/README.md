# Native Claude Code + Qwen pilot

This separate pilot tests the main benchmark's native Claude agent with the existing Qwen Anthropic endpoint. The main registry supports Claude/Opus only, so a small explicit routing adapter selects Qwen without editing the registry or the native agent loop.

The completed [q001 confirmation](results/20261020-confirmation-v1/README.md) and [q002/q003 expansion](results/20261020-expansion-v1/README.md) did not establish a stable favorable benchmark set. A separate fixed [current-task repetition plan](repeat-plan-v1.json) now implements the user’s outlier-filtering request: all three existing tasks, ten fresh baseline/zg pairs each, with original questions, rubrics and runtime. Historical observations are excluded. See the study details below.

The [completed live v2 pair](results/20261020-live-v2/README.md) passed both independent execution/source audits and blinded quality review. Both answers scored 8/10 and passed; zg reported input including cache fell 63.27%, native execution wall fell 20.24%, and full slot wall including fresh indexing fell 5.24%. This meets the prospectively frozen reported-input development candidate rule. It is one previously exercised task and one pair, not a confirmed stable benefit or a favorable benchmark set. All raw answers, logs, independent reviews and the unchanged primary grading are retained.

The separate [confirmation plan](confirmation-plan-v1.json) and [decision](confirmation-decision-v1.json) scheduled exactly two fresh pairs: c01 baseline→zg and c02 zg→baseline, each on its own fork CI runner. The [wrapper](confirmation_v1.py) validates the unchanged original plan and reuses the original execution/collection function bodies, with a new protocol identity and explicit pair order. Both pairs must separately meet the original reported-input candidate conditions to confirm that signal; the development pair is excluded. Time and quality benefits remain separate outcomes. No retries, replacement trials, prompt changes or task expansion are part of this phase.

The [completed confirmation](results/20261020-confirmation-v1/README.md) **did not confirm** the signal: c01 scored baseline 9/10 versus zg 7/10, while c02 scored 8/10 each. Input decreased 51.1% and 48.9%, but c01 failed quality and score non-inferiority; outer-slot wall increased 13.7% in c01 and decreased 4.7% in c02. The original grades, separate non-scoring citation erratum, all four answers and both successful execution/source audits are retained. Only one of the two pairs passed the original primary gate. This q001 confirmation phase is closed without further sampling, and no favorable multi-task set is established.

The prior 22 custom Claude rows disabled `CLAUDE.md`, persistent sessions and task delegation. This stack enables native behavior and uses the pinned upstream Rust zg at `a424e0ce06868dc9ad8f142f57de59b8f9b58699`. It is a whole-stack development comparison, not an isolated estimate of one setting.

The user's subsequent variability requirement is implemented in the separate [statistics adapter](robust_statistics_v1.py), borrowing [PR #261](https://github.com/zvec-ai/zvec-grep/pull/261) at `5d9fc0174cd2e4baad6337164fa1abb87f900839`. It reports raw, score-trimmed and task-screened means with equal weight per task. Exactly one lowest and one highest score are removed within each task/profile when at least three trials exist; ties use trial index then original position. Every resource metric uses those same retained tuples. The planned full experiment uses ten executions per task/profile. After trimming, score sample SD and time/input-token CV are maximized across profiles for each task. A single upper-tail MAD pass screens tasks with modified Z strictly above 3.5, using the same final task set for every profile and metric. Fewer than five tasks, missing dispersion or zero MAD explicitly disable the applicable screening. Original evidence and quality/execution decisions remain retained.

The [pinned reference and validation](provenance/robust-statistics-pr261-v1/provenance.json) retain the original source and tests. Eleven selection/numeric source nodes are byte-identical; fourteen unchanged upstream test bodies and seven native-adapter tests passed. The native adapter keeps the input/accounting scope explicit, accepts separately named native and outer-slot time measurements, and preserves unknown monetary cost. This analysis was introduced after q002 outcomes had been observed and while q003 was executing; it supplements the frozen phase decision. The current two-task, one-pair-per-task expansion cannot estimate residual variability, so all observations remain and both trimming and task screening are explicitly unavailable. A passing or failing quality decision alone is never an outlier rule.

To analyze normalized native evidence without model calls, run `python robust_statistics_v1.py input.json new-report.json`. Input contains explicit `measurement_scope` and `time_scope` strings plus `cases`; each case has a unique `task_id` and `profiles.baseline.trials` / `profiles.zvec-grep.trials`. Each original trial supplies matching positive `trial_index`, `judge.total`, and numeric `metrics.input_tokens`, `output_tokens`, `tool_calls`, `agent_wall_seconds`; optional numeric measurements use distinct keys such as `outer_slot_seconds`, with unknown cost represented as `null`. Missing raw measurements are rejected rather than silently excluded. Existing output files are never overwritten.

The [fixed repetition decision](repeat-decision-v1.json) authorizes 30 fresh pairs (60 trials), with no retries, replacements or favorable early stopping. Each task has five baseline-first and five zg-first pairs; job order is predeclared and concurrency is capped at three independent fresh runners. Restricted branch pushes run provider-free preflight; exactly one subsequent fork dispatch starts paid execution after the same commit passes. The current upstream tip is `33a931e53350c039b824367efe1d44e747399e80`: its complete Rust tree is identical to the pinned binary’s revision. The one intervening change concerns benchmark container shutdown. This study keeps the previously verified harness unchanged and records that difference before execution.

The [repeat driver](repeat_live_v1.py) validates the original native controls, all three original task/source/question/rubric identities, fixed schedule, prepared exports, statistical policies, strict source policy and execution decision. It reuses unchanged native execution/collection bodies. The [strict scope policy](repeat-scope-policy-v1.json) preserves the old source-only interpretation: metadata-only enumeration outside supplied source is still a deviation, with factual-content exposure reported separately. Trimming cannot rehabilitate an invalid run.

For each task/profile, score-tail trimming retains eight of the ten original tuples, and all resource means use those exact tuples. All ten observations and exclusions remain visible. With **three distinct tasks**, the PR’s five-task MAD guard disables task-level exclusion; repetitions do not count as additional tasks. The [repeat analysis](repeat_analysis_v1.py) computes raw and trimmed equal-task estimates, score SD, time/input CV and deterministic paired within-task bootstrap intervals (10,000 resamples, seed 20261020). Profiles share bootstrap pair draws and trim independently after each draw. Report interval widths and any variance increase; reduced variability is not assumed. Quality and reported-input direction checks must agree in raw and trimmed views, and all execution/scope/metric checks must pass before a favorable observed stability conclusion. Absolute original quality-pass rates and every core failure remain separate, so a stable low-quality answer does not establish a suitable benchmark set. These intervals concern only these three previously observed tasks, with no population or billing guarantee.
