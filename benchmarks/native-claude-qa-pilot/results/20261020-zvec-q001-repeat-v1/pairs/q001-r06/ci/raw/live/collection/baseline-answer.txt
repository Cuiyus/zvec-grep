Summary of the causal chain: WAL replay recovery (`segment.cc:4193-4301`) refills the memory block through a throwaway read handle and leaves the segment's `wal_file_` member null; `flush()`'s dirty check (`segment.cc:2220-2222`) keys off that handle, so `Optimize()`'s `switch_to_new_segment_for_writing()` (`collection.cc:1517-1552`) dumps a no-op, strips the writing block from the meta, registers the segment as "persisted" with zero data blocks, and commits a new manifest while deleting the old one (`version_manager.cc:282-301`) — orphaning the WAL that still holds the only durable copy. The minimal repair is to re-attach (or otherwise mark dirty) the replayed WAL at recovery so the existing flush lifecycle runs unchanged, and the regression test is a three-process sequence: kill-after-insert → reopen + optimize with **no** intervening writes → reopen and assert the count, which is precisely the window the current `tests/db/crash_recovery` suite skips by closing gracefully and re-inserting before optimizing.
