## Summary of the failure, from the frozen source

The root cause is a single state asymmetry: after crash recovery, the recovered writing segment's live WAL handle (`wal_file_`) is **nullptr**, and `SegmentImpl::flush()` uses that handle as its "is there anything to persist?" test. So the first `flush()`/`dump()` after recovery silently persists nothing, and `Optimize()` then commits a manifest that reclassifies the data-less segment as *persisted*, orphaning the WAL that is the data's only on-disk copy. Every step returns `OK`.

---

### 1. Recovery state vs. ordinary insertion state; why the data is initially readable

**Ordinary insert path.** `SegmentImpl::Insert` (`src/db/index/segment/segment.cc:903-918`) appends the serialized doc to the WAL via `append_wal` (`segment.cc:4324-4340`), which **lazily opens the member `wal_file_`** on first write (`open_wal_file()`, `segment.cc:4303-4322`; WAL file is `<collection>/<seg_id>/<block_id>.wal`, `src/db/common/file_helper.h:74-78`). It then calls `internal_insert` (`segment.cc:837-881`), which populates in-memory state: `id_map_->upsert`, `memory_store_->insert` (a `MemForwardStore`, created lazily by `init_memory_components`, `segment.cc:4119-4157`), the in-memory vector indexers, `doc_ids_.push_back(g_doc_id)`, and the writing-block counters (`segment.cc:874-878`).

**Recovery path.** `CollectionImpl::recovery()` (`src/db/collection.cc:1836-1892`) loads the manifest (`VersionManager::Recovery`, `src/db/index/common/version_manager.cc:190-241`), opens persisted segments read-only, then opens the writing segment from `v.writing_segment_meta()` (`collection.cc:1880-1887`). `SegmentImpl::Open` calls `recover()` **only when the meta has a `writing_forward_block`** (`segment.cc:484-501`).

`SegmentImpl::recover()` (`segment.cc:4193-4301`) opens the WAL through a **local, temporary handle** `recover_wal_file` (`segment.cc:4206-4215`, closed by `AILEGO_DEFER`), replays each record through `internal_insert`/`internal_update`/`internal_upsert`/`internal_delete` (`segment.cc:4234-4283`), and patches `mem_block.max_doc_id_` (`segment.cc:4285-4288`). Crucially, it **never assigns the member `wal_file_`** — the only caller of `open_wal_file()` is `append_wal()` (`segment.cc:4327-4329`), which never runs if no new documents are inserted.

So the differing state after recovery is: *identical in-memory structures, but `wal_file_ == nullptr` instead of an open handle over a WAL that has records*.

**Why the recovered data is readable:** every read path is served from the replayed in-memory state, not from persisted blocks. `Stats()` sums `segment->doc_count()` = `doc_ids_.size()` (`collection.cc:403-442`, `segment.cc:589-600`); `get_all_segments()` includes the writing segment whenever `doc_count() > 0` (`collection.cc:2076-2082`); `Fetch` resolves pk→doc_id via `id_map_` (repopulated by replay through `id_map_->upsert`, `segment.cc:852-853`) and reads the row from `memory_store_` (`collection.cc:1757-1790`); vector search uses `memory_vector_indexers_`.

### 2. The call sequence and the exact condition that let `optimize()` succeed without preserving the data

1. `CollectionImpl::Optimize` (`collection.cc:779-915`) sees `writing_segment_->doc_count() != 0` (`collection.cc:794`) and calls `switch_to_new_segment_for_writing()` (`collection.cc:1517-1552`).
2. That calls `writing_segment_->dump()` (`segment.cc:2197-2215`), which first calls `flush()` (`segment.cc:2217`). **The exact condition is `segment.cc:2220-2222`:**
   ```cpp
   if (wal_file_ == nullptr || !wal_file_->has_record()) {
     return Status::OK();
   }
   ```
   After recovery with no new inserts, `wal_file_` is null, so `flush()` returns `OK` having done **nothing**: no `memory_store_->flush()` (`2233-2236`), no `finish_memory_components()` (`2288-2291` → `segment.cc:4342-4384`, the only code that writes the forward-block file and adds `SCALAR`/`VECTOR_INDEX` `BlockMeta`s to the segment meta), no `update_version()` (`2300-2302` → `4414-4426`), no WAL removal (`2304-2315`). `dump()` then seals indexers and sets `sealed_ = true` — all succeed.
3. `switch_to_new_segment_for_writing` proceeds anyway: the recovered segment is added to `segment_manager_` (`collection.cc:1522`), its meta's writing block is erased via `remove_writing_forward_block()` (`collection.cc:1538`; `meta.h:263-265` sets the optional to `nullopt`), the meta is added as a **persisted** segment meta (`collection.cc:1539`), and `version_manager_->apply()` + `flush()` write a new `MANIFEST.N` (`collection.cc:1546-1549`; `version_manager.cc:282-301`; manifest fields incl. optional `writing_forward_block` at `src/db/proto/zvec.proto:216-220`). **This is the point of no return:** the manifest now says the recovered segment is persisted with zero data blocks and no writing block, so nothing on disk references `<seg>/0.wal` anymore — though the file itself still exists.
4. `build_compact_task` (`collection.cc:917-1005`) on the single recovered segment with no deletes (`rebuild == false`) produces a `CreateVectorIndexTask` (`collection.cc:991-1001`), not a data-moving `CompactTask`. `ExecuteCreateVectorIndexTask` (`segment_helper.cc:1113-1125`) → `create_all_vector_index` (`segment.cc:1617-1640`). With the default index params (`DefaultVectorIndexParams` is **FLAT**, `src/include/zvec/db/index_params.h:437-439`, and FLAT fields are marked indexed at segment creation, `segment.cc:534-539`, carried in the manifest), `create_vector_index` hits the skip branch `segment_meta_->vector_indexed(column) && params equal` (`segment.cc:1685-1690`) and returns OK with an unchanged copy of the (block-less) meta. Even with a non-default index type, the path merges only the *persisted* `vector_indexers_[column]` (`merge_vector_indexer`, `segment.cc:1642-1668`) — the recovered vectors sit in `memory_vector_indexers_`, which `finish_memory_components` never moved — so it would build an empty index and still return OK.
5. Optimize commits the version (`update_persisted_segment_meta`, `apply`, `flush`, `collection.cc:822-877`) and calls `reload_vector_index` on the same segment object (`collection.cc:902-909`; `segment.cc:1882-1940`), which swaps `segment_meta_` but leaves `doc_ids_`, `memory_store_`, and `memory_vector_indexers_` intact. `Optimize` returns `Status::OK()`.
6. **Next open:** `recovery()` opens the old segment as a *persisted* segment; with no `writing_forward_block` in its meta, `SegmentImpl::Open` skips `recover()` entirely (`segment.cc:484-510`), and WAL replay only ever targets the path derived from the *current writing* segment's (segment id, block id) (`segment.cc:4198-4199`). The orphaned `0.wal` is never read again. `load_persist_scalar_blocks` (`segment.cc:3913-3957`) finds no `SCALAR` blocks, so `doc_ids_` stays empty and `doc_count()` is 0. The id-map entries (RocksDB `Put`, synchronous, `src/db/index/common/id_map.cc:97-103`) still exist, so `Fetch` resolves the pk but `local_segment_by_doc_id` finds no covering segment and yields a null result (`collection.cc:1780-1786`) — the documents are gone.

Why the control (no crash) works: the first insert opened `wal_file_`, so in step 2 `has_record()` is true (`local_wal_file.h:74-76`: file size > header) and `flush()` runs the full path — persisting the forward block, adding block metas, committing the manifest via `update_version`, and removing the WAL — *before* the switch commits the segment as persisted.

(Aside: the same no-op gate makes an explicit `Collection::Flush()` after recovery-without-inserts a silent no-op too — `collection.cc:340-361, 389-395` — but that alone doesn't lose data because the manifest still points at the WAL. It is Optimize's *version commit* that converts the silent no-op into permanent loss. The same `switch_to_new_segment_for_writing` is also used by `CreateIndex`/`DropIndex` (`collection.cc:501-503, 674-677`), so those share the defect.)

### 3. Why `OK` and same-handle statistics prove nothing here

- **`OK` is hollow:** the decisive step *succeeded by early return* (`segment.cc:2220-2222` returns `OK` for "WAL handle not open", conflating "nothing to persist" with "never opened"). The index task succeeded by *skipping* (`segment.cc:1685-1690`). Manifest writes genuinely succeeded. No code ever reconciles "in-memory doc count" against "doc count accounted for by manifest-visible blocks/WAL".
- **Stats read the heap, not the disk:** `Stats()` computes `doc_count` from `doc_ids_.size()` and `index_completeness` from `meta()->vector_indexed(...)` (`collection.cc:403-442`); after `reload_vector_index` the recovered segment object still holds all N docs in `doc_ids_`/`memory_store_`/`memory_vector_indexers_`. `Fetch`/`Query` serve from the same RAM. None of these consult `MANIFEST.N`, the forward-block files, or the WAL — which are the *only* inputs to the next `Open` (`version_manager.cc:190-241`, `collection.cc:1861-1887`, `segment.cc:484-510, 3913-3957`).
- Durability in this design means exactly one of: (a) the manifest's writing-block meta references a WAL containing the record, or (b) `finish_memory_components` converted the row into persisted blocks and the manifest was flushed. After Optimize, neither holds — yet every observable signal in-process is green.

### 4. Smallest repair principle and a regression test (described, not implemented)

**Repair principle — restore the invariant "a writing segment whose writing block has records has its WAL open," so recovered writes are indistinguishable from in-process writes.** The minimal change is at the end of `SegmentImpl::recover()` (or in `Open` right after a successful `recover()`, `segment.cc:499-501`): when the replayed WAL exists/has records, call `open_wal_file()` to bind the member `wal_file_` (it opens the existing file for append, `local_wal_file.cc:92-106`). Then `has_record()` is true, and `flush()`/`dump()`/`switch_to_new_segment_for_writing`/`Close` all take the full persist-then-commit path, including proper WAL removal. An equally small alternative is to change the flush gate itself (`segment.cc:2220-2222`) to test *unpersisted memory data* (e.g., `memory_store_ && memory_store_->num_rows() > 0`, or writing-block `doc_count != 0`) instead of the WAL handle, with WAL cleanup done by path when `wal_file_` was never opened. What should **not** be done is patching only `Optimize` (e.g., pre-flushing there) — `Close`, `CreateIndex`, `DropIndex`, and the column DDL paths reach the same no-op flush.

**Regression test** (reuses the existing fork+SIGKILL harness style in `tests/db/crash_recovery/optimize_recovery_test.cc:91-107`):

1. **Process A:** create collection; insert N docs (N small enough to avoid buffer/segment rollover, per `ready_for_dump_block`, `segment.cc:2959`); die abruptly (`_exit`/SIGKILL) without `Flush`.
2. **Process B:** open; assert `Stats().doc_count == N` and all N pks fetch. Call `Optimize()`; assert OK. Optionally (white-box, the sharpest detector): load the newest `MANIFEST.*` via `Version::Load` and assert the persisted metas account for N docs — i.e., some `SCALAR` block with total `doc_count == N`, *or* a writing block whose WAL file exists. Under the bug this fails immediately: the manifest lists a segment with zero blocks.
3. **Process B** closes cleanly; **Process C** reopens and asserts `Stats().doc_count == N`, every pk fetches with correct fields/vectors, and a vector query for the inserted vectors returns N hits. Under the bug C sees 0 (fetches return null).
4. **Control leg:** same as A→B without the crash (insert, optimize, reopen, expect N) — already passes today; guards against over-correction.
5. **Same-root legs:** crash → reopen → explicit `Flush()` only → reopen → expect N, plus manifest shows persisted blocks (today the reopen passes but the manifest assertion fails — an early signal); and crash → reopen → `CreateIndex` on a scalar column → reopen → expect N (exercises the shared `switch_to_new_segment_for_writing` path).

**Established from source vs. requiring execution.** Everything above is derived by reading the frozen tree (cited file:line); I did not build or run anything. Reading alone establishes the no-op flush gate, the manifest commit of a block-less segment, the reopen path that skips WAL replay, and the empty-`doc_ids_` outcome. What would require executing a test: end-to-end confirmation on a real binary (e.g., that `Optimize` returns OK for a non-default index type where `merge_vector_indexer` merges an empty list, and the precise `Fetch` symptom after reopen). The FLAT-default path — which matches the reported scenario — involves no step whose success is in doubt from source. A secondary latent hazard also visible in source but not exercised by the single-segment scenario: if ≥2 persisted segments triggered a real `CompactTask`, `scan()` would call `writing_forward_block().value()` on the emptied optional (`segment.cc:2837`) with rows still in `memory_store_` — a `bad_optional_access` rather than a silent loss.
