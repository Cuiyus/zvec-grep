# Root cause: recovery replays the WAL but leaves `wal_file_ == nullptr`, and `flush()` uses that member as its "is there anything to persist" test

## 1. State difference: recovery path vs. ordinary insertion path

**Ordinary insertion** — `SegmentImpl::Insert` (`src/db/index/segment/segment.cc:903-918`) calls `append_wal(doc)` **before** `internal_insert(doc)`. `append_wal` (`segment.cc:4324-4340`) lazily runs `open_wal_file()` (`segment.cc:4303-4322`), which sets the member `wal_file_` to a handle on `<collection>/<seg_id>/<block_id>.wal` (`src/db/common/file_helper.h:74-78`). So after any insert, the writing segment holds: RAM state (`doc_ids_`, `memory_store_`, memory indexers, in-memory writing-block counters — `internal_insert`, `segment.cc:837-881`) **plus a live `wal_file_` handle whose `has_record()` is true** (`src/db/index/storage/wal/local_wal_file.h:75-77`: file size > header).

**Recovery** — `CollectionImpl::recovery()` (`src/db/collection.cc:1836-1892`) opens the writing segment; `SegmentImpl::Open` sees a `writing_forward_block` in the meta and calls `recover()` (`segment.cc:490-501`). `recover()` (`segment.cc:4193-4301`) opens the WAL into a **local** `recover_wal_file` that is closed on scope exit (`segment.cc:4206-4215`), and replays each record by calling `internal_insert/internal_update/internal_upsert/internal_delete` **directly** (`segment.cc:4250-4266`) — bypassing `append_wal`. 

So after recovery the RAM state is identical to the insert case (which is why reads work): `doc_count()` is `doc_ids_.size()` (`segment.cc:589-600`), `fetch` serves rows from `memory_store_` while `has_writing_forward_block()` (`segment.cc:2743-2757`), and `scan` unions persisted blocks with the memory store (`segment.cc:2825-2841`). **The one differing piece of state is the member `wal_file_`, which stays `nullptr`** even though the on-disk WAL holds every recovered doc. The invariant flush depends on — “`wal_file_ == nullptr` ⟺ nothing unpersisted” (a full flush removes the WAL and resets the handle, `segment.cc:2304-2315`) — is broken exactly in this window. Note the version file on disk is also stale (last written pre-crash; `update_version` runs only inside a full flush, `segment.cc:2300-2302, 4414-4426`), so the WAL is the *only* durable copy of the docs.

## 2. Call sequence and exact condition letting `optimize()` succeed while orphaning the data

In the recovering process, `CollectionImpl::Optimize` (`collection.cc:779-915`):

1. `collection.cc:794`: `writing_segment_->doc_count() != 0` — true, because replay filled `doc_ids_` — so it calls `switch_to_new_segment_for_writing()` (`collection.cc:796`).
2. `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`):
   - `writing_segment_->dump()` (`1519`) → `SegmentImpl::dump()` (`segment.cc:2197-2215`) → `flush()`, which **early-returns `Status::OK()` at `segment.cc:2220-2222` because `wal_file_ == nullptr`**. Nothing persists: no `memory_store_->flush()` (2233-2236), no indexer flushes (2238-2264), no `finish_memory_components()` (2288-2298 → 4342-4411, the step that converts the writing block into persisted block metas and demotes memory indexers to persisted ones), no `update_version()` (2300-2302), no WAL removal (2304-2315). `dump()` then seals and returns OK.
   - The old segment is registered as a persist segment (`1522`); a **new empty writing segment with a new id** is created (`1527-1534`); the old segment’s live meta is mutated in place — `remove_writing_forward_block()` (`1537-1538`; `meta()` returns the shared `segment_meta_`, `segment.cc:585-587`; the setter nulls the optional, `src/db/index/common/meta.h:263-265`) — and added to the version as a *persisted* meta (`1539`). `SegmentMeta::doc_count()` counts only the writing block plus persisted SCALAR blocks (`meta.h:307-318`), so this meta describes **zero docs, zero blocks**.
   - `version_manager_->apply(version)` + `flush()` (`1546-1549`) **durably commits that fiction**. This is the exact point of no return: on disk, the old segment is “persisted-empty” with no writing block, and the WAL is now orphaned — replay on any future open is gated on a writing block existing in the meta (`segment.cc:484-501`), and the new writing segment has a different id/directory, so `<old_seg>/<block>.wal` is never read again. Removing the writing block also disconnects the RAM copy in-process (fetch’s memory branch requires `has_writing_forward_block()`, `segment.cc:2744`).
3. Optimize proceeds: `persist_segments` = [old segment] (`802-803`); `build_compact_task` (`917-1005`) with one group and `rebuild=false` produces a single `CreateVectorIndexTask` (`991-1001`). `ExecuteCreateVectorIndexTask` (`src/db/index/segment/segment_helper.cc:1113-1125`) → `create_all_vector_index` (`segment.cc:1617-1640`): for FLAT fields it takes the “already indexed, skip” path (`1685-1690`; FLAT is marked indexed at `Create`, `segment.cc:534-539`); for other index types it merges only from `vector_indexers_[column]` — the *persisted* indexers, which are empty (`1642-1668`). Either way it succeeds without ever touching `memory_store_` or the memory indexers.
4. Optimize updates the persisted meta with the task output (`863-867`), applies + flushes the version again (`871-877`), reloads the (empty) vector index in RAM (`902-909`), and returns OK (`914`).

**The exact condition:** every durability-relevant decision reads either the `wal_file_` member (flush’s guard) or the persisted meta (0 blocks after `remove_writing_forward_block`), and none of them reads the replayed RAM state or the WAL file on disk. The one counter that still reflects the recovered docs, `doc_ids_.size()`, is used only as the *trigger* at `collection.cc:794`, never as a check. Every step therefore legitimately returns OK.

On the next open, `recovery()` (`collection.cc:1858-1887`) rebuilds purely from the flushed version: the old segment opens read-only with no blocks and no writing block (so no `recover()`/replay), the new writing segment is empty → 0 docs. If a later compaction ever consumes and destroys the phantom segment, `destroy()` + destructor → `cleanup()` deletes the whole segment directory, WAL included (`segment.cc:2326-2338`, `segment.cc:110-120`, `src/db/index/segment/segment_manager.cc:45-56`).

**Control case:** with no crash, `wal_file_` has records, so Optimize’s `dump()` runs the *full* flush body — data files written, blocks moved into `persisted_blocks_`, version flushed, WAL removed only after (`segment.cc:2224-2315`) — and the meta persisted at `collection.cc:1539` describes real blocks. Hence no loss. Also note: had process B inserted even one new doc before optimizing, `open_wal_file()` would have re-adopted the existing WAL (`segment.cc:4308-4309`, `create_new=false`), restoring the invariant — which is why the bug hides outside the precise “recover → no writes → optimize” window. The same hazard applies to every other `switch_to_new_segment_for_writing` trigger (`CreateIndex` `collection.cc:501`, `DropIndex` `674`, `AddColumn` `1154`, `DropColumn` `1226`, `AlterColumn` `1310`) and to `Collection::Flush()` itself, which routes straight into the same no-op `flush()` (`collection.cc:380-395`).

## 3. Why OK + same-handle stats prove nothing here

- `Optimize`’s `Status::OK()` reports only that no step *errored*. The step that would have created durability short-circuited at its guard (`segment.cc:2220-2222`); success is vacuous — fully consistent with zero bytes of doc data written.
- `Stats()` (`collection.cc:403-442`) sums `segment->doc_count(filter)` over `get_all_segments()`, which is the in-RAM `doc_ids_.size()` (`segment.cc:589-600`). The old segment is still in `segment_manager_` (added at `collection.cc:1522`; in the single-segment flow it is never destroyed), so the same handle keeps reporting N docs from volatile memory; `index_completeness` can read 1.0 because it checks the meta flag `vector_indexed()` (`collection.cc:431-438`). Nothing in `Stats()` consults the version file, block files, or WAL — the actual inputs to the next `VersionManager::Recovery` (`collection.cc:1846-1888`). Durability in this design is established only inside flush’s full body (persist blocks → `update_version`/version flush → WAL removal), which never ran.

## 4. Smallest repair principle and regression-test sequence (described only)

**Repair principle:** restore the invariant “the writing segment knows about its unflushed WAL records” at the end of recovery. Smallest change: in `SegmentImpl::recover()`, after a successful replay of ≥1 record, adopt the WAL as the member handle — e.g., call `open_wal_file()` (`segment.cc:4303-4322`), which already reopens an existing WAL with `create_new=false` — instead of leaving `wal_file_` null (the local `recover_wal_file` is closed at `4215`). Then the existing guard evaluates `has_record()` against the real file (true), and `dump()/flush()/Optimize/Close/Flush` all take the full persistence path with the existing correct ordering (data → version → WAL removal, `segment.cc:2224-2315`). No other call site changes. (An equivalent-but-larger alternative is to make the guard test durable state — WAL file existence or memory-vs-persisted doc delta — rather than the handle; and an eager variant would flush immediately at end of recovery. Adoption is the minimal one.) One implementation nuance: adopt *after* the replay loop, since `internal_insert`’s rollover check (`segment.cc:841-844`) can invoke `flush()` mid-replay.

**Regression test** (fits the existing fork/exec/kill harness in `tests/db/crash_recovery/` — see `optimize_recovery_test.cc:54-120` and helper `collection_optimizer.cc`; the current `CrashDuringOptimize` misses this because its writer exits via `collection.reset()`, a clean close that fully flushes):

1. **Process A (writer):** create collection, insert N docs (N small enough to avoid `ready_for_dump_block` rollover), verify in-process `Stats()==N`, then die abruptly — `kill(getpid(), SIGKILL)` / `_exit()` — with **no** `Flush()`/close, guaranteeing a non-empty WAL and stale version.
2. **Process B (optimizer, no writes):** `Collection::Open` (triggers replay); assert `Stats().doc_count == N` and `Fetch` of sample pks matches; call `Optimize()`; assert OK; optionally assert `Stats()==N`; exit cleanly.
3. **Process C (verifier — the assertion that fails today):** `Collection::Open` again; assert `Stats().doc_count == N`, `Fetch` returns all N docs with correct content, and a `Query` returns hits. From the source, current code yields 0 here.
4. **Hardening variants:** (a) process B inserts 1 doc before optimizing (guards the re-adoption path); (b) process B calls `Flush()` instead of `Optimize()` (same no-op bug via `collection.cc:380-395`); (c) durable-state assertions after step 2: either no `*.wal` remains under the collection path, or the persisted metas in the version account for N docs; (d) a multi-persist-segment variant, since there `ReduceScalar`’s `scan()` on the phantom segment would dereference the removed optional at `segment.cc:2837` — a predicted crash rather than silent loss.

**Established from source vs. requiring execution:** every code path, guard, line-cited call chain, the test-coverage gap, and the prediction that process C observes 0 docs (recovery reads only the flushed version; the flushed version describes zero blocks and no writing block) are established by reading the frozen tree. I did **not** build or run anything: the end-to-end data-loss outcome, the `bad_optional_access` prediction in variant (d), and any timing-dependent behavior are inferences that would need an actual reproduction to confirm empirically.
