# Root-cause analysis: recovered docs lost after `optimize()`

All findings below are from reading the frozen tree (`/workspace`, the zvec repo); I executed nothing. The root cause is a state asymmetry: **WAL recovery replays documents into memory but never re-attaches a live WAL handle, and `SegmentImpl::flush()` uses "live WAL handle with records" as its only test for "there is unpersisted data" — so the flush inside `optimize()`'s segment switch is a silent no-op that returns OK, while the version manifest is durably rewritten to declare the segment persisted.**

## 1. Recovery path vs. ordinary insertion path

**Ordinary insertion** (`src/db/index/segment/segment.cc:903–989`): every public write (`Insert/Update/Upsert/Delete`) calls `append_wal(doc)` *before* `internal_insert/...`. `append_wal` (`segment.cc:4324–4340`) lazily calls `open_wal_file()` (`segment.cc:4303–4322`) when `wal_file_` is null. So any segment that accepted a write **in this process** has `wal_file_ != nullptr`, and the file grows past its 64-byte header (`local_wal_file.h:75–77`, `has_record()` = `file_.size() > sizeof(header_)`).

**Recovery path**: `CollectionImpl::recovery()` (`src/db/collection.cc:1836–1892`) opens the writing segment, and `SegmentImpl::Open` calls `recover()` when the meta has a writing forward block (`segment.cc:484–510`). `SegmentImpl::recover()` (`segment.cc:4193–4301`):

- opens the WAL through a **separate local handle** `recover_wal_file` (4206–4214), closed by `AILEGO_DEFER` (4215) — it is never assigned to the member `wal_file_`;
- replays each record via `internal_insert/internal_update/internal_upsert/internal_delete` **directly** (4250–4266), bypassing `append_wal`.

`internal_insert` (`segment.cc:837–881`) populates `id_map_` (853), `memory_store_` (857), scalar/FTS/vector in-memory indexers (861–872; vectors go to `memory_vector_indexers_`, `segment.cc:763`), the writing-block meta counters (874–876), and `doc_ids_` (878). **That is why the recovered data is immediately readable**: `Stats()` sums `segment->doc_count()` (`collection.cc:403–442`), which is `doc_ids_.size()` minus deletes (`segment.cc:589–599`), and fetch/query read `memory_store_` and the memory indexers.

The decisive difference: after recovery the segment holds N docs in memory, an N-record WAL file on disk, and **`wal_file_ == nullptr`** — the segment is blind to its own pending state.

## 2. The `optimize()` sequence and the exact condition

`CollectionImpl::Optimize` (`collection.cc:779–915`):

1. `writing_segment_->doc_count() != 0` is true (recovered docs in `doc_ids_`) → `switch_to_new_segment_for_writing()` (`collection.cc:1517–1552`).
2. That calls `writing_segment_->dump()` (`segment.cc:2197–2215`) → `flush()` (`segment.cc:2217–2324`), which hits the gate at **`segment.cc:2220–2222`**:
   ```cpp
   if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();
   ```
   This is the exact condition. For the recovered segment `wal_file_` is null, so `flush()` returns OK having done **nothing**: no `memory_store_->flush()` (2233–2236), no `finish_memory_components()` (2288–2298; impl at 4342–4368, which would write the forward-block meta into `persisted_blocks`), no `update_version()` (2301; impl 4414–4427), and no WAL removal (2304–2315). `dump()` then seals indexers and sets `sealed_ = true` (2204–2212) — still OK.
3. `switch_to_new_segment_for_writing` proceeds as if the dump had persisted the data: the old segment (say id 0) is registered as a persist segment (1522), **`remove_writing_forward_block()` strips the in-memory block from its shared meta** (1538), the stripped meta is added to the new version as a *persisted* segment (1539), a fresh writing segment id 1 is created (1527–1531), and `version_manager_->apply/flush` (1546–1549) durably writes a new MANIFEST, deleting the previous one (`src/db/index/common/version_manager.cc:282–300`).
4. Back in `Optimize`: with one small persist segment and no rebuild trigger, `build_compact_task` produces a single `CreateVectorIndexTask` (`collection.cc:991–1001`), executed via `segment_helper.cc:1113–1125` → `create_all_vector_index` (`segment.cc:1617–1640`). For default/FLAT params it short-circuits (1685–1690); otherwise it merges from `vector_indexers_[column]` (1652), which is empty because the recovered vectors live in `memory_vector_indexers_`. Version update + flush succeed (872–877), `reload_vector_index` swaps indexers in memory (905–909). **`Optimize` returns OK.**

Why the data is gone on the next open: the old segment's WAL file still physically exists (removal happens only inside a *successful* flush, `segment.cc:2304–2313`), but it is orphaned. On reopen, segment 0 is a persist segment whose meta has **no writing forward block**, and `SegmentImpl::Open` calls `recover()` only when `writing_block.has_value()` (`segment.cc:484–510`); the new writing segment (id 1) has a different WAL path (`MakeWalPath` keys on segment id + block id, `file_helper.h:74`, `segment.cc:4305–4306`). Nothing ever replays or deletes the old WAL; the persisted segment has zero blocks, so count/fetch return 0.

**Why "without inserting any additional documents" is essential**: a single new write would call `append_wal` → `open_wal_file()`, which reopens the *existing* WAL with `create_new = false` (`segment.cc:4308–4312`; `local_wal_file.cc:92–106` opens at end for append). Then `wal_file_ != nullptr` and `has_record()` is true (file-size based), so the next `flush()/dump()` takes the full persist path and everything — including the recovered docs — is saved. New writes *mask* the bug. (Note the same gate also makes an explicit `Flush()` in the recovering process a silent no-op: `collection.cc:389–395` → `segment.cc:2220`.)

**Why the control case works**: inserts in the same process leave `wal_file_` attached with records, so `dump()`→`flush()` executes fully: memory store flushed, `finish_memory_components()` moves the block into `persisted_blocks` (4342–4368), version updated and flushed (4414–4427), and only then is the WAL removed (2304–2315). The segment switched to "persisted" genuinely is persisted.

## 3. Why success + same-handle statistics prove nothing here

- **Every status is legitimately OK.** The flush gate *returns success* for "nothing to do" (`segment.cc:2221`); dump, version `apply`, and version `flush` all succeeded — but what they durably committed is a manifest declaring segment 0 persisted **with no blocks** and no writing block. Success attests that the *metadata transition* committed, not that document bytes reached any persisted block. The durability contract ("WAL removed only after data is in a committed version") is inverted: the version was committed while the data existed only in RAM and in an orphaned WAL.
- **Same-handle stats read the same RAM that recovery populated.** `Stats()` sums `doc_count()` over the live `Segment::Ptr` objects (`collection.cc:403–442`, `segment.cc:589–599`); segment 0 remains in `segment_manager_` holding `doc_ids_`/`memory_store_` (`collection.cc:1522`). No code path in that process re-reads the committed manifest, so nothing observable in-process reflects what was written to disk. Only a fresh `Open` — which trusts the version and skips WAL replay for block-less persist segments — exposes the loss.
- A related divergence (source-level inference): `id_map_` is RocksDB-backed and recovery's `internal_insert` did `upsert` Puts (`segment.cc:853`; `src/db/index/common/id_map.cc:102–103`), so pk→doc_id entries can outlive the forward data; after reopen, `Fetch` may resolve the pk but find no rows, and re-`Insert` of the same pk can hit `AlreadyExists` (`segment.cc:906–909`). The exact reopen symptom (empty result vs. error) would need execution to pin down.

## 4. Smallest repair principle and regression test

**Principle (invariant to restore):** *after WAL replay, a writing segment must regard its recovered records as unpersisted; `flush()/dump()` must persist memory blocks and commit them into the version before the WAL is eligible for removal; and a writing segment must never be converted into a persist segment (writing block stripped, meta committed) unless that persistence actually happened.*

**Smallest repair (describe-only):** at the end of `SegmentImpl::recover()` (`segment.cc:4193–4301`), when a WAL file existed, call `open_wal_file()` to attach `wal_file_` to that existing file. `open_wal_file` already handles this case (`create_new = false` when the file exists, `segment.cc:4308–4312`) and `LocalWalFile::open` seeks to end for appending (`local_wal_file.cc:104–106`), so later writes append after the recovered records. Since `has_record()` is file-size based (`local_wal_file.h:75–77`), the existing `flush()` gate then evaluates true and the *unchanged* persist machinery runs — memory block written, version updated, WAL removed only afterwards (`segment.cc:2231–2315`). No caller changes. (Equivalent alternative: replace the gate at `segment.cc:2220` with a test of actual unpersisted state — `memory_store_ != nullptr`, writing-block `doc_count_ > 0`, or WAL-file existence. A cheap second-line guard: `switch_to_new_segment_for_writing` should fail rather than strip the writing block if, after `dump()`, the block still holds unpersisted docs.)

**Regression test (describe-only), reusing `tests/db/crash_recovery/` harness** (`data_generator.cc` with SIGKILL-mid-insert as in `write_recovery_test.cc:53–126`, `collection_optimizer.cc`, `utility.h`):

1. **Crash writer**: spawn `data_generator` inserting a small N (well under `max_doc_count_per_segment`, so no rollover); SIGKILL it mid-run, before any `Flush()`/`Close()`. Assert a `*.wal` file exists and the latest manifest still names a writing segment.
2. **Recover (process B)**: `Collection::Open`; assert `Stats().doc_count == N' > 0`, `Fetch` of sampled pks matches `CreateTestDoc`, and a top-k query hits.
3. **Optimize with zero writes (process C or same)**: run `collection_optimizer` (`Open → Optimize → close`); assert OK. Crucially, **no inserts between recovery and optimize** — the existing `optimize_recovery_test.cc` inserts 500 more batches after recovery (lines 207–218) before optimizing, which re-attaches the WAL via `append_wal` and masks this bug; that is precisely the coverage gap (no current test chains crash → reopen → optimize-with-no-writes → reopen).
4. **Verify durability (fresh open)**: `Collection::Open` again; assert `Stats().doc_count == N'`, every pk fetches byte-equal, query top-1 is `pk_0`, and no orphaned `*.wal` remains. Pre-fix this fails with 0 docs; post-fix it passes.
5. Optional masking-control variant: repeat with one insert before optimize — passes even pre-fix, confirming the `wal_file_`-reattachment mechanism.

**Established from source vs. requiring execution.** The entire causal chain — `recover()` bypassing `append_wal` and leaving `wal_file_` null; the `flush()` early-return gate; `dump()`'s reliance on `flush()`; the writing-block strip + manifest commit in `switch_to_new_segment_for_writing`; WAL orphaning because `recover()` runs only for metas with a writing block; in-memory-only stats — is established by reading the code. What I could not establish without running it: the exact reopen symptom (silent count 0 vs. load error); whether `Optimize` returns OK for non-FLAT schemas, since `merge_vector_indexer` would merge an *empty* `vector_indexers_[column]` (`segment.cc:1642–1668`) and core `Merge` behavior on empty input is unverified here; the fate of the resulting inconsistent vector-index block meta (claims `doc_ids_.size()` docs, `segment.cc:1720–1727`); and a latent hazard that if a multi-segment `CompactTask` were built instead, its `scan()` would call `writing_forward_block().value()` on the stripped meta while `memory_store_` is non-empty (`segment.cc:2825–2839`) — undefined behavior, not exercised in the single-segment scenario described. I did not run any reproduction.
