## Root cause in one sentence

`SegmentImpl::flush()` decides whether the writing segment has unpersisted data by looking at the **lazily-attached WAL member handle** (`wal_file_ == nullptr || !wal_file_->has_record()` → return `OK`, `src/db/index/segment/segment.cc:2220-2222`), but the crash-recovery path replays the WAL through a **separate local handle** and never attaches the member (`segment.cc:4206-4215`, `4303-4330`) — so after recovery the segment is full of unpersisted data yet looks "clean"; `Optimize()` then converts it into a "persisted" segment with a no-op flush and rewrites the on-disk version without a writing block, which orphans the WAL that was the data's only durable copy.

All of the following is source analysis of the frozen tree; I did not build or run anything.

---

### 1. State that differs between recovery and ordinary insertion; why reads work

**Ordinary insert** (`SegmentImpl::Insert`, `segment.cc:903-918`): `append_wal(doc)` → on first write `open_wal_file()` attaches the member `wal_file_` (`segment.cc:4324-4340`, `4303-4322`) and appends the record; then `internal_insert(doc)` (`segment.cc:837-881`) populates `id_map_`, `memory_store_`, scalar/FTS/vector indexers, `mem_block.doc_count_/max_doc_id_`, and `doc_ids_`. Net state: memory populated **and** `wal_file_` attached.

**Recovery** (`CollectionImpl::recovery()` `src/db/collection.cc:1836-1892` → `SegmentImpl::Open` → `recover()`, gated on `writing_forward_block().has_value()` at `segment.cc:484-501`): `recover()` (`segment.cc:4193-4301`) opens the WAL file `<collection>/<seg_id>/<block_id>.wal` (`src/db/common/file_helper.h:74-78`) into a **local** `recover_wal_file`, replays each record directly into `internal_insert/update/upsert/delete`, and closes it on scope exit (`segment.cc:4215`). It also bumps `mem_block.max_doc_id_` (`segment.cc:4285-4288`). Net state: **all the same in-memory structures are populated, but the member `wal_file_` remains `nullptr`** — nothing else in `Open` attaches it; only the next user write's `append_wal()` would.

Why reads work: counting/fetching never touch disk state the reopen would use. `doc_count()` is `doc_ids_.size()` (`segment.cc:589-599`), `Stats()` sums per-segment `doc_count` (`collection.cc:403-442`), and fetches read `memory_store_` via the still-present writing-block meta. The WAL on disk still holds every record — it is the data's *only* durable representation, and it is still referenced by the version's `writing_segment_meta` at this point, so a plain close/reopen keeps recovering it.

(Incidental: `recover()` declares `Status status;` at `segment.cc:4249` and never assigns it from the `internal_*` calls, so replay errors are logged as successes — not the cause here, but a symptom of the same path.)

### 2. Call sequence and exact condition letting `optimize()` succeed while losing the data

1. `CollectionImpl::Optimize` (`collection.cc:779-810`): `writing_segment_->doc_count() != 0` is true (doc_ids_ populated by replay) → `switch_to_new_segment_for_writing()` (`collection.cc:794-800`).
2. `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`):
   - `writing_segment_->dump()` (`segment.cc:2197-2215`) → `flush()` → **the exact condition: `wal_file_ == nullptr` at `segment.cc:2220` short-circuits to `return Status::OK()`**. Nothing runs: no `memory_store_->flush()`, no `finish_memory_components()` (`segment.cc:4342-4413` — the *only* code that writes the forward-block file, moves `memory_vector_indexers_` into persisted `vector_indexers_`, and adds SCALAR/VECTOR block metas), no `update_version()`, and no WAL removal (`segment.cc:2304-2315`). `dump()` then seals indexers and sets `sealed_ = true` as if persistence had happened.
   - The old segment is registered as a persist segment (`collection.cc:1522`), a new empty writing segment is created (1527-1531), **`remove_writing_forward_block()`** strips the writing block from the old segment's meta (1537-1538; `src/db/index/common/meta.h:263-265` sets the `std::optional` to `nullopt`), the old meta is added as *persisted* (1539), and the version is applied and **flushed to the manifest** (1546-1549 → `src/db/index/common/version_manager.cc:282-301`). **This is the instant the loss becomes durable**: disk now says "this segment is persisted, has no writing block, and (since flush was skipped) has zero persisted forward blocks."
3. Optimize continues: `get_all_persist_segments()` returns the converted segment (`collection.cc:802-803`, `2084-2086`). With one persist segment and no rebuild trigger, `build_compact_task` emits a `CreateVectorIndexTask` (`collection.cc:993-1001`), or nothing if `all_vector_index_ready()` (skip at ~963-965; `segment.cc:1949-1956` — false for never-dumped segments). `ExecuteCreateVectorIndexTask` (`src/db/index/segment/segment_helper.cc:1113-1126`) → `create_vector_index` (`segment.cc:1670-1729`) merges `vector_indexers_[column]` (`merge_vector_indexer`, `segment.cc:1642-1668`) — it never scans or persists the forward store; it only adds a VECTOR_INDEX block meta whose min/max/count come from in-memory `doc_ids_` (`segment.cc:1724-1726`). Optimize updates the persisted meta, flushes the version again (`collection.cc:863-877`), and returns OK. No step ever fails.
4. Reopen: `recovery()` loads the new version; the old segment opens read-only, `load_persist_scalar_blocks()` (`segment.cc:3913-3953`) finds no SCALAR blocks → `doc_ids_` empty; `writing_forward_block()` has no value → **`recover()` is never invoked** (`segment.cc:484-501`) → the still-existing WAL file is orphaned and never replayed. Count is 0; the documents are gone.

Variant (multi-persist-segment collections): the `CompactTask` path would call `segment->scan(...)` (`segment_helper.cc:232-241`), whose memory branch does `segment_meta_->writing_forward_block().value()` (`segment.cc:2825-2841`) on the now-`nullopt` optional — a standard-guaranteed `std::bad_optional_access`; and compaction then destroys input segment directories *including the WAL* (`collection.cc:898-901` → `segment.cc:2334-2338`; WAL lives inside the segment dir). The described scenario (small collection, optimize succeeds) matches the single-segment `CreateVectorIndexTask`/skip path, which never scans.

**Why the control doesn't lose data:** without the crash, `wal_file_` is attached from the first insert, so in `switch_to_new_segment_for_writing` the flush gate passes and the full sequence runs — forward block written, `finish_memory_components()` converts memory state into persisted blocks referenced by the meta, version updated, and only *then* the WAL is removed (`segment.cc:2224-2323`). By the time the writing block is stripped, the data is already in persisted files the new version references.

**Same-class exposure:** every other caller of `switch_to_new_segment_for_writing` — `CreateIndex` (`collection.cc:502`), `DropIndex` (675), `AddColumn` (1155), `DropColumn` (1227), `AlterColumn` (1311), and the write-rollover in `write_impl` (1446) — plus a plain `Collection::Flush()` after recovery with no new writes (`collection.cc:380-394`, same gate) hit the identical no-op. The bare `Flush()` case is benign only because the version still points at the writing segment, so the WAL keeps being replayed on each reopen.

### 3. Why success and same-handle statistics prove nothing here

- **The OK is vacuous.** The gate at `segment.cc:2220-2222` returns `OK` for "nothing to flush," and it cannot distinguish "genuinely clean" from "dirty, but the log handle was never attached." `dump()`, the version rewrite, and the index task all then legitimately succeed. No API in the chain ever acknowledges that document bytes reached disk.
- **Statistics are pure RAM.** `Stats()` sums `doc_count()` = `doc_ids_.size()` over `get_all_segments()` (`collection.cc:403-442`; `segment.cc:589-599`), and the converted segment object — with its intact `memory_store_` — is still registered in `segment_manager_` (`collection.cc:1522`). The same handle never re-reads the manifest; the destructive change (the flushed version without a writing block) is visible only to a *fresh* open. Optimize intentionally preserves in-memory queryability, so health on the old handle and durability on disk have decoupled.

### 4. Smallest repair principle and a regression test (described only)

**Repair principle:** answer "is there unpersisted data?" from the authoritative dirty state, not from the presence of a lazily-attached log handle — and preserve the invariant that *a segment is demoted from writing to persisted only after its memory components have actually been persisted*. The minimal change:

1. At the end of `SegmentImpl::recover()`, when any record was replayed, attach the member WAL via the existing `open_wal_file()` (`segment.cc:4303-4322`; it opens the existing file for append, and `has_record()` is `file_.size() > sizeof(header_)`, `local_wal_file.h:75-77`, so the existing gate then evaluates true). The first subsequent `flush()`/`dump()` runs the full persist path — memory flush → `finish_memory_components` → version update → WAL removal — restoring the intended lifecycle with no change to `flush()` itself.
2. Defense in depth: make flush's early-return also consult real memory state (e.g. `memory_store_ && num_rows() > 0` or `mem_block.doc_count_ != 0`), and/or have `switch_to_new_segment_for_writing` verify after `dump()` that the meta actually gained persisted blocks (or holds zero docs) before stripping the writing block and flushing the version.

**Regression test** (fits the existing fixture: `tests/db/crash_recovery/utility.h` schema/doc factories; the fork+`SIGKILL` `RunGeneratorAndCrash` harness in `tests/db/crash_recovery/write_recovery_test.cc:95-150`):

1. Create collection; run the generator child inserting N docs (no flush) and `SIGKILL` it mid-run → WAL-only state.
2. Reopen (process B): assert `Open` OK, `Stats().doc_count == K > 0`, `Fetch` each pk equals `CreateTestDoc` (mirrors `CrashRecoveryDuringInsertion`, `write_recovery_test.cc:182-219`).
3. With **no new inserts**, call `Optimize()` on that handle; assert OK; optionally assert `Stats()` still shows K.
4. Reset the handle; reopen (fresh `Collection::Open`): **assert `Stats().doc_count == K` and every doc fetches unchanged** — this assertion fails on current code (yields 0) and passes after the repair. Optionally also run a vector search expecting K results.
5. Disk-invariant check: after step 3, assert no `*.wal` remains under the collection directory — a flushed writing segment must consume its WAL (`segment.cc:2304-2315`); today the orphaned WAL survives, so this pins the fix from the disk-state side as well.
6. Control arm (passes today): same sequence in one process without the crash — insert, optimize, reopen, count == N — proving the test discriminates the recovery path, not optimize in general.

**Established from source vs. requiring execution.** Everything above is a static trace with file:line citations. I did not build or run the project, so these would need runtime confirmation: the end-to-end loss (K → 0 after reopen); which task `build_compact_task` actually selects for a given schema (`CreateVectorIndexTask` vs. skip, and whether `VectorColumnIndexer::Merge` succeeds on an empty input list — note the loss is already durable at `collection.cc:1546-1549` *before* any task runs, so Optimize's success doesn't depend on that detail); and the multi-segment compact variant's `bad_optional_access` behavior at `segment.cc:2837` (the throw itself is standard-guaranteed; whether it surfaces as an error or crash depends on callers above `Optimize`).
