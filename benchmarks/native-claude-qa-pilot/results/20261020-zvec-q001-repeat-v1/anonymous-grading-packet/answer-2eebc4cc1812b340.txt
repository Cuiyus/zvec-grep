## Root cause (one line)

`SegmentImpl::recover()` replays the WAL into memory through a **local, read-only WAL handle** and never arms the member `wal_file_`; the persistence gate in `SegmentImpl::flush()` keys off that member, so a later `Optimize()` — which treats a non-empty writing segment as "flushable" — silently skips persisting the replayed data, then rewrites the manifest in a way that retires the writing block and orphans the WAL. Everything below is static source analysis of the frozen tree; I did not build or run anything.

---

## 1. Recovery path vs. ordinary insertion path

**Ordinary insert** (`src/db/collection.cc:1420-1470` → `SegmentImpl::Insert`, `src/db/index/segment/segment.cc:903-918`): `Insert` first calls `append_wal(doc)` (`segment.cc:4324-4340`), which lazily opens the **member** `wal_file_` (`segment.cc:4303-4322`; member declared null at `segment.cc:401`) and appends the record; only then does `internal_insert` (`segment.cc:837-881`) populate `memory_store_`, `memory_vector_indexers_`, `id_map_`, `doc_ids_`, and bump the in-memory writing-block meta. Post-state: dirty memory **and** a non-null `wal_file_` whose `has_record()` is true (`has_record()` = file size > header, `src/db/index/storage/wal/local_wal_file.h:73-75`).

**Recovery** (`CollectionImpl::recovery`, `collection.cc:1836-1892`): loads the highest-numbered manifest (`VersionManager::Recovery`, `src/db/index/common/version_manager.cc:190-241`), then opens the writing segment from `v.writing_segment_meta()`. `SegmentImpl::Open` calls `recover()` only when the meta has a `writing_forward_block` (`segment.cc:484-501`). `SegmentImpl::recover()` (`segment.cc:4193-4301`) opens the WAL `<collection>/<seg_id>/<block_id>.wal` (`FileHelper::MakeWalPath`, `src/db/common/file_helper.h:74-78`) into a **local** `recover_wal_file` (`segment.cc:4206-4215`, closed by `AILEGO_DEFER`), and replays each record by calling `internal_insert/internal_update/internal_upsert/internal_delete` **directly** (`segment.cc:4250-4272`) — bypassing `append_wal`. It then patches the in-memory block meta (`mem_block.max_doc_id_ += added_docs`, `segment.cc:4288`). The `SegmentImpl` constructor copies the manifest meta into a fresh `shared_ptr` (`segment.cc:99-105`), so these meta mutations are RAM-only.

**The differing state:** after recovery the segment holds the identical in-memory structures a live insert would have built, but `wal_file_ == nullptr`. The "dirty" state that `flush()` uses as its trigger is absent even though the data exists only in memory.

**Why it's initially readable:** `get_all_segments()` appends the writing segment whenever `doc_count() > 0` (`collection.cc:2076-2082`); `doc_count()` is `doc_ids_.size()` (`segment.cc:589-600`); `Fetch`/`Query` resolve via the replay-populated `id_map_` (RocksDB `Put`, `src/db/index/common/id_map.cc:97-104`) and the in-memory forward store. Durability at this moment still rests entirely on the *old* manifest (which still describes the writing block) plus the on-disk WAL — which is why a plain `Flush()`/`Close()` after recovery, though also a no-op (below), is *harmless*: the next open replays again.

## 2. The Optimize sequence and the exact loss condition

`CollectionImpl::Optimize` (`collection.cc:779-915`):

1. `writing_segment_->doc_count() != 0` is true (replay filled `doc_ids_`), so it calls `switch_to_new_segment_for_writing()` (`collection.cc:794-799`, body at `1517-1552`).
2. That calls `writing_segment_->dump()` (`collection.cc:1519`; `segment.cc:2197-2215`), which first calls `flush()`.
3. **Exact condition:** `flush()` begins with the gate `if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();` (`segment.cc:2220-2222`). Because recovery left `wal_file_ == nullptr` and no new append has occurred, `flush()` returns OK having done **nothing**: no `memory_store_->flush()`, no `finish_memory_components()` (`segment.cc:4342-4412` — the only code that converts the memory writing block into persisted SCALAR/VECTOR-index `BlockMeta`s), no `update_version()` (`segment.cc:4414-4426` — manifest persistence), and no WAL removal (`segment.cc:2304-2315`, itself gated on `wal_file_`).
4. `dump()` proceeds anyway: seals the inverted indexer, dumps FTS if present, sets `sealed_ = true`, returns OK (`segment.cc:2204-2214`). For a plain vector collection no document data reaches disk.
5. **The destructive commit** (`collection.cc:1522-1549`): the data-less segment is registered in the in-memory `segment_manager_` (just a map, `src/db/index/segment/segment_manager.cc:26-31`); a new empty writing segment is created (new segment id, `min_doc_id = old max_doc_id()+1`); then `writing_segment_meta->remove_writing_forward_block()` (`collection.cc:1538`; `src/db/index/common/meta.h:263-265`) erases the manifest's only pointer to the WAL; `version_manager_->apply()` + `flush()` (`collection.cc:1546-1549`) write `manifest.<n+1>` and **delete `manifest.<n>`** (`version_manager.cc:282-301`). The pre-crash manifest is gone.
6. Optimize continues: `get_all_persist_segments()` now includes the sealed segment (`collection.cc:802`). Small collection ⇒ one segment, no deletes ⇒ `rebuild == false` ⇒ `build_compact_task` emits only a `CreateVectorIndexTask` (`collection.cc:991-1002`). With the default FLAT params (`src/include/zvec/db/index_params.h:437`), the writing-segment meta was marked vector-indexed at creation (`segment.cc:534-539`), so `create_vector_index` early-returns success with a meta copy minus the writing block (`segment_helper.cc:1113-1125`; `segment.cc:1677-1690`). Final version apply/flush at `collection.cc:863-877` returns OK.

**End state on disk:** a manifest listing the old segment as "persisted" with **no SCALAR forward block**, a new empty writing segment, and an orphaned `<old_seg>/<block>.wal`. On the next open, `SegmentImpl::Open` skips `recover()` for any segment whose meta lacks a writing block (`segment.cc:484-510`), and the new writing segment's WAL path uses its new ids — the WAL is never read again. `load_persist_scalar_blocks` finds no SCALAR blocks ⇒ `doc_ids_` empty ⇒ `doc_count() == 0` (`segment.cc:3913-3960`). If process B exited cleanly, the id-map RocksDB (WAL-disabled writes, `src/db/common/rocksdb_context.cc:93,199`; memtable flushed on clean close) may still map pks to doc ids owned by no segment, so `Fetch` returns `{pk: nullptr}` with a "Segment not found" warning (`collection.cc:1780-1786`, `2054-2074`).

**Control case:** inserts in the same process left `wal_file_` non-null with records, so step 3's gate passes and `flush()` fully persists (memory store → `finish_memory_components()` → `update_version()` → WAL removed) *before* the manifest is rewritten. Data is on disk ahead of every meta change ⇒ survives reopen.

## 3. Why success and same-handle stats prove nothing here

- **Success is honest but vacuous:** every sub-step legitimately returned OK — including `flush()`, whose "nothing to do" early return (`segment.cc:2220-2222`) is indistinguishable from "persisted." Nothing in `Optimize` or `switch_to_new_segment_for_writing` asserts that a segment being converted to "persisted" actually has persisted blocks matching its `doc_count`.
- **Stats read RAM, not disk:** `Stats()` iterates `get_all_segments()` (`collection.cc:403-442`) — the very same `SegmentImpl` object populated by replay, merely reclassified into `segment_manager_`; Optimize never reloads it from disk. `index_completeness` reads `meta()->vector_indexed(...)` (FLAT is marked indexed from creation). `Fetch`/`Query` hit the same in-memory forward store and id map. The RAM view and the manifest+blocks view diverge silently, and the divergence is observable only through a fresh `Collection::Open` (or by inspecting the manifest/block/WAL files directly).

## 4. Smallest repair principle and regression test (described, not implemented)

**Repair principle:** *WAL replay must leave the segment in the same dirty lifecycle state as a live append; the flush gate must never report "nothing to persist" for memory state that exists only because of replay.* The minimal change is inside `SegmentImpl::recover()` (`segment.cc:4193-4301`): after replaying ≥1 record, arm the member handle via the existing `open_wal_file()` (`segment.cc:4303-4322`, which reopens the existing file with `create_new=false`). Then `flush()`'s gate (`wal_file_ != nullptr && has_record()` — `has_record()` is size-based, so it sees the pre-existing records) runs the full body: persist memory store, register persisted blocks, update the manifest, and **remove the WAL** — restoring the intended invariant "WAL exists ⇔ block not yet persisted; block persisted ⇒ WAL removed." An explicit `dirty_after_recovery_` flag consulted by the same gate is an equivalent variant. Fixing it at this one site also repairs the identical window in `Flush()`/`Close()` (currently silent no-ops after recovery) and in every DDL path that funnels through `switch_to_new_segment_for_writing` / `commit_schema_change_with_new_writing_segment` (`CreateIndex`/`DropIndex`/`AddColumn`/`DropColumn`/`AlterColumn`, `collection.cc:501-503, 674-676, 1154-1156, 1226-1228, 1310-1312`). A defense-in-depth addition (not the minimal fix): in `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`), refuse to `remove_writing_forward_block()` on a meta whose writing block still shows `doc_count > 0` without a corresponding persisted SCALAR block.

**Regression-test sequence** (fits the existing harness in `tests/db/crash_recovery/` — fork+SIGKILL of `data_generator` in `write_recovery_test.cc:138-162,182`, and the `collection_optimizer` child-process runner in `optimize_recovery_test.cc`; note the existing `CrashDuringOptimize` test always closes cleanly or inserts after recovery before optimizing, which is exactly why it misses this):

1. Create a collection; in a child process insert N docs (single writing segment; no rollover); SIGKILL/`_exit` the child **before** any Flush/Close — leaves a dirty WAL and pre-flush manifest.
2. New process: `Collection::Open` → assert `Stats().doc_count == N` and `Fetch` of every pk (recovery readable — existing tests stop here).
3. **New step:** on the same handle, with zero intervening writes, call `Optimize()`; assert OK.
4. Terminate the process **hard** again (so a close-time flush cannot mask the defect), then `Collection::Open` in a fresh process.
5. Assert `Stats().doc_count == N`, `Fetch` returns all N docs, and a vector `Query` finds them. Optionally white-box: assert a persisted forward-block file exists for the recovered range and that no orphaned `<seg_id>/<block_id>.wal` remains.

On the current tree step 5 fails (count 0 / null fetches); a control arm (insert + optimize in one process, clean close) passes. The same test should be repeated for at least one DDL path (e.g., `CreateIndex`) since they share the commit helper.

**Static vs. execution-required:** all causal steps above are established by reading the source. What would need an actual run to confirm: that `Optimize()` returns OK end-to-end in this exact scenario (the code paths all return OK on paper, e.g. `reload_vector_index` with an empty output map at `collection.cc:902-909` looks benign but is untested here), the precise reopen symptom mix (stale id-map entries depend on clean-exit vs. kill), and the exact manifest contents after the loss. I have not run a reproduction.
