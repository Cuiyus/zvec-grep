## Root cause (summary)

`SegmentImpl::flush()` uses "this process's WAL handle has no records" as its proxy for "nothing needs persisting" (`src/db/index/segment/segment.cc:2220-2222`). The crash-recovery path replays the WAL through a **separate, local** file handle and never sets the member `wal_file_`. So when `Optimize()` triggers `dump()` → `flush()` on the recovered segment, the flush silently no-ops — yet the caller, `switch_to_new_segment_for_writing()`, still commits a new version that reclassifies the segment as *persisted* and removes its writing-block marker, destroying the only path (`recover()`) by which a future open would replay the still-orphaned WAL.

---

## 1. Recovery state vs. ordinary insertion state

**Ordinary write path** — `SegmentImpl::Insert/Update/Upsert/Delete` (`segment.cc:903-989`) each call `append_wal(doc)` first, which lazily opens the member `wal_file_` (`segment.cc:4324-4340`, `open_wal_file` at `4303-4322`), then `internal_insert()` etc. (`segment.cc:837-901`) populate `id_map_`, `memory_store_`, scalar/FTS/vector indexers, `doc_ids_`, and the writing-block counters (`segment.cc:874-878`). So after normal writes: `wal_file_ != nullptr` and `has_record()` is true (`file_.size() > sizeof(header_)`, `src/db/index/storage/wal/local_wal_file.h:75-77`).

**Recovery path** — `SegmentImpl::Open` calls `recover()` only when the segment meta has a `writing_forward_block` (`segment.cc:484-501`). `recover()` (`segment.cc:4193-4301`) opens the on-disk WAL `<collection>/<seg_id>/<block_id>.wal` (`src/db/common/file_helper.h:74-78`) into a **local** `recover_wal_file` (`segment.cc:4206-4215`), replays each record by calling `internal_insert/update/upsert/delete` directly (`segment.cc:4250-4266`), and closes it. The member `wal_file_` is never assigned — only `append_wal` does that.

**Why reads work anyway**: replay populates exactly the same in-memory structures as real writes. `doc_count()` is `doc_ids_.size()` (`segment.cc:589-599`); queries/stats iterate `get_all_segments()` including the writing segment (`src/db/collection.cc:2076-2082`). But the *durable* copy of the data is still only the WAL; the segment's `persisted_blocks_` remain empty.

Two secondary divergences in `recover()` worth noting (not the loss cause): the `Status status;` at `segment.cc:4249` is never assigned from the `internal_*` calls, so replay failures are silently ignored (`segment.cc:4274-4280` can never fire); and `mem_block.max_doc_id_ += added_docs` (`segment.cc:4285-4288`) double-counts, because `internal_insert` already set `max_doc_id_ = g_doc_id` per doc (`segment.cc:874-875`; `writing_forward_block()` returns a live reference, `src/db/index/common/meta.h:328-334`).

## 2. The call sequence and exact condition

In the recovering process (no new writes), `CollectionImpl::Optimize` (`collection.cc:779`):

1. `collection.cc:794` — `writing_segment_->doc_count() != 0` is **true** (recovered ids are in `doc_ids_`) → `switch_to_new_segment_for_writing()` (`collection.cc:1517-1552`).
2. `collection.cc:1519` → `SegmentImpl::dump()` (`segment.cc:2197-2215`) → `flush()` (`segment.cc:2217`).
3. **The exact condition**: `segment.cc:2220-2222` — `if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();`. Here `wal_file_ == nullptr`, so flush returns OK **before** every persistence step: `memory_store_->flush()` (2233-2236), `finish_memory_components()` which converts the memory block into persisted block metas (2288-2298, `segment.cc:4342-4408`), `update_version()` (2300-2302, `segment.cc:4414-4427`), and even the WAL removal (2304-2315). `dump()` then sets `sealed_ = true` and returns OK (`segment.cc:2212-2214`).
4. `collection.cc:1536-1549` — the version commit proceeds regardless: `remove_writing_forward_block()` on the old segment's meta (1538; `meta.h:263-265`), `add_persisted_segment_meta(...)` (1539), a new empty writing segment (1527-1531, 1543), then `version_manager_->apply()` + `flush()` (1546-1549). **The durable version now says: old segment = persisted with zero persisted blocks; writing segment = new and empty.**
5. Reopen in process 3: `CollectionImpl::recovery()` (`collection.cc:1836-1892`) opens persisted metas read-only (1861-1874); `SegmentImpl::Open` finds no writing block, so `recover()` is **skipped** (`segment.cc:490-501`) and `load_persist_*` find no blocks (468-482). The WAL file may still sit on disk, but it is orphaned — no meta references its block id, and only a writing-block segment triggers replay. It is physically deleted whenever that segment is later destroyed (destructor → `cleanup()` → `RemoveDirectory(seg_path)`, `segment.cc:112-117`, `2334-2336`). Result: 0 documents.

**Control case**: with in-process inserts, `wal_file_` is open and has records, so the same `dump()` executes the full sequence — persist blocks → update version → *then* remove the WAL (`segment.cc:2304-2315`) — and the switch commits a version whose persisted blocks actually exist. Note also that a single new insert after recovery would re-open the existing WAL via `append_wal` (`segment.cc:4308-4312, 4327-4330`) and mask the bug — matching the scenario's "without inserting any additional documents."

## 3. Why success and same-handle statistics prove nothing

- Every step *legitimately* returns `Status::OK()`: the flush early-exit (2221), `dump()` (2214), the version apply/flush (1546-1549), and hence `Optimize`. No code path distinguishes "persisted the data" from "concluded there was nothing to persist."
- `CollectionImpl::Stats()` (`collection.cc:403-442`) sums `segment->doc_count(delete_filter)`, i.e., in-memory `doc_ids_` (`segment.cc:589-599`), over `get_all_segments()`. After the switch, the old segment object — still holding `memory_store_`, indexers, and `doc_ids_` — was added to `segment_manager_` (`collection.cc:1522`), so the same handle keeps counting and fetching the recovered docs.
- Durability in this design is defined solely by what a fresh `recovery()` can see: persisted block files referenced by the committed version, or a WAL reachable via a writing-block meta. The optimize sequence left the first empty and dereferenced the second, while the handle's memory (the only place the data still existed) is exactly what a new process does not inherit. Same-handle stats are therefore evidence about process memory, not about disk.

## 4. Smallest repair principle and regression test

**Principle / invariant**: a writing segment's WAL may be dereferenced or removed only after the data it protects has been persisted; and "this segment has unpersisted data" must be established by *replay*, not only by fresh writes through `append_wal`.

**Smallest repair** (describe-only): at the end of `SegmentImpl::recover()`, when at least one record was replayed, establish the live WAL handle — e.g., call the existing `open_wal_file()` (`segment.cc:4303-4322`), which opens the existing file (`create_new=false`) and assigns `wal_file_`. Then `flush()`'s guard at 2220 sees `wal_file_ != nullptr && has_record() == true` and executes the intended persist → version-update → WAL-removal order before `switch_to_new_segment_for_writing` reclassifies the segment. (A broader alternative with the same principle: make the flush guard consult actual dirty state, e.g. `memory_store_ != nullptr` or writing-block `doc_count_ > 0`, instead of only WAL-handle state. The one-line recovery-side fix is smaller and keeps flush ordering untouched.)

**Regression test sequence** (describe-only), reusing the existing fork/kill harness in `tests/db/crash_recovery/` (`utility.h`, `data_generator.cc`):
1. Process A: create collection, insert N docs (N small — no rollover), SIGKILL before any flush.
2. Process B: open the collection (triggers WAL replay); assert `Stats().doc_count == N` and fetch-by-pk succeeds.
3. Same Process B: call `Optimize()` **with no intervening writes**; assert it returns OK.
4. Process C: reopen; assert `doc_count == N` and every pk fetches with matching content. **Step 4 is the assertion that fails today** (it would see 0).
5. Controls: identical sequence without the crash between insert and optimize (must stay green), and a variant inserting one doc after recovery before optimizing (documents the masking behavior).

The current tests do not cover this: `optimize_recovery_test.cc` covers a crash *during* optimize (`RunOptimizerAndCrash`, line 167) and a separate-process optimize only *after a clean close* (`collection.reset()` at 220, then `RunOptimizer` at 223) — where the flush already persisted everything, so the no-op flush is harmless. `write_recovery_test.cc` covers crash-then-reopen without an optimize in the recovering process.

**Established from source vs. requiring execution.** Everything above is static analysis of the frozen tree — I did not build or run anything, so the end-to-end reproduction is predicted, not observed. Points that would need execution to pin down: (a) whether the orphaned WAL file is physically removed during the same `Optimize` (its later phases, `collection.cc:807-1001`, may compact or rebuild the switched segment and eventually destroy its directory) or merely left unreachable; (b) whether `CreateVectorIndexTask` on the block-less switched segment is skipped or succeeds (the scenario stipulates success); and (c) the on-disk state of the IDMap after replay, since `id_map_->flush()` (`segment.cc:2266-2269`) is also skipped — irrelevant to the loss (forward/vector data is gone regardless) but observable in a test.
