# Root cause

`SegmentImpl::flush()` decides "nothing to persist" by testing whether the **WAL file handle** is open, not whether the segment actually holds unflushed state (`src/db/index/segment/segment.cc:2217–2222`). After crash recovery, replayed documents live in memory and in the on-disk WAL, but the handle is null — so the `dump()` inside `Optimize()`'s segment switch persists nothing, while the switch still erases the writing-block meta that is the *only* pointer to the WAL and commits a new manifest. The loss is durable the moment that manifest is written; the reopened process never replays the orphaned WAL because replay is gated on the (now removed) writing-block meta.

Everything below is established by reading the frozen tree; I did not build or run anything.

---

## 1. State that differs between recovery and ordinary insertion

**Ordinary insertion path.** `SegmentImpl::Insert/Upsert/Update/Delete` call `append_wal()` *before* mutating memory (`segment.cc:903–918`, 920–948, 950–989). `append_wal()` lazily opens the **member** `wal_file_` (`segment.cc:4324–4340` → `open_wal_file()`, `segment.cc:4303–4322`), then `internal_insert()` lazily creates `memory_store_` (a `MemForwardStore`) and writes id map, forward store, scalar/FTS/vector indexers, `doc_ids_`, and the writing-block counters (`segment.cc:837–881`, `init_memory_components` at 4119–4191). So in a process that inserted, the writing segment has: an open `wal_file_` with records (`has_record()` = file size > header, `src/db/index/storage/wal/local_wal_file.h:75–77`), plus dirty memory state.

**Recovery path.** `CollectionImpl::recovery()` (`src/db/collection.cc:1836–1892`) loads the latest manifest (`VersionManager::Recovery`, `src/db/index/common/version_manager.cc:190–241`) and re-opens the writing segment via `Segment::Open`. In `SegmentImpl::Open` (`segment.cc:461–517`), the presence of `writing_forward_block` in the meta (line 484–501) triggers `recover()` (`segment.cc:4193–4301`). `recover()`:

- opens the WAL `<collection>/<seg_id>/<block_id>.wal` (`src/db/common/file_helper.h:74–78`) into a **local** handle `recover_wal_file` and closes it on scope exit via `AILEGO_DEFER` (`segment.cc:4206–4215`);
- replays each record through `internal_insert/internal_update/internal_upsert/internal_delete` (`segment.cc:4234–4283`), which populate `memory_store_`, `memory_vector_indexers_`, `doc_ids_`, id map and delete store — all in memory. (Side observations: the replay's return `status` is declared but never assigned at 4249–4280, so per-doc failures are silently swallowed; and `mem_block.max_doc_id_ += added_docs` at 4288 double-counts, since `internal_insert` already set `max_doc_id_` per doc at 874–876. Neither causes this loss, but both weaken recovery.)

**The differing state:** the member `wal_file_` stays `nullptr` after recovery; it is only (re)opened by the *next* `append_wal()`. The recovered data is dirty in memory *and* still durable in the untouched on-disk WAL, but nothing in the segment object records "I have unflushed data" in a way `flush()` consults.

**Why it can be read initially.** All read paths operate on the live in-memory structures: `Stats()` sums `segment->doc_count()` = `doc_ids_.size()` (`collection.cc:403–442`; `segment.cc:589–600`); `get_all_segments()` includes the writing segment whenever `doc_count() > 0` (`collection.cc:2076–2082`); `Fetch`/`Query` read `memory_store_` and the memory indexers. Moreover, durability at this point is still provided by the WAL + unchanged manifest: a plain reopen (no optimize) would hit `recover()` again. WAL records survive the crashed process because `LocalWalFile::append` writes through `ailego::File::write`, an unbuffered `write(2)` wrapper (`src/ailego/io/file.cc:209–227`; `flush()` = `fsync`, 281–284), so bytes are in the kernel by the time `Insert` returns.

## 2. Call sequence and exact condition letting `Optimize()` succeed without preserving the data

Precondition (exactly as stated in the scenario): the recovered process performed **no writes**, so `wal_file_ == nullptr`.

1. `CollectionImpl::Optimize` (`collection.cc:779–915`): `writing_segment_->doc_count() != 0` (line 794) → `switch_to_new_segment_for_writing()` (796 → 1517–1552).
2. `switch_to_new_segment_for_writing` calls `writing_segment_->dump()` (`collection.cc:1519` → `segment.cc:2197–2215`), which calls `flush()` (`segment.cc:2201`).
3. **The exact condition:** `flush()`'s guard at `segment.cc:2220–2222`:
   ```cpp
   if (wal_file_ == nullptr || !wal_file_->has_record()) { return Status::OK(); }
   ```
   With the handle null, `flush()` returns OK *vacuously*, skipping every persistence step: `memory_store_->flush()` (2233–2236, writes the `scalar.<block>.parquet/ipc` file, `src/db/index/storage/memory_forward_store.cc:212+`), `finish_memory_components()` (2288–2298 → `segment.cc:4342–4412`, which converts the memory block and memory vector indexers into **persisted block metas** in `segment_meta_`), `update_version()` (2301 → 4414–4426), and the WAL removal (2304–2315). `dump()` then seals the (absent) invert/FTS indexers and sets `sealed_ = true` (2204–2212) — the segment is now marked "dumped" though nothing was written.
4. Back in `switch_to_new_segment_for_writing`: the segment is registered as persisted (`collection.cc:1522`); a new empty writing segment is created (1527–1534); then the critical meta mutation `writing_segment_meta->remove_writing_forward_block()` (1538 → `src/db/index/common/meta.h:263–265`) deletes the only manifest-visible pointer to the WAL; `version.add_persisted_segment_meta(...)` (1539), `apply` (1546) and `version_manager_->flush()` (1548) write `manifest.<N+1>` and **delete** `manifest.<N>` (`version_manager.cc:282–301`). This is the durable point of no return: the committed manifest describes the old segment with no writing block and no SCALAR (forward) block containing the recovered docs.
5. Optimize proceeds: `persist_segments` = {old segment} (802–803); `build_compact_task` with one segment and no deletes (`rebuild=false`) produces a single `CreateVectorIndexTask` (`collection.cc:991–1002`), executed via `SegmentHelper::ExecuteCreateVectorIndexTask` → `create_all_vector_index` (`src/db/index/segment/segment_helper.cc:1113–1125`; `segment.cc:1617–1640`). With the default index (`DefaultVectorIndexParams` = `FlatIndexParams`, `src/include/zvec/db/index_params.h:437`), the field was already marked indexed at segment creation (`segment.cc:534–539`), so `create_vector_index` hits the skip branch (`segment.cc:1685–1690`) and returns OK having written nothing; its output meta again strips any writing block (1624–1625). (With HNSW params it would merge from `vector_indexers_[column]` — the *persisted* indexer list — which never received the memory indexers because `finish_memory_components()` never ran, `segment.cc:1652–1662`, 4371–4384.)
6. Optimize commits that meta (`collection.cc:863–868`), `apply` + `flush` again (871–877), and `reload_vector_index` (902–910 → `segment.cc:1882–1940`) swaps the live segment's `segment_meta_` while leaving `memory_store_`/`doc_ids_` intact. `Optimize` returns `Status::OK()` (914).

**Reopen (process C):** `recovery()` loads the new manifest; the old segment is opened as a *persisted* segment (`collection.cc:1861–1874`). In `SegmentImpl::Open`, `writing_forward_block()` is now `std::nullopt`, so the WAL-replay branch (484–501) is skipped — the WAL file, still sitting at `<coll>/<seg_id>/<block_id>.wal` with every record intact, is never read again (and never deleted; nothing calls `remove()` on a null handle, and the segment directory survives because `CreateVectorIndexTask` inputs are not destroyed, unlike `CompactTask` inputs at `collection.cc:898–901`). `load_persist_scalar_blocks` finds no SCALAR blocks, so `doc_ids_` stays empty (`segment.cc:3913–3957`) → `doc_count()==0`, `Fetch` misses via id-map/segment lookup, documents gone.

**Control (no crash):** in the inserting process `wal_file_` is open with records, so step 3's guard passes and `flush()` performs the full sequence — memory block written to a file, `finish_memory_components()` adds SCALAR/VECTOR_INDEX blocks to the meta, manifest updated, WAL removed — *before* step 4 removes the writing block. The committed manifest references real data files, which reopen loads. No loss.

Note the trigger sharpness: had process B inserted even one document, `append_wal` → `open_wal_file()` would have reopened the existing WAL (`segment.cc:4308–4312`), making `has_record()` true and the subsequent `dump()/flush()` real — masking the bug. That matches the scenario's "without inserting any additional documents."

## 3. Why success + same-handle statistics don't establish durability

- **`Status::OK()` is compositional, not semantic.** Optimize returns OK because each step returned OK; the pivotal step (`dump()`→`flush()`) returned OK through an early-exit that means "I saw no open WAL handle," which the code conflates with "everything is persisted." No step verifies that the segment's documents exist in files referenced by the committed manifest.
- **Same-handle reads never touch the persisted image.** `Stats()`, `Fetch()`, and `Query()` read `doc_ids_`, `memory_store_`, and memory indexers (`collection.cc:403–442`, 1757–1790; `segment.cc:589–600`), all of which are unchanged in-process — `reload_vector_index` even swaps `segment_meta_` while preserving them (`segment.cc:1882–1940`). The handle cannot observe that the manifest it just committed (`version_manager.cc:282–301`) describes zero forward blocks for those docs. Durability is defined solely by what a *fresh* open loads (`version_manager.cc:190–241`; `segment.cc:461–517`, 3913–3957) — only a reopen (or inspecting manifest/segment files) tests it.
- An explicit `Collection::Flush()` in process B is equally uninformative: it routes to the same guarded `flush()` (`collection.cc:389–395`) and no-ops.

## 4. Smallest repair principle and regression test (described, not implemented)

**Repair principle:** *a writing segment that replayed WAL records is dirty, and the guard in `flush()` must reflect dirty state rather than handle state.* Minimally, at the end of a successful `recover()` (`segment.cc:4193–4301`), adopt the WAL — e.g., call `open_wal_file()` (4303–4322), which reopens the existing file in append mode — so `wal_file_ != nullptr && has_record()` and the existing `flush()` machinery does what it already does correctly on the ordinary path: write the memory block, run `finish_memory_components()`, commit the meta via `update_version()`, then remove the WAL. This restores the invariant that `switch_to_new_segment_for_writing`'s `remove_writing_forward_block()` (`collection.cc:1538`) and `create_all_vector_index`'s equivalent (`segment.cc:1625`) rely on: the writing-block pointer is dropped only *after* the block's contents are described by persisted blocks in the committed manifest. An equivalent alternative is to rebase the guard itself (`segment.cc:2220`) on `memory_store_ != nullptr` / writing-block `doc_count_ > 0`, but that variant must then also handle removing the orphaned on-disk WAL, so adopting the handle in `recover()` is the smaller, more faithful change. (Independently worth hardening: assign and check the replay statuses at `segment.cc:4249–4280`, and remove the `max_doc_id_` double-count at 4288.)

**Regression test sequence** — fits the existing harness in `tests/db/crash_recovery/` (fork/exec + SIGKILL pattern in `write_recovery_test.cc:53–144`; helper binary `collection_optimizer.cc:59–139` already does exactly "Open → Stats → Optimize → exit"):

1. **Process 1 (writer, killed):** create the collection with `max_doc_count_per_segment` and buffer sizes large enough that no rollover occurs (per the scenario's assumption; rollover triggers are `need_switch_to_new_segment`, `collection.cc:1472–1474`, and `ready_for_dump_block`/`is_full`, `segment.cc:841–844`, 2959–2962, `memory_forward_store.h:55–57`); insert N deterministic docs (`CreateTestDoc`, `tests/db/crash_recovery/utility.h:87–156`); terminate abruptly **without** `Flush()`/graceful close (`_exit` or SIGKILL — note the existing `data_generator` flushes before exiting, `data_generator.cc:244–253`, so a no-flush kill mode is required).
2. **Process 2 (recover + optimize, no writes):** open the collection (WAL replay); assert `Stats().doc_count == N` and `Fetch` returns sample docs — proves recovery itself works; then call `Optimize()` and assert OK. Insert nothing in between. The existing `collection_optimizer` binary is this process verbatim.
3. **Process 3 (verify durability):** reopen; assert `Stats().doc_count == N`, `Fetch` all N pks with content equality, and a vector `Query` returns expected hits (assertion style as in `optimize_recovery_test.cc:169–205`). **This is the assertion that fails today** (predicted `doc_count == 0` from the source trace above) and passes after the repair.
4. **Controls:** (a) same sequence with process 1 closing gracefully — must pass before and after the fix (this is the user's control collection); (b) a variant where process 2 inserts one doc before `Optimize` — must show N+1 after reopen, pinning the null-`wal_file_` trigger; (c) optionally assert the WAL file is gone after process 2's optimize (post-fix it should be consumed and removed by `flush()`, `segment.cc:2304–2315`).

The existing `CrashDuringOptimize` test (`optimize_recovery_test.cc:144–261`) cannot catch this: it crashes the *optimizer*, not the writer, and its post-crash reopen inserts 25,000 more docs (lines 207–218) before the final optimize — which opens the WAL handle and makes `flush()` real, masking the defect.

**Established from source vs. requiring execution.** The entire causal chain — the null-handle guard, the vacuous `dump()`, the writing-block removal, the manifest commit/delete, the reopen gating of WAL replay on `writing_forward_block`, and `doc_ids_` being rebuilt only from persisted SCALAR blocks — is directly traceable in the code cited above, as is Optimize's success for the single-segment/FLAT-default case (the skip branch at `segment.cc:1685–1690`). What I have *not* done is run it: the concrete observation "process C reports 0 docs" and the WAL bytes surviving the specific kill method are predictions consistent with the source (unbuffered `write(2)` WAL appends, `file.cc:209–227`), and would need the described test to confirm empirically.
