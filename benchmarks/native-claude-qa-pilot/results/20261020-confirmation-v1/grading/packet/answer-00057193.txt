All causal steps are now verified in the frozen tree. Here is the analysis.

# Root cause: after WAL replay, the segment's member WAL handle is `nullptr`, which makes `flush()`/`dump()` a silent no-op — yet `Optimize()` still commits a manifest that reclassifies the segment as "persisted"

## 1. State that differs between the recovery path and the insertion path

**Ordinary insertion path.** `SegmentImpl::Insert` (`src/db/index/segment/segment.cc:903-918`) calls `append_wal` first. `append_wal` (`segment.cc:4324-4340`) lazily opens the **member** `wal_file_` via `open_wal_file()` (`segment.cc:4303-4322`), then `internal_insert` (`segment.cc:837-881`) writes the doc into the IDMap (RocksDB `Put`, `segment.cc:853`), the in-memory forward store (`memory_store_->insert`, `segment.cc:857`, buffered in Arrow builders — `src/db/index/storage/memory_forward_store.cc:117-134`), the scalar/FTS/vector indexers, updates the writing-block meta (`segment.cc:874-876`), and appends to `doc_ids_` (`segment.cc:878`). After any insert, the invariant holds: *member `wal_file_` is open and `has_record()` is true exactly when the writing block holds unpersisted docs* (`local_wal_file.h:75-77`: `has_record() = file_.size() > sizeof(header_)`).

**Recovery path.** `CollectionImpl::recovery()` (`src/db/collection.cc:1836-1892`) loads the latest manifest (`version_manager.cc:190-241`), then opens the writing segment from `v.writing_segment_meta()` (`collection.cc:1880-1887`). `SegmentImpl::Open` sees a `writing_forward_block` in the meta and calls `recover()` (`segment.cc:484-501`). `recover()` (`segment.cc:4193-4301`) opens the WAL at `<path>/<seg_id>/<block_id>.wal` (`segment.cc:4198-4199`, path per `src/db/common/file_helper.h:74-78`) into a **separate local handle** `recover_wal_file` (`segment.cc:4206-4215`), replays every record through the same `internal_insert/update/upsert/delete` (`segment.cc:4250-4266`), and closes the local handle on scope exit. **The member `wal_file_` is never assigned** — nothing on the recovery path calls `open_wal_file()`.

So after recovery the segment holds all the volatile state of an inserted-into segment (`doc_ids_`, `memory_store_` builders, in-memory indexers, IDMap memtable entries, updated writing-block meta) but violates the invariant above: `wal_file_ == nullptr` despite the writing block being dirty.

**Why the data is initially readable.** All reads in the recovering process are served from that volatile state: `doc_count()` is `doc_ids_.size()` (`segment.cc:589-600`); `Stats()` sums per-segment `doc_count` over `get_all_segments()`, which includes the writing segment whenever its `doc_count() > 0` (`collection.cc:403-442`, `2076-2082`); `Fetch` resolves pk → doc_id via `id_map_->has` (a RocksDB `Get` that sees the memtable, `src/db/index/common/id_map.cc:120-134`) and then reads columns from `memory_store_` (`segment.cc:1096-1117`, `2531-2532`). None of this touches the manifest or requires persisted blocks.

## 2. Call sequence and exact condition letting `Optimize()` "succeed" without preserving the data

1. `CollectionImpl::Optimize` (`collection.cc:779-915`) takes the write lock; `writing_segment_->doc_count() != 0` is true (replayed docs are in `doc_ids_`), so it calls `switch_to_new_segment_for_writing()` (`collection.cc:794-800`).
2. That calls `writing_segment_->dump()` (`collection.cc:1519`), which calls `flush()` (`segment.cc:2197-2202`).
3. **The exact condition:** `flush()` begins with `if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();` (`segment.cc:2220-2222`). On the recovery-only handle `wal_file_` is `nullptr`, so `flush()` returns OK having done nothing. Skipped steps: `memory_store_->flush()` (`2233-2236`), indexer flushes (`2239-2264`), **`id_map_->flush()`** (`2266-2269`), **`finish_memory_components()`** (`2288-2291`) — the only place the writing block's data is registered as a persisted SCALAR block in the segment meta (`segment.cc:4342-4368`) —, `update_version` (`2300-2302`), and the WAL removal (`2304-2315`). `dump()` then seals (no-op) indexers and returns OK (`segment.cc:2204-2214`).
4. `switch_to_new_segment_for_writing` proceeds as if the dump had worked: the old segment is added to `segment_manager_` (`collection.cc:1522`), its meta's writing block is removed (`remove_writing_forward_block()`, `collection.cc:1537-1538`), the meta — now containing **zero persisted SCALAR blocks** — is added to the version (`collection.cc:1539`), a new empty writing segment is created (`collection.cc:1527-1531`), and `version_manager_->apply(...)` + `flush()` write a **new manifest to disk** (`collection.cc:1546-1549`; `version_manager.cc:282-301`). This manifest commit is the destructive step: from now on, recovery reads this manifest, and nothing in it points at the still-existing WAL file `<path>/0/<block>.wal` (orphaned, never removed).
5. Optimize continues: `persist_segments` = [the dumped segment] (`collection.cc:802-803`). With exactly one segment and no deletes, `build_compact_task` emits a `CreateVectorIndexTask`, **not** a `CompactTask` (`collection.cc:991-1002`). Executing it (`segment_helper.cc:1113-1125` → `segment.cc:1670-1829`) builds a merged vector-index file from the live in-memory indexers and records a VECTOR_INDEX block whose range comes from the in-memory `doc_ids_` (`segment.cc:1720-1727`). Optimize commits this meta too (`collection.cc:863-877`) and returns `Status::OK()` (`collection.cc:914`). Forward data is never rewritten to disk on this path. (With ≥2 persisted segments, `ExecuteCompactTask` would `scan()` inputs — `segment_helper.cc:233` — and rewrite forward data into a new segment, which would incidentally have rescued the docs; the "small collection" premise guarantees the single-segment, index-only path.)
6. **Next reopen:** `recovery()` loads the new manifest; segment 0 is opened read-only (`collection.cc:1863-1874`). In `SegmentImpl::Open`, `writing_forward_block()` is absent, so `recover()` is never called and the orphaned WAL is never replayed (`segment.cc:484-510`); `load_persist_scalar_blocks` finds no SCALAR blocks, so `doc_ids_` stays empty (`segment.cc:3913-3960`). The IDMap is reopened from disk, but the replayed pk→doc_id `Put`s were memtable-only writes with `write_opts_.disableWAL = true` (`rocksdb_context.cc:93`) in a process that never reached `id_map_->flush()`; RocksDB does not persist memtable data across close without a WAL (this last disk-level effect is the one step whose manifestation I'd confirm by test, not by reading). Result: `Stats().doc_count == 0`, `Fetch` → not found. The documents are gone even though the manifest even claims an N-doc vector index.

The control (no crash) never hits this: inserts in the same process opened the member `wal_file_`, so `dump()`→`flush()` runs the full pipeline — persisting forward blocks, flushing the IDMap, committing a version, and removing the WAL — *before* the meta transition at `collection.cc:1537-1549`.

## 3. Why success + same-handle statistics prove nothing here

- The `Status::OK()` from `flush()` on the no-op branch (`segment.cc:2221`) is indistinguishable from the OK of a real persist; every caller (`dump()`, `switch_to_new_segment_for_writing`, `Optimize`, even an explicit `Collection::Flush()` — `collection.cc:380-395` — which is *also* a no-op on a recovery-only handle) trusts it and commits the manifest anyway. The system's durability contract — "a committed manifest only references data that is on disk" — is enforced nowhere else.
- `Stats()`/`Fetch()`/`Query()` on the same handle read the live `Segment` object: `doc_count()` is the in-memory `doc_ids_` vector (`segment.cc:589-600`), forward reads fall back to `memory_store_` (`segment.cc:2531-2532`), pk lookups hit the RocksDB memtable (`id_map.cc:120-134`), and `index_completeness` is computed from meta flags (`collection.cc:425-439`) — which optimize just set to "indexed". Every one of these is a process-local view; none re-reads the manifest or the segment files that the *next* open will use. Durability here is defined solely by what the committed manifest + referenced files contain, and only a reopen observes that.

## 4. Smallest repair principle and regression test (described, not implemented)

**Repair principle:** *A segment that recovered documents from its WAL must end recovery in the same state a segment would be in had those documents arrived through `Insert` — specifically, with the member WAL handle adopted — so that the existing `flush()` guard means what it says.* Concretely: at the end of `SegmentImpl::recover()` (`segment.cc:4193-4301`), when records were replayed, call `open_wal_file()` (`segment.cc:4303-4322`; it already reopens an existing WAL with `create_new = false`). Then `flush()`'s `has_record()` check passes, the full persist pipeline runs (including `finish_memory_components()` registering the SCALAR block and `id_map_->flush()`), and the WAL is removed only after the data is durable — restoring the invariant that a manifest commit implies on-disk data. The alternative (changing the guard at `segment.cc:2220` to test real dirtiness, e.g. `memory_store_ != nullptr` or writing-block `doc_count_ > 0`) is also viable but must then carefully preserve the WAL-removal-after-persist ordering; the adopt-the-WAL fix is smaller and keeps one source of truth. Two secondary defects on the same path deserve attention while there: `recover()` discards every replay status (the `Status status;` at `segment.cc:4249` is never assigned by the switch, so the check at `4274` is dead and failures are counted as successes), and `mem_block.max_doc_id_ += added_docs` at `segment.cc:4285-4288` double-counts, because `internal_insert` already assigns `max_doc_id_` (`segment.cc:874-875`) — this inflates the segment's doc-id range and creates gaps for the next segment (`collection.cc:1529`).

**Regression test sequence** (fits the existing harness in `tests/db/crash_recovery/`, which already has the pieces — `data_generator` that can be SIGKILLed mid-insert and `collection_optimizer` that opens a collection and calls `Optimize` with no inserts, `collection_optimizer.cc:85-125`):

1. Process A: create collection, insert N docs (N small enough to avoid rollover), **SIGKILL before flush** (`RunGeneratorAndCrash`-style, `write_recovery_test.cc:182-198`) — leaves an unflushed WAL.
2. Process B: run `collection_optimizer --path ...` (open → `Optimize` → exit 0), **inserting nothing**; assert it exits successfully.
3. Process C: `Collection::Open`; assert `Stats().doc_count == N` and `Fetch` returns every original doc byte-identical (the verification pattern at `optimize_recovery_test.cc:169-193`), plus a top-k `Query` sanity check.

The current suite misses this because its post-crash optimizer run is always preceded by fresh inserts in the recovered handle (`optimize_recovery_test.cc:207-218` insert 500 batches before `RunOptimizer` at line 223), which reopens the member `wal_file_` via `append_wal` and masks the no-op flush. Step 3 fails on the unfixed tree and passes after the repair; the control variant (A closes cleanly instead of being killed) passes both before and after.

## What is established statically vs. what would need execution

Everything above is derived by reading the frozen source: the `wal_file_ == nullptr` guard (`segment.cc:2220-2222`), the fact that only `append_wal` opens the member handle (`segment.cc:4324-4330`) while `recover()` uses a local one (`4206-4215`), the meta transition and manifest commits (`collection.cc:1517-1552`, `779-915`; `version_manager.cc:282-301`), the reopen behavior (`collection.cc:1836-1892`; `segment.cc:461-517`, `3913-3960`), and the disableWAL IDMap writes (`id_map.cc:97-112`; `rocksdb_context.cc:93`). I did **not** build or run anything. Two claims rest on well-known RocksDB semantics rather than this repo's code and would need the regression test to confirm empirically: that memtable `Put`s with `disableWAL=true` are lost across DB close without an explicit flush, and the exact on-disk residue (orphaned `.wal` and vector-index files) after the failing sequence. The loss mechanism itself, however, is fully determined by the manifest commit at `collection.cc:1546-1549` of a meta with no persisted forward blocks — no RocksDB behavior is needed to explain why the documents cannot be found after reopen.
