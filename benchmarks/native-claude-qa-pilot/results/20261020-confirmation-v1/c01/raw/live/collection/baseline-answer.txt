# Root cause: WAL replay re-populates memory but never re-attaches the WAL handle that `flush()` uses as its dirty flag

## 1. Recovery path vs. ordinary insertion path

**Ordinary insertion.** `CollectionImpl::write_impl` → `SegmentImpl::Insert` (`src/db/index/segment/segment.cc:903-918`) calls `append_wal(doc)` *before* `internal_insert(doc)`. `append_wal` lazily opens the member `wal_file_` on first write (`segment.cc:4324-4332`), so after any insert the writing segment has **both** (a) data in `memory_store_`, `memory_vector_indexers_`, `doc_ids_`, and the meta's `writing_forward_block` (`internal_insert`, `segment.cc:837-881`) **and** (b) a live `wal_file_` member whose `has_record()` is true (`local_wal_file.h:75-77` — file size > header).

**Recovery path.** On reopen, `CollectionImpl::recovery()` (`src/db/collection.cc:1836-1892`) opens the writing-segment meta from the manifest. `SegmentImpl::Open` sees a `writing_forward_block` and calls `recover()` (`segment.cc:484-501`). `recover()` (`segment.cc:4193-4301`) opens the on-disk WAL (`<path>/<seg_id>/<block_id>.wal`, `src/db/common/file_helper.h:74-78`) into a **local** handle `recover_wal_file` that is closed by an `AILEGO_DEFER` at line 4215, replays each record through `internal_insert/internal_update/...` (4234-4283), and returns. It **never assigns the member `wal_file_`**, and nothing else records "this segment holds unpersisted replayed data." So after recovery the in-memory state (a) is fully populated — identical to the insertion path — but state (b) is missing: `wal_file_ == nullptr`.

**Why the data is initially readable.** All read paths are memory-resident: `Stats()` counts `doc_ids_.size()` via `Segment::doc_count` (`segment.cc:589-599`) over `get_all_segments()`, which includes the writing segment whenever `doc_count() > 0` (`collection.cc:2076-2082`); `Fetch()` resolves pk→doc_id through the RocksDB-backed `IDMap` (its `Put`s during replay are durable in RocksDB's own log, `src/db/index/common/id_map.cc:97-112`) and reads the doc from `memory_store_` (`collection.cc:1757-1790`). `MemForwardStore` explicitly "keeps data in memory and can flush to disk when needed" (`src/db/index/storage/memory_forward_store.h:32-34`). Readability here says nothing about persistence.

## 2. The exact sequence in `Optimize()` that loses the data

`CollectionImpl::Optimize` (`collection.cc:779-915`), with the recovered writing segment holding *n* docs:

1. **`collection.cc:794-800`** — `writing_segment_->doc_count() != 0` (it is *n*, from `doc_ids_`), so it calls `switch_to_new_segment_for_writing()` (`collection.cc:1517-1552`):
   - **Line 1519: `writing_segment_->dump()`** → `SegmentImpl::dump()` (`segment.cc:2197-2215`) → `flush()`. **The critical condition, `segment.cc:2220-2222`:**
     ```cpp
     if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();
     ```
     Because recovery never re-attached `wal_file_`, `flush()` is a **silent no-op returning OK**. It skips everything that would make the replayed data durable: `memory_store_->flush()`, `id_map_->flush()`, `finish_memory_components()` (which moves the mem block into the meta's persisted SCALAR blocks and promotes memory vector indexers, `segment.cc:4342-4412`), `update_version()` (`segment.cc:4414-4426`), and WAL removal (`segment.cc:2304-2315`). `dump()` then seals indexers and sets `sealed_ = true` — success.
   - **Line 1522:** the old segment (data still *only* in RAM) is added to `segment_manager_` as a "persisted" segment.
   - **Lines 1527-1531:** a new empty writing segment is created with `min_doc_id = old_meta->max_doc_id() + 1` — computed from the still-present mem block (`meta.h:293-305`), so the doc-ID space advances *as if* the recovered docs were persisted.
   - **Lines 1536-1540:** `writing_segment_meta->remove_writing_forward_block()` erases the **only** block meta describing the recovered data, then `version.add_persisted_segment_meta(...)`. The old segment's meta now has no SCALAR forward block at all.
   - **Lines 1546-1549:** `version_manager_->apply()` + `flush()` — `VersionManager::flush` writes a new MANIFEST and **deletes the previous one** (`src/db/index/common/version_manager.cc:282-301`). The manifest now durably claims the recovered docs live nowhere.
2. **`collection.cc:802-816`** — with a single persisted segment and no deletes, `build_compact_task` produces a `CreateVectorIndexTask`, not a compaction (`collection.cc:962-966`, `991-1002`). `ExecuteCreateVectorIndexTask` → `create_all_vector_index` (`segment.cc:1617-1640`) copies the (already writing-block-less) meta and calls `create_vector_index`, which merges only `vector_indexers_[column]` — the **persisted** index blocks (`merge_vector_indexer`, `segment.cc:1652-1653`); the recovered vectors sit in `memory_vector_indexers_` and are never consulted. It then stamps a VECTOR_INDEX `BlockMeta` with `doc_ids_.front()/back()/size()` (`segment.cc:1720-1727`) — metadata claiming *n* docs over an index merged from zero inputs.
3. **`collection.cc:822-877`** — the new version (old segment: no forward block; writing segment: empty) is applied and the manifest flushed again.
4. **`collection.cc:902-910`** — `reload_vector_index` swaps the live segment's `segment_meta_` to the output meta (`segment.cc:1882-1890`); `memory_store_`/`doc_ids_` are untouched.

**Why the next reopen finds nothing:** `recovery()` opens persisted segments read-only; WAL replay is gated on the meta *having* a `writing_forward_block` (`segment.cc:484-501`). The committed meta has none, so the still-present orphaned `.wal` file is never read; `doc_ids_` is rebuilt solely from persisted SCALAR blocks (`load_persist_scalar_blocks`, `segment.cc:3913-3960`) — there are none — so `doc_count()` is 0. The new writing segment's WAL path is keyed to its own segment/block IDs and doesn't exist. The documents are gone (while stale pk→doc_id entries remain in the ID map's RocksDB, so `Fetch` would hit the "segment not found" branch, `collection.cc:1780-1785`).

**Why the control (no crash) survives:** in the original process `wal_file_` is attached by the first insert, so the same `dump()`→`flush()` runs the full path: `finish_memory_components()` adds the SCALAR/VECTOR blocks to the meta *before* `remove_writing_forward_block()` and the manifest commit, and the WAL is removed only after `update_version()` persists. The manifest always references the data.

## 3. Why success + same-handle statistics prove nothing

- `flush()`'s no-op path returns `Status::OK()` (`segment.cc:2221`), so `dump()`, `switch_to_new_segment_for_writing()`, and `Optimize()` all return success. "OK" here means "nothing to do," not "data persisted" — the dirty check consults a handle (`wal_file_`) that recovery invalidated as a state indicator.
- `Stats()` (`collection.cc:403-442`) counts `doc_ids_` (pure RAM) and computes `index_completeness` from `meta()->vector_indexed(field)` — which step 2 above *set* on the output meta (`segment.cc:1636`) even though the merged index is empty. After Optimize the same handle therefore reports doc_count = n and completeness = 1.0 while the on-disk manifest references zero documents. Nothing in `Stats` reads the manifest or disk; durability in this design is exactly "referenced by the flushed MANIFEST," and only a fresh `Collection::Open` observes that.

## 4. Smallest repair principle and regression test

**Repair principle (describe-only):** restore the invariant *flush() is dirty-aware for replayed data*. The minimal change is in `SegmentImpl::recover()`: after a successful replay of ≥1 record, re-attach the WAL exactly as `append_wal` does — `open_wal_file()` with `create_new=false` (`segment.cc:4303-4322`) so `wal_file_ != nullptr && has_record()` — leaving the existing lifecycle untouched: the next `flush()` then runs the full persist path and removes the WAL itself. (Equivalently, base the `segment.cc:2220` guard on real pending state, e.g. `memory_store_ && memory_store_->num_rows() > 0` / `mem_block.doc_count_ > 0`, or make `dump()` refuse to seal while unpersisted rows exist.) One re-attachment, no protocol change. A secondary hardening worth noting: `create_vector_index` stamping block metas from `doc_ids_` while merging only persisted indexers (`segment.cc:1652-1653` vs `1720-1727`) lets metadata claim docs the files don't contain; and `scan()` would throw `std::bad_optional_access` at `segment.cc:2837` in the multi-segment variant of this state (memory rows + removed writing block), i.e., the compaction path fails loudly where the index path fails silently.

**Regression test (fits the existing harness in `tests/db/crash_recovery/`):** the gap is that `write_recovery_test.cc` never optimizes after recovery, and `optimize_recovery_test.cc:CrashDuringOptimize` (a) cleanly closes the inserter (`collection.reset()`, line ~160) so no WAL replay precedes the first optimize, and (b) inserts 500 more batches after recovery before the second optimize (lines ~205-218) — those inserts re-attach the WAL via `append_wal` and mask the bug. The detecting sequence:

1. Process A: `data_generator`-style create + insert N docs; **SIGKILL before flush/close** (as `RunGeneratorAndCrash`).
2. Process B: `collection_optimizer` as-is — open (triggers WAL replay), print `Stats()`, `Optimize()`, **no inserts** — exit 0. Assert exit success and (in-test) that B's pre/post `Stats().doc_count == N`.
3. Process C (the test body): `Collection::Open`; assert `Stats().doc_count == N`; `Fetch` every pk and compare contents; run a top-k vector query and assert hits — reusing the verification block of `optimize_recovery_test.cc:170-190`.

On current source, step 2 passes and step 3 fails with doc_count 0 — precisely the reported symptom. Variants worth adding: ≥2 persisted segments before the crash (exercises the compact/`scan()` path), and an explicit `Flush()`-vs-crash control matrix.

## What is established from source vs. what needs execution

**Established by reading the frozen tree:** every causal link above — the `wal_file_ == nullptr` no-op guard (`segment.cc:2220-2222`), `recover()`'s local-handle replay (`segment.cc:4206-4215`), Optimize's call sequence and meta surgery (`collection.cc:794-800`, `1517-1552`, `822-911`), manifest replacement/old-manifest deletion (`version_manager.cc:282-301`), WAL-replay gating on reopen (`segment.cc:484-501`), `doc_ids_` rebuild from SCALAR blocks only (`segment.cc:3913-3960`), and the memory-only nature of the recovered data (`memory_forward_store.h:32-34`).

**Would require executing a test (I did not build or run anything):** end-to-end confirmation that `Optimize()` returns OK in this state — in particular that `VectorColumnIndexer::Merge` over zero input indexers succeeds (I did not read its implementation; the scenario stipulates success, and either outcome still loses the data — silently on success, loudly on failure); the exact post-reopen counts; the incidental double-count of `mem_block.max_doc_id_ += added_docs` after `internal_insert` already advanced it (`segment.cc:4285-4288`), which appears to leave a doc-ID gap but is orthogonal to the loss; and whether the multi-segment variant aborts via the `scan()` optional dereference (`segment.cc:2837`) rather than silently succeeding.
