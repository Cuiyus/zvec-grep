## Root cause: `optimize()` rebuilds the vector index in place while densely renumbering vector keys, but leaves the scalar rows (and their row IDs) untouched

### The path this sequence actually takes

**Delete.** `SegmentImpl::Delete(pk)` (`src/db/index/segment/segment.cc:986`) resolves pk → g_doc_id via `id_map_`, then `internal_delete` (`segment.cc:933-937`) does only two things: `delete_store_->mark_deleted(g_doc_id)` (a Roaring bitmap of **global** doc IDs, `src/db/index/common/delete_store.h:96-100`) and `id_map_->remove(pk)`. The physical row stays in the forward store, `doc_ids_` (local row → g_doc_id, `segment.cc:398`) keeps 28 entries, and the mutable vector indexer keeps 28 vectors. This is why scalar state stays coherent: deletion is pure bookkeeping.

**Optimize.** `CollectionImpl::optimize` (`src/db/collection.cc:910`) seals the writing segment (929-934), snapshots persist segments (936-937), clones the delete store into a filter (945-948), and calls `build_compact_task` (`collection.cc:1086`). With 3/28 ≈ 0.107 deleted, `rebuild` stays false because the ratio is below `COMPACT_DELETE_RATIO_THRESHOLD = 0.3f` (`collection.cc:1100-1104`, `src/db/common/constants.h:41`). A single-segment group under the limit then produces a **`CreateVectorIndexTask`**, not a compaction (`collection.cc:1160-1164`).

**Index build.** `ExecuteCreateVectorIndexTask` (`src/db/index/segment/segment_helper.cc:1121-1133`) → `SegmentImpl::create_vector_index` (`segment.cc:1519`) → `merge_vector_indexer` (`segment.cc:1491-1517`), which calls `VectorColumnIndexer::Merge(vector_indexers_[column], filter_, …)` (`segment.cc:1511`; `src/db/index/column/vector_column/vector_column_indexer.cc:103-134`). `filter_` is the `SegmentIndexFilter` (`segment.cc:464-476`) that translates a **segment-local row ID** through `doc_ids_` (`get_global_doc_id`, `segment.cc:4444-4451`) and checks the delete bitmap — filtering is correct.

**The defect** is in the engine merge. `Index::merge` (`src/core/interface/index.cc:1016-1077`) drives `MixedStreamerReducer`. In `read_vec` (`src/core/mixed_reducer/mixed_streamer_reducer.cc:255-326`):

- line 288: `filter(iterator->key() + id_offset)` correctly **skips** the deleted rows (local rows 0-2);
- line 318: `mt_list_.produce(VectorItem((*next_id)++, std::move(bytes)))` assigns each survivor a **fresh dense key 0,1,2,…**, discarding the original key (`iterator->key()` is only logged). `add_vec`/`add_vec_with_builder` then insert into the target with that rewritten pkey (lines 375-377, 410). The `enable_pk_rewrite_` flag (line 30, header line 88) is set to true by `Index::merge` (`index.cc:1049-1050`) but is **never read** — renumbering is unconditional.

So the new HNSW file holds 25 vectors keyed 0-24, where key *k* holds the vector of physical row *k+3*. Meanwhile the segment's scalar side is **not rewritten** by this task: the forward block still has 28 rows, `doc_ids_` still has 28 entries, and the new `BlockMeta` even declares `doc_count = doc_ids_.size()` = 28 (`segment.cc:1569-1576`). Phase 3 just swaps in the new indexer via `reload_vector_index` and persists the version (`collection.cc:1036-1070`), so the broken key space survives reopen (read-only or not).

### Why reads go wrong while counts agree

The read side treats a vector-index key as a segment-local row ID:

- Search: `VectorRecallNode::State::collect_batch` pushes `iter_->doc_id()` (the index key) into `indices` and calls `segment_->fetch(columns, indices)` (`src/db/sqlengine/planner/vector_recall_node.cc:225, 231`), where `fetch` takes `segment_doc_ids` — local row positions (`segment.cc:2571-2572`). Vector payloads for hits use the same indices (`vector_recall_node.cc:255-259`).
- Fetch-by-pk: `SegmentImpl::Fetch` lower-bounds `doc_ids_` to get `segment_doc_id`, then calls `vector_indexer->Fetch(block_doc_id)` (`segment.cc:1040-1051, 1282-1301`); the indexer fetch is a fetch **by key** (`vector_column_indexer.cc:150-159`).

With the shifted keys: querying doc-0006's basis vector matches key 3 → scalar row 3 → returns **doc-0003** (wrong live ID). Queries for doc-0003/4/5 match keys 0-2, which map to deleted rows 0-2 and get filtered — those docs vanish. Keys only span 0-24, so rows 25-27 (**doc-0025…doc-0027, the live tail**) are unreachable by any search. `Fetch(doc-0025..27, include_vector=true)` computes `segment_doc_id` 25-27, and `Fetch` by that key fails since the index has only 25 entries → `Fetch` returns nullptr (`segment.cc:1294-1300`) even though the scalar columns for those rows are intact.

The count/enumeration checks agree because they never touch the vector index: `doc_count(filter)` (`segment.cc:616`) and scalar enumeration read the forward block minus the delete bitmap — 28 − 3 = 25, with correct pks in `USER_ID`/`GLOBAL_DOC_ID`. The corruption exists only in the vector index's key space, i.e. in the **association** between keys and rows, which no count can observe.

### The two controls

- **Optimizing the empty collection first** changes nothing: `optimize()` finds no records in the writing segment and `persist_segments.size() == 0`, returning OK immediately (`collection.cc:929-942`). The later failing sequence is byte-for-byte the same.
- **Optimizing the non-empty data before deleting** builds the HNSW index through the *same* `CreateVectorIndexTask` path, but with an empty delete store: `SegmentIndexFilter::is_filtered` is false for every row, so nothing is skipped and the dense renumbering `(*next_id)++` coincides with the original row offsets 0-27 — an identity mapping, hence a correct index. The column is then marked indexed (`segment.cc:1540`). After the deletes, the second `optimize()` again selects `CreateVectorIndexTask` (ratio still < 0.3), but `create_vector_index` short-circuits at `segment.cc:1534-1539` ("already indexed and index params are same, skip create"). The correct 28-key index survives and queries still exclude deleted rows via the delete bitmap. The bug only manifests when the **first** index build happens with deletions already present.

### The contrasting maintenance path (large deleted fraction)

If the deleted fraction reaches ≥ 0.3, `build_compact_task` sets `rebuild = true` and emits a **`CompactTask` carrying the filter** (`collection.cc:1100-1104, 1166-1169`; existing test coverage at `tests/db/collection_test.cc:3913, 6745`). `ExecuteCompactTask` (`segment_helper.cc:100-175`) then rewrites the scalar side *first*: `ReduceScalar`/`FilterRecordBatch` scan rows in min_doc_id order, drop deleted rows physically, and record their concatenated local row IDs in `delete_row_id_bitmap` (`segment_helper.cc:255-256, 934-997`, esp. 964 and 969). `ReduceVectorIndex` merges the vector indexes under a `RowIdFilter` over that same bitmap (`segment_helper.cc:85-98, 146-153, 638-759`), and reuse-of-first-indexer is disabled whenever a filter is present (`CanReuseFirstIndexer`, `segment_helper.cc:767-772`). The identical `MixedStreamerReducer` dense renumbering runs here too — but it is **consistent**, because the compacted forward store assigns the survivors exactly the same dense row IDs 0..N−1 in the same scan order. (Note the third variant: multi-segment groups with `rebuild=false` get a `CompactTask` with a **null** filter, `collection.cc:1137-1140` — no rows are skipped, so renumbering is again identity.) The broken combination is unique to `CreateVectorIndexTask`: filter active (rows skipped) + scalar side not rewritten.

### Mapping invariant a fix must preserve

For every segment, in every vector index serving reads: **vector-index key == segment-local row ID (`segment_doc_id`) == index into `doc_ids_` == row position in the forward store**, for every row the segment physically holds. Equivalently: for every live doc, `search(its vector)` must yield a key whose `fetch(columns, key)` row is that doc, and `Fetch(g_doc_id, include_vector)` must retrieve that doc's vector at `doc_ids_` position. Any merge that skips filtered rows may renumber keys densely **only if** the scalar rows are rewritten in the same order in the same operation (the CompactTask/rebuild contract); otherwise the original keys must be carried through `read_vec` (e.g. produce `iterator->key() + id_offset` instead of `(*next_id)++` — the builder path already tolerates key holes via `PushToDocCache`'s `kInvalidKey` padding, `mixed_streamer_reducer.cc:542-550, 560-561`). A fix should also make the emitted `BlockMeta.doc_count` (`segment.cc:1575`) agree with the index's actual key space.

### Regression check that detects association errors

Count assertions (doc_count == 25) pass with this bug, so the test must assert **content-addressed identity**:

1. Create a non-quantized FP32 HNSW/COSINE collection with a scalar label; insert N docs `doc-0000…` each with a distinct unit basis vector kept outside the collection; do **not** pre-optimize.
2. Delete a leading subset whose fraction is strictly below 0.3 (e.g. 3 of 28) so `build_compact_task` selects `CreateVectorIndexTask`; flush; `optimize()`.
3. For **every live ID**: (a) search with its saved reference vector and assert the top-1 hit ID equals that exact ID (catches the shift-by-deleted-count and the unreachable tail — assert specifically that the last deleted-count-many live IDs appear as top-1 for their own vectors); (b) `fetch(id, include_vector=True)` and assert the returned vector equals the saved reference vector bit-for-bit (catches the `Fetch` key-range failure and cross-wiring); (c) assert a scalar-only enumeration's ID set equals the searched-and-found ID set.

Mirror the same assertions above the 0.3 threshold to pin the rebuild path too. Existing tests don't cover the failing combination: `Feature_Optimize_Rebuild` (`collection_test.cc:3913`) exercises the ≥-threshold compaction, and `SegmentCompactReuseTest` (`segment_helper_test.cc:656`) exercises filter-less multi-segment reuse; neither builds a first index over pre-deleted rows below the threshold.

All conclusions above are limited to the paths traced in this checkout: `collection.cc` optimize/task selection, `segment_helper.cc` compact/create-index execution, `segment.cc` insert/delete/fetch/search plumbing, `vector_column_indexer.cc`, `index.cc`/`mixed_streamer_reducer.cc` merge core, `delete_store.h`, and `vector_recall_node.cc`; I did not run or modify anything.
