All findings below come from reading the frozen tree; I built and ran nothing. Paths are repo-relative.

# Root cause in one sentence

`SegmentImpl::flush()` uses "is the member WAL handle open and non-empty" (`src/db/index/segment/segment.cc:2220-2222`) as a proxy for "is there unpersisted in-memory data", but WAL crash-recovery replays documents through a *separate, read-only* WAL handle and leaves the member `wal_file_` null (`segment.cc:4206-4215`, `4303-4340`) — so `Optimize()`'s dump-then-reclassify sequence commits a version that declares the recovered segment fully persisted while its forward data was never written and its WAL is orphaned.

# 1. State difference: recovery path vs ordinary insertion path

**Ordinary insertion (control):** `CollectionImpl::handle_insert` → `SegmentImpl::Insert` (`segment.cc:903-918`) calls `append_wal(doc)` *first*. `append_wal` lazily assigns the member `wal_file_` via `open_wal_file()` (`segment.cc:4324-4340`, `4303-4322`; member declared at `segment.cc:400-401`). Then `internal_insert` (`segment.cc:837-881`) populates the in-memory components: `id_map_->upsert` (853), `memory_store_->insert` (857), scalar/FTS/vector memory indexers (861-872), `doc_ids_.push_back` (878), and updates the meta's writing-block counters (874-876). So a normally-written segment has **both**: live in-memory data **and** an open `wal_file_` whose on-disk file exceeds the 64-byte header (`has_record()` = `file_.size() > sizeof(header_)`, `src/db/index/storage/wal/local_wal_file.h:75-77`).

**Recovery path:** `CollectionImpl::recovery()` (`src/db/collection.cc:1836-1892`) opens persisted segments read-only (1858-1874), then opens the version's *writing* segment (1879-1885). `SegmentImpl::Open` calls `recover()` only when the meta has a `writing_forward_block` (`segment.cc:484-501`). `recover()` (`segment.cc:4193-4301`) opens the WAL at `<collection>/<seg_id>/<block_id>.wal` (`src/db/common/file_helper.h:74-78`) into a **local** `recover_wal_file` handle, replayed read-only and closed by `AILEGO_DEFER` (4206-4215). Each record is re-applied through `internal_insert/internal_update/internal_upsert/internal_delete` (4250-4266) — the same in-memory mutation path, but **without** `append_wal`, so the member `wal_file_` is never assigned (its only assignment site is `open_wal_file()`, reachable only from `append_wal`). The mem-block's `max_doc_id_` is advanced in memory only (4288).

Result: the recovered writing segment has the in-memory data and a WAL file on disk, but `wal_file_ == nullptr`. The invariant the flush gate assumes — *non-null WAL handle with records ⟺ unpersisted in-memory data exists* — is broken.

**Why it is initially readable:** all reads are served from live in-process objects. `get_all_segments()` appends `writing_segment_` whenever `doc_count() > 0` (`collection.cc:2076-2082`); `doc_count()` is `doc_ids_.size()` (`segment.cc:589-600`); `Stats()` sums those counts (`collection.cc:403-442`); `Fetch` resolves pk→doc_id through the RocksDB-backed IDMap (durable on its own: `src/db/index/common/id_map.h:92`, `id_map.cc:97-111`) and reads the segment's memory forward store (`collection.cc:1376-1401`). Nothing on the read path touches disk state for the writing segment.

# 2. Call sequence and exact condition that loses the data

`CollectionImpl::Optimize` (`collection.cc:779-915`):

1. `collection.cc:794-800` — `writing_segment_->doc_count() != 0` (true: replay filled `doc_ids_`), so it calls `switch_to_new_segment_for_writing()` (`collection.cc:1517-1552`).
2. `collection.cc:1519` — `writing_segment_->dump()` (`segment.cc:2197-2215`) calls `flush()`, which hits the gate:

   ```cpp
   if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();   // segment.cc:2220-2222
   ```

   **This is the exact condition.** Because the process inserted nothing since recovery, `wal_file_` is null and `flush()` returns OK *without* executing `memory_store_->flush()`, `finish_memory_components()` (which would convert the memory block into persisted block metas, `segment.cc:4342-4412`), `id_map_->flush()` (2266-2269), `update_version()` (2301, 4414-4426), or WAL removal (2304-2315). `dump()` then even sets `sealed_ = true` (2212) and returns OK.
3. `collection.cc:1522` — the old writing segment (data still memory-only) is added to `segment_manager_` as a "persisted" segment.
4. `collection.cc:1527-1531` — a new empty writing segment is created (its `min_doc_id` uses the old meta's `max_doc_id()+1`, still correct in memory since the writing block is removed only afterwards).
5. **The point of no return:** `collection.cc:1536-1549` — `writing_segment_meta->remove_writing_forward_block()` (1538; `src/db/index/common/meta.h:265-267`), then `version.add_persisted_segment_meta(...)` (1539), `version_manager_->apply(version)` and `flush()` (1546-1549). The on-disk version now says: segment N is *persisted*, and its `persisted_blocks()` contain **no SCALAR forward block** (nothing was ever dumped; `SegmentMeta::doc_count()/max_doc_id()` derive solely from persisted blocks once the writing block is gone, `meta.h:271-315`). The WAL file `<path>/N/<B>.wal` still physically exists, but the version no longer references any writing block that would lead to it.
6. `collection.cc:802-810` — `persist_segments` now contains segment N (size 1, so no "nothing to optimize" early return). `build_compact_task` with one segment and `rebuild == false` produces a `CreateVectorIndexTask` (`collection.cc:991-1001`), which runs against the **live in-process segment object** (`src/db/index/segment/segment_helper.cc:51-70`, `1113-1125` → `create_all_vector_index`, `segment.cc:1617-1641`). It reads vectors from the still-alive in-memory indexers, writes index files into segment N's directory, and emits an output meta that is a copy of N's meta with the writing block removed plus vector-index blocks — still no forward block. Optimize applies/flushes that version (`collection.cc:863-868`, `872-877`) and hot-swaps the index on the live segment (`905-909`). Everything returns `Status::OK()`.

**On the third open:** `recovery()` opens segment N from `persisted_segment_metas()` read-only (`collection.cc:1858-1874`). In `SegmentImpl::Open`, `writing_forward_block()` has no value, so `recover()` is skipped (`segment.cc:484-510`) — persisted segments never replay WALs. `load_persist_scalar_blocks()` iterates `persisted_blocks()`, finds no SCALAR block, loads nothing (`segment.cc`, `load_persist_scalar_blocks` body). The current writing segment is the new empty N+1 with its own (nonexistent) WAL. The recovered documents are unreachable; the original WAL sits orphaned in segment N's directory (and would be physically deleted if a later `CompactTask` destroyed that segment, `collection.cc:898-901` → `segment.cc:2334-2338`).

**Why the control doesn't lose data:** without the crash, `wal_file_` is open with records, so step 2's `flush()` runs to completion: memory block → persisted forward/index blocks in the meta (`finish_memory_components`, `segment.cc:2288-2298`, `4342-4412`), version updated (2301), WAL removed (2304-2315). The subsequent reclassification at `collection.cc:1536-1549` is then truthful.

**Why "insert even one doc after recovery" masks it:** `append_wal` re-opens the *existing* WAL with `create_new=false`, which seeks to end-of-file for appending (`segment.cc:4303-4322`; `local_wal_file.cc:92-106`), so `wal_file_` is non-null and `has_record()` is true — the gate passes and everything (recovered + new) is persisted. This matches the scenario's "without inserting any additional documents" precondition. The scenario's other precondition (no rollover) matters because rollover paths route through the same gated `flush()` (`collection.cc:1444-1448`, `1472-1474`; `segment.cc:841-844`, `2959-2962`) and would behave identically, muddying the repro.

# 3. Why success + same-handle stats prove nothing

- `Optimize`'s OK only reports that each step's `Status` was OK; the pivotal step (`dump()`→`flush()`) *silently* returns OK as a no-op (`segment.cc:2220-2222`). There is no postcondition check anywhere that the demoted segment's meta actually gained forward blocks covering its documents before the version is committed (`collection.cc:1519-1549`).
- `Stats()` is computed from the live in-process segment list (`collection.cc:403-442` → `2076-2086`), and `doc_count()` is `doc_ids_.size()` (`segment.cc:589-600`). After the switch, segment N is still the same object with its memory store, `doc_ids_`, and freshly built in-memory vector index — so doc counts and `index_completeness` (`collection.cc:425-439`, using `meta()->vector_indexed(...)`, which the CreateVectorIndexTask *did* legitimately set) all look healthy. None of this consults the persisted version or files.
- Durability here is a property of the on-disk version + block files, and the only component that checked disk (the version manager) was *told* by the code that the segment was persisted. Even the destructor path wouldn't help: `~CollectionImpl` → `Close` → `flush_unsafe` → `writing_segment_->flush()` (`collection.cc:302-306`, `340-361`, `380-395`) flushes only the *new, empty* writing segment. (Note the same gate also makes an explicit `Collection::Flush()` after pure recovery a silent no-op — harmless there, since the WAL and version are untouched, but it shows the proxy is wrong for every caller.)

# 4. Smallest repair principle and regression test (described, not implemented)

**Repair principle:** never let "writing → persisted" demotion depend on a proxy for persisted-ness; make `flush()`'s skip condition reflect *actual unpersisted in-memory state*. Smallest change consistent with the existing design: in `SegmentImpl::recover()` (or `Open`, when a writing block exists and ≥1 record was replayed), re-establish the invariant by assigning the member `wal_file_` via `open_wal_file()` after replay — the file exists, opens in append mode at EOF, and `has_record()` is true, so the existing gate at `segment.cc:2220` now correctly forces a real dump. The more robust variant: replace the gate's condition with a dirty-state test (e.g., `memory_store_` non-empty / writing-block `doc_count_ != 0` / `delete_store_->modified_since_last_flush()`), optionally plus a defensive assertion in `switch_to_new_segment_for_writing` (`collection.cc:1519-1539`) that after `dump()` the segment meta contains persisted SCALAR blocks accounting for the writing block's documents before `remove_writing_forward_block()`/version commit. A related latent defect worth fixing while there: `recover()` declares `Status status;` (`segment.cc:4249`) but the switch arms discard `internal_*` return values, so replay failures are never detected (4274-4280 is dead).

**Regression test** — the existing harness in `tests/db/crash_recovery/` (fork + SIGKILL of helper binaries: `write_recovery_test.cc`, `collection_optimizer.cc`, `utility.h`) covers crash-during-write and crash-during-optimize, but `CrashDuringOptimize` (`optimize_recovery_test.cc:143-259`) *masks* this bug by inserting 25,000 more documents after recovery before re-running the optimizer. The missing sequence:

1. Fork a writer child: `Collection::CreateAndOpen`, insert N docs (N far below `max_doc_count_per_segment` and the buffer-full threshold so no rollover), **no** `Flush()`; parent SIGKILLs the child (mirrors `write_recovery_test.cc` mechanics).
2. `Collection::Open` in a fresh handle/process; assert `Stats().doc_count == N` and `Fetch` returns every doc byte-equal (WAL replay works — this passes today).
3. **With zero intervening writes**, call `Optimize()`; assert OK and `Stats().doc_count == N` (also passes today — that's the trap).
4. Release the handle; `Collection::Open` again in a fresh process.
5. Assert `Stats().doc_count == N`, every pk fetches with correct content, and a vector `Query(topk)` returns expected hits. On current code this fails with `doc_count == 0`.
6. Optional structural assertions to pin the invariant: after step 3, the persisted version's meta for the demoted segment lists forward blocks summing to N docs; no `*.wal` remains unreferenced by the current version after a successful optimize.

**Established from source vs. requiring execution.** Everything in §1-§3 and the mask/masking behavior is directly readable from the cited code. I did not build or run anything; a reproduction would still be needed to confirm runtime-dependent details: (a) that `CreateVectorIndexTask` succeeds for every schema shape on such a segment (e.g., a schema without vector fields makes it near-no-op — Optimize still returns OK, loss already sealed at `collection.cc:1546-1549`); (b) the exact third-open symptom for `Fetch` — since the RocksDB IDMap persists pk→doc_id independently (`id_map.cc:97-111`), fetch may fail as `InternalError("Segment not found"/"Fetch doc failed")` (`collection.cc:1388-1398`) rather than clean NotFound; (c) that WAL records actually reached disk before the first kill — `LocalWalFile::append` writes immediately but fsync cadence depends on `max_docs_wal_flush` (`local_wal_file.cc:29-50`), which the scenario stipulates survived.
