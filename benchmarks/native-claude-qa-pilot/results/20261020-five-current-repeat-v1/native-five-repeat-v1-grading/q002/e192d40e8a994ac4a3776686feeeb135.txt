# Root cause: an empty inverted-filter result is silently downgraded to "no filter" in the FTS recall path

## 1. How the query is routed

- The public `Query` target carries an `FtsClause` (`src/include/zvec/db/query.h:53-58`). `SQLEngineImpl` parses it into an FTS AST stored as `FtsCondInfo` (`src/db/sqlengine/sqlengine_impl.cc:162-271, 314-339`), while the scalar condition string becomes the WHERE tree the analyzer walks.
- `SearchCondCheckWalker` classifies each scalar condition: if the field `has_invert_index()` it becomes an **invert** condition, otherwise a **forward filter** (`src/db/sqlengine/analyzer/query_node_walker.cc:196-199, 216-250, 296, 686-701`). `QueryAnalyzer::decide_filter_index_cond` then detaches the invert subtree into `query_info->invert_cond` and the remainder into `filter_cond` (`src/db/sqlengine/analyzer/query_analyzer.cc:257-314`); the FTS clause is copied separately (`query_analyzer.cc:402-403`).
- With an FTS target, `QueryPlanner::make_plan` picks `fts_scan` (`src/db/sqlengine/planner/query_planner.cc:414-415, 645-668`), which builds a `DocFilter` (invert cond carried via `query_info_->invert_cond()`, `src/db/sqlengine/planner/doc_filter.h:33-41`) and an `FtsRecallNode`. The `InvertCondOptimizer` doesn't rescue this case: EQ/NE/IN/LIKE always stay invert (`src/db/sqlengine/planner/optimizer.cc:38-45`), and a GT with a zero-size range has ratio 0 < threshold so it stays invert too (`optimizer.cc:79-86`).

## 2. The failure chain for `hello` + `status='archived'` (or `views > 1000`)

**Step 1 — the zero-match invert search.** `FtsRecallNode::prepare()` calls `doc_filter_->compute_filter()` (`src/db/sqlengine/planner/fts_recall_node.cc:110-114`), which runs `InvertSearch::exec_invert_cond_tree` (`src/db/sqlengine/planner/doc_filter.cc:24-34`; `src/db/sqlengine/planner/invert_search.cc:38-72, 154-162`):

- For `status='archived'`, EQ on a term absent from RocksDB returns a **null bitmap** (`src/db/index/column/inverted_column/inverted_column_indexer_search.cc:30-33`, wrapped at `:756-820`). An `InvertedSearchResult` with a null bitmap has `count()==0`, `extract_ids()` yields nothing, and — critically — `make_filter()` returns **`nullptr`** (`src/db/index/column/inverted_column/inverted_search_result.h:48-50, 79-85, 140-156`). So `invert_filter_` is already null at `doc_filter.cc:33`: the first conflation of *"matches nothing"* with *"no filter"*.
- For `views > 1000`, the range scan returns a created-but-empty bitmap (`inverted_column_indexer_search.cc:343, 440-451`), so `count()==0` but `make_filter()` would return a reject-all `Filter` (`inverted_search_result.h:34-50`).

**Step 2 — brute-force-by-keys erases the filter.** `prepare()` then calls `get_bf_by_keys_and_update(fts_brute_force_by_keys_ratio)` (`fts_recall_node.cc:124-129`; default ratio 0.05, `src/db/common/config.cc:40`). With `count()==0` the condition `match_count <= doc_count * ratio` is **always true** (0 ≤ 0 even for this 3-doc segment), so it extracts the (empty) id list and **resets `invert_filter_` and `invert_result_`**, returning an empty vector (`src/db/sqlengine/planner/doc_filter.cc:109-133`, esp. 123-128).

**Step 3 — `DocFilter::empty()` now reports "no filter at all".** `params.filter = doc_filter_->empty() ? nullptr : doc_filter_` (`fts_recall_node.cc:132`). `empty()` checks only `delete_filter_ || invert_filter_ || forward_plan_ || forward_filter_expr_` (`doc_filter.cc:68-71`): `invert_filter_` was just reset, `delete_filter_` is null because nothing was deleted (`SegmentImpl::get_filter()` returns nullptr for an empty delete store, `src/db/index/segment/segment.cc:1613-1615`), and there is no forward condition — so **`filter = nullptr`**.

**Step 4 — empty `candidate_ids` means "unrestricted".** `SegmentImpl::fts_search` forwards params to `FtsColumnIndexer::search` (`segment.cc:4585-4601`). There, candidate-driven mode engages only `if (!query_params.candidate_ids.empty())` (`src/db/index/column/fts_column/fts_column_indexer.cc:206-217`), and the pushed-down filter is null (`:220, 229-230`). The empty candidate list produced by a **zero-match filter** is indistinguishable from "no candidate restriction was computed" — the second conflation. The scan runs unfiltered and `hello` matches all three docs → **IDs {1,2,3}**.

Note the struct comment even documents the intended contract — "when non-empty, FtsColumnIndexer restricts evaluation to this set" (`src/db/index/column/fts_column/fts_types.h:25-36`) — but says nothing about what an empty set should mean, and the FTS path collapses the distinction. The vector path does not: it keeps a *list* of key-vectors, so "absent" (`bf_pks` empty → `nullptr`, `src/db/index/column/vector_column/vector_column_indexer.cc:184-193`) differs from "present but empty" (a non-null shared_ptr to an empty key set → per-block dispatch skips blocks with no pks, `combined_vector_column_indexer.cc:299-322`; brute force over zero keys, `src/core/interface/index.cc:742-745`).

## 3. Why the three controls behave correctly

- **`hello` + `status='published'` → {2,3}.** The invert result has `count()==2 > 0` (threshold is `(uint64_t)(3×0.05)=0`), so `get_bf_by_keys_and_update` returns `nullopt` and keeps `invert_filter_` (`doc_filter.cc:134-140`). `empty()` is false → the filter is pushed into the FTS scan loop via `next_doc(filter_ptr)` (`fts_column_indexer.cc:220, 229-250`), which excludes doc 1 through `Filter::is_filtered = !contains(id)` (`inverted_search_result.h:39-41`).
- **`one` + `status='published'` → ∅.** Same retained filter; `one` matches only doc 1, which `is_filtered` rejects. This proves the filter machinery works whenever the invert result is non-empty — the loss happens *only* on the zero-match → empty-id-list path.
- **Scalar-only query → ∅.** Without an FTS/vector cond the planner picks `invert_scan` (`query_planner.cc:416-418, 589-643`). `InvertRecallNode` consumes the `InvertedSearchResult` directly (`src/db/sqlengine/planner/invert_recall_node.cc:82-85`); its iterator over a null bitmap has `iter_==nullptr` → `valid()==false` (`inverted_search_result.h:88-137`), so `gen()` ends immediately (`invert_recall_node.cc:41-45`). The zero-match state never passes through the ids/filter handoff, so it can't be lost.
- **No inverted indexes → ∅.** The conditions are classified forward (`query_node_walker.cc:199, 296, 688-698`), so `filter_cond` is set and the planner builds an Acero forward-bitmap plan or a forward filter expression inside `DocFilter` (`query_planner.cc:398-407, 533-557`; `doc_filter.cc:36-64`). `get_bf_by_keys_and_update` no-ops because `invert_result_` is null (`doc_filter.cc:116-118`), `empty()` is false (a forward member is set), and every FTS candidate for `hello` fails the forward check in `is_filtered` (`doc_filter.cc:73-107`) → empty set.

## 4. Minimal repair principle

**Principle: "filter evaluated to the empty set" must short-circuit the recall to ∅; only "no filter was ever evaluated" may mean unrestricted.** Concretely, the minimal, safest change is at the single choke point that owns the handoff:

1. In `FtsRecallNode::prepare()` (`fts_recall_node.cc:124-132`): if `get_bf_by_keys_and_update` returns an engaged-but-empty id list, return an empty `FtsIndexResults` immediately instead of calling `fts_search`. This is sound because the invert cond is the *whole* scalar condition's evaluation, and the other filter components (delete, forward) can only narrow, never widen. This one change fixes both zero-match variants (null-bitmap EQ and empty-bitmap range) before either leak is reached.
2. To make the invariant structural rather than caller-side, encode the distinction in the type: make `FtsQueryParams::candidate_ids` an `std::optional<std::vector<uint64_t>>` (`fts_types.h:30-35`) and have `FtsColumnIndexer::search` return `{}` when it is engaged but empty (`fts_column_indexer.cc:209`) — mirroring how the vector path's `bf_pks` already separates absent from empty.
3. Close the secondary leak: a present `invert_result_` with `count()==0` should never read as "no filter" — either keep `invert_result_` reachable in `DocFilter::empty()` (`doc_filter.cc:68-71`), or don't reset `invert_filter_` when the extracted id set is empty (`doc_filter.cc:126-128`), or make `make_filter()` return a reject-all filter for a null bitmap (`inverted_search_result.h:48-50`). Any one of these preserves correctness even if the planner-side short-circuit is bypassed.

Ordinary queries are untouched: no-filter queries still get `candidate_ids = nullopt`/unrestricted scans; non-empty selective filters still take the pushdown or bf-by-keys paths exactly as today.

## 5. Regression checks

Functional (each asserts ID *sets*, per the four reported behaviors):

1. **Repro matrix on the FTS + invert path:** zero-match EQ (`status='archived'`), zero-match range (`views>1000`, and LT/GE variants), zero-match IN/CONTAIN_ANY, zero-match LIKE prefix/suffix, `IS NULL` on a null-free column → all must return ∅ alongside a matching full-text term.
2. **Non-empty filters keep working:** `hello`+`published` → {2,3}; `one`+`published` → ∅; filter matching *all* docs (`views>0`) → same set as unfiltered `hello`; unfiltered `hello` → {1,2,3}.
3. **Alternate paths stay correct (the controls):** scalar-only zero-match → ∅ (`InvertRecallNode`); same data without inverted indexes → ∅ via *both* forward-filter flavors (two-stage bitmap plan and single-stage expression, `query_planner.cc:541-552`); vector search + zero-match filter → ∅ (pins the `bf_pks` null-vs-empty contract, `vector_recall_node.cc:163-169`).
4. **Composite conditions:** zero-match AND non-empty → ∅; zero-match OR non-empty → the non-empty side only (bitmap AND/OR null handling, `inverted_search_result.h:173-191`; `invert_search.cc:53-55`).
5. **Boundaries:** multi-segment collections where the filter is zero-match in one segment and non-empty in another (per-segment planning, `query_planner.cc:370-430`) — the zero-match segment must contribute nothing; deletes present (delete filter non-null changes `empty()` outcomes, `segment.cc:1613-1615`); `fts_brute_force_by_keys_ratio` at 0 and 1 (`config.cc:40, 74-78`); large collections where `0 < count ≤ ratio×doc_count` so bf-by-keys engages with a *non-empty* set (restriction must still be exact); `topk=0` early return (`fts_column_indexer.cc:181-183`); FTS AST variants (phrase, must/should/must_not) crossed with a zero-match filter.
6. **Unit level:** `DocFilter::get_bf_by_keys_and_update` returning engaged-empty must leave the caller able to distinguish it (contract test for whichever representation the fix adopts), and `InvertedSearchResult::make_filter()` on a null bitmap must not be interpretable as "no filter".
