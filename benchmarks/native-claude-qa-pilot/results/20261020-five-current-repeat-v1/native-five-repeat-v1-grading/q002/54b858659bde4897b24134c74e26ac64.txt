All the evidence is in hand. Here is the complete analysis — everything below is **source-based inference** (I read the snapshot; I did not build or execute anything).

# Root cause: "restricted to zero docs" is silently converted into "no restriction"

The FTS planner has a *brute-force-by-keys* optimization: when an inverted-index filter is highly selective, it extracts the matching doc IDs, **destroys the filter object**, and passes the IDs as `candidate_ids`. A zero-match filter is maximally "selective", so it always takes this branch — producing an *empty* ID list. Two downstream conventions then conspire:

1. `FtsColumnIndexer::search` treats an **empty** `candidate_ids` as *"unrestricted"* (`if (!query_params.candidate_ids.empty())`, `src/db/index/column/fts_column/fts_column_indexer.cc:209`), a contract even locked in by a test (`BruteForceEmptyCandidatesFallsBack`, `tests/db/index/column/fts_column/fts_column_indexer_test.cc:1795-1806`) and the field comment "when non-empty, … restricts" (`src/db/index/column/fts_column/fts_types.h:30-35`).
2. `FtsRecallNode` then computes `params.filter = doc_filter_->empty() ? nullptr : doc_filter_` (`src/db/sqlengine/planner/fts_recall_node.cc:132`). Since the brute-force step already reset `invert_filter_`, there is no delete filter (no deletions ⇒ `SegmentImpl::get_filter()` returns `nullptr`, `src/db/index/segment/segment.cc:1613-1615`), and no forward filter (the condition was fully inverted), `DocFilter::empty()` (`src/db/sqlengine/planner/doc_filter.cc:68-71`) returns **true**.

Result: FTS search runs with **no candidate restriction and no filter** → every doc matching `hello` is returned: {1, 2, 3}.

## Step-by-step trace of the anomalous query (`hello` + `status='archived'`)

1. **Classification.** `status` has an inverted index, so the walker marks the relation `invert` (`query_node_walker.cc:196,216,685-702` — `has_invert_index()`); `QueryAnalyzer::decide_filter_index_cond` detaches it as `invert_cond` (`src/db/sqlengine/analyzer/query_analyzer.cc:276-287`); the FTS predicate becomes `fts_cond_info`.
2. **Plan choice.** With `fts_cond_info` set, the planner picks `fts_scan` (`src/db/sqlengine/planner/query_planner.cc:413-415`), which builds a `DocFilter` (`query_planner.cc:642-652`, `build_doc_filter` at `533-557`; `forward_filter` is null because nothing was left over as a forward condition).
3. **Filter computation.** `FtsRecallNode::prepare()` calls `doc_filter_->compute_filter()` (`fts_recall_node.cc:111`), which runs the inverted condition tree (`doc_filter.cc:24-34`). For EQ on a missing term, `get_bitmap_eq` returns a **null bitmap** on RocksDB `kNotFound` (`src/db/index/column/inverted_column/inverted_column_indexer_search.cc:30-33`), wrapped into the result at `811-813`. For `views > 1000`, `get_bitmap_gt` instead builds an **empty non-null** bitmap (`inverted_column_indexer_search.cc:363-368` + term scan finding nothing). Either way `count() == 0` (`src/db/index/column/inverted_column/inverted_search_result.h:79-85`). Note also `make_filter()` returns `nullptr` when `bitmap_` is null (`inverted_search_result.h:48-50`) — so in the EQ case `invert_filter_` is *already* null before the brute-force step.
4. **The fatal branch.** `prepare()` calls `get_bf_by_keys_and_update(fts_brute_force_by_keys_ratio())` (`fts_recall_node.cc:126-129`; default ratio **0.05**, `src/db/common/config.cc:40`). Threshold = `static_cast<uint64_t>(3 × 0.05) = 0` (`doc_filter.cc:119-120`). `match_count(0) ≤ 0` ⇒ it extracts IDs (none — `extract_ids` no-ops on a null bitmap, `inverted_search_result.h:145-147`), **resets `invert_filter_` and `invert_result_`**, and returns an engaged-but-empty `std::vector<uint64_t>` (`doc_filter.cc:123-133`).
5. **Loss of the restriction.** `params.candidate_ids` = `{}`; `doc_filter_->empty()` = true (see above) ⇒ `params.filter = nullptr` (`fts_recall_node.cc:126-132`).
6. **Unrestricted search.** `SegmentImpl::fts_search` passes params verbatim to `FtsColumnIndexer::search` (`segment.cc:4585-4601`). The empty-candidate guard skips wrapping in `CandidateDocIterator` (`fts_column_indexer.cc:209-217`), `filter_ptr` is null (`:220`), and the plain posting walk returns all `hello` docs (`:229-251`) → **{1, 2, 3}**.

## Why the three controls behave correctly

- **`hello` + `status='published'`** → {2, 3}. `match_count = 2 > threshold = 0`, so `get_bf_by_keys_and_update` returns `nullopt` and *keeps* `invert_filter_` (`doc_filter.cc:134-140`). `empty()` is false ⇒ `params.filter = doc_filter_` (`fts_recall_node.cc:132`), and the filter-aware `next_doc(filter_ptr)` loop (`fts_column_indexer.cc:229-250`) skips doc 1 via `DocFilter::is_filtered` → `InvertedSearchResult::Filter::is_filtered(id) = !contains(id)` (`inverted_search_result.h:39-41`, `doc_filter.cc:73-79`).
- **`one` + `status='published'`** → ∅. Same pushdown path; the term posting yields only doc 1, which the filter excludes.
- **Inverted indexes removed** → ∅. The conditions are now classified `filter_rels` (no `set_invert()`, `query_node_walker.cc:196,216`) and become a *forward* filter. `build_doc_filter` converts it into an Acero bitmap plan (`query_planner.cc:541-553`), materialized in `compute_filter` (`doc_filter.cc:36-49`). With `invert_result_` null, `get_bf_by_keys_and_update` returns `nullopt` (`doc_filter.cc:116-118`), and `empty()` is false because `forward_plan_` is set — so the DocFilter survives as `params.filter`, and `get_forward_bit` = false for every doc (`doc_filter.cc:80-107`) → empty set.
- **Scalar-only query** → ∅. No FTS/vector condition ⇒ `invert_scan` → `InvertRecallNode` (`query_planner.cc:416-418`, `584-600`), which iterates the inverted result directly; a null/empty bitmap gives `valid() == false` immediately (`invert_recall_node.cc:41-46`; `inverted_search_result.h:88-132`). It never passes through the lossy brute-force conversion.

The bug is therefore **strategy-dependent**: only the "invert result exists ∧ count ≤ threshold" branch loses information, and with 3 docs the threshold is 0, so *only zero-match* filters trigger it. (In a ≥20-doc collection, 1-match filters also take the branch — but with non-empty IDs, which works.)

# Minimal repair principle

**Principle: a computed restriction to the empty set is a first-class answer and must never be re-encoded as "absent".** Concretely, the smallest correct fix is at the point where the ambiguity is introduced, `FtsRecallNode::prepare()` (`fts_recall_node.cc:126-129`):

- If `get_bf_by_keys_and_update` returns an **engaged optional whose vector is empty**, short-circuit: return an empty `FtsIndexResults` without calling `fts_search`. This is sound because an empty candidate set intersects any posting list to ∅, and because `count()==0` always satisfies `0 ≤ threshold` (threshold is unsigned), so *every* zero-match invert condition — null-bitmap EQ and empty-bitmap GT alike — funnels through this branch.
- Everything else is bit-for-bit unchanged: no condition ⇒ `nullopt` + null filter (unrestricted); matching selective condition ⇒ non-empty IDs; non-selective condition ⇒ filter pushdown.

**Contract-level hardening (recommended companion):** make the type express the distinction, mirroring the vector path, which does *not* have this bug: `bf_pks` is a `shared_ptr<vector<uint64_t>>` where null = unrestricted and *set-but-empty = restrict to nothing* (`src/include/zvec/core/interface/index_param.h:187`; `src/core/interface/index.cc:742-745`; `vector_recall_node.cc:163-169` emplaces even an empty vector). Change `FtsQueryParams::candidate_ids` to `std::optional<std::vector<uint64_t>>` (`fts_types.h:35`), wrap `CandidateDocIterator` whenever *engaged* (`fts_column_indexer.cc:209`), and update `BruteForceEmptyCandidatesFallsBack` (`fts_column_indexer_test.cc:1795-1806`), which currently codifies the ambiguous contract.

**Secondary latent hazard:** `InvertedSearchResult::make_filter()` returns `nullptr` for a null bitmap (`inverted_search_result.h:48-50`), and `DocFilter::empty()` ignores `invert_result_` (`doc_filter.cc:68-71`). Even without the brute-force branch, a zero-match EQ condition degrades to "no filter" through this path. Returning an exclude-everything `Filter` when the result object exists (or counting an existing `invert_result_` as non-empty) closes the same class of hole for any future caller.

# Regression checks

1. **Reported matrix, end-to-end** (integration, e.g. under `python/tests` / `tests/db`): the exact 3-doc collection — `hello`∧`archived` → ∅; `hello`∧`views>1000` → ∅; `hello`∧`published` → {2,3}; `one`∧`published` → ∅; scalar-only `archived` → ∅; and the **no-condition guard** `hello` → {1,2,3} (the repair must not empty unrestricted queries). Compare ID sets, not order.
2. **Index-configuration invariance**: rerun the identical matrix with the inverted indexes dropped (forward-filter path) and assert identical ID sets — results must not depend on which physical filter strategy the analyzer chose.
3. **Strategy-boundary unit tests** (`DocFilter`/`FtsRecallNode` level): match counts at 0, exactly-threshold, threshold±1; sweep `fts_brute_force_by_keys_ratio` ∈ {0.0, 0.05, 1.0} (`config.cc:40`) and assert identical ID sets across ratios — the empty-result outcome must be ratio-independent.
4. **Both zero-match bitmap shapes**: missing-term EQ (null bitmap, `inverted_column_indexer_search.cc:30-33`) and out-of-range GT/GE (empty bitmap, `:363-368`); also IN-lists with all terms missing (null bitmap via the `kNotFound` branch, `:109-113`) and IS NULL/IS NOT NULL.
5. **Interaction guards**: zero-match filter *plus deletions* (ensures the `delete_filter_`/`empty()` interplay at `doc_filter.h:38`, `doc_filter.cc:68-71` doesn't regress); non-empty brute-force IDs still return the posting∩candidates intersection with unchanged BM25 scores (extend `BruteForceTermMatchesPostingDriven`, `fts_column_indexer_test.cc:1637`); candidate+filter coexistence (`:1767-1793`).
6. **Cross-path guard**: vector query with the same zero-match filter must still return ∅ (already correct via `bf_pks`, `index.cc:742`) — protects against a "fix" that breaks the working convention, and covers hybrid `MultiQuery` (FTS+vector) paths.
7. **Multi-segment**: force a dump/merge so ≥2 segments exist, rerun the matrix; per-segment empty results must merge to empty through `SegmentNode` + order-by-score + fetch (`query_planner.cc:433-464`) and the FTS reducer's local↔global doc_id remapping (`fts_types.h:38-45`) must not resurrect docs. Include an empty collection as a degenerate case.
