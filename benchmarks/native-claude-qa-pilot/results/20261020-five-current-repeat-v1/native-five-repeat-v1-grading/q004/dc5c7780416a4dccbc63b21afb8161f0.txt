## Setup: what `zvec.init(optimize_threads=4)` configures

`init()` puts `optimize_threads` into a config dict (`python/zvec/zvec.py:162-163`, call at `:173`), the pybind layer validates it is positive and stores it as `data.optimize_thread_count = 4` (`src/binding/python/model/common/python_config.cc:154-157`), then applies it via `GlobalConfig::Instance().initialize(data)` (`:193`). The global optimize pool is built lazily **once** under `std::call_once`: `new ailego::ThreadPool(optimize_thread_count(), optimize_thread_binding())` (`src/db/common/global_resource.cc:22-33`), i.e. a 4-worker pool (worker counts are clamped to `[1, hardware_concurrency]`, `src/ailego/parallel/thread_pool.cc:93-100`; hardware ≥ 4 is assumed; binding defaults to false, `src/db/common/config.cc:42-43`).

## 1. Pool and worker-count selection for A vs. B

`OptimizeOptions.concurrency_` defaults to 0, with the comment "default use config.optimize_thread_pool" (`src/include/zvec/db/options.h:56-62`). `collection.optimize()` passes it into the compact tasks (`src/db/collection.cc:952`, `:988-990`, task construction `:1128-1207`), which reach the vector-index merge at `SegmentHelper::MergeWithOptionalReuse` (`src/db/index/segment/segment_helper.cc:743-745`, `:799-811`). The identical selection logic also exists for per-segment index creation at `src/db/index/segment/segment.cc:1560-1567`.

The selection (`segment_helper.cc:804-811`):

- **A (`concurrency=0`)**: `merge_options.pool = GlobalResource::Instance().optimize_thread_pool()` and `write_concurrency = pool->count()` → the **global 4-worker optimize pool**.
- **B (`concurrency=2`)**: `pool` stays `nullptr` (default, `src/include/zvec/core/interface/index_param.h:54-56`); `write_concurrency = 2`.

Both are forwarded verbatim by `VectorColumnIndexer::merge` (`src/db/index/column/vector_column/vector_column_indexer.cc:128-130`) into the core engine's `Index::merge` (`src/core/interface/index.cc:1416-1446`), which materializes the pool:

- A (`options.pool != nullptr`): `reducer->set_thread_pool(options.pool)`; `effective_write_concurrency = min(4, pool->count()=4) = 4` (`index.cc:1436-1439`). The reducer keeps the raw pointer (`src/include/zvec/core/framework/index_reducer.h:173-175`, `:183`) and errors if unset (`src/core/mixed_reducer/mixed_streamer_reducer.cc:211-214`).
- B (`pool == nullptr`): a **fresh function-local** `ailego::ThreadPool(2, false)` is created, kept alive by a `std::unique_ptr` declared to outlive `reduce()` (`index.cc:1433-1445`), set on the reducer, `effective_write_concurrency = 2`.

**B does not change the global pool.** The global pool is constructed once via `call_once` (`global_resource.cc:22-24`) and nothing in this path reconfigures it; B's 2-worker pool is scoped to that single `Index::merge` call and destroyed afterward. (For a builder-backed rebuild, `effective_write_concurrency` only feeds `PARAM_MIXED_STREAMER_REDUCER_NUM_OF_ADD_THREADS` for the streaming add path, `index.cc:1448-1452`; the builder path's parallelism comes from the pool itself, below.)

## 2. Handoff to the target builder's train/build and conversion training

When the merge needs a rebuild (`target_builder_ != nullptr`), `reduce()` dispatches to `reduce_with_builder` (`mixed_streamer_reducer.cc:218-223`; the builder was attached via `set_target_streamer_wiht_info`, `index.cc:1506-1511`; `reduce` invoked at `index.cc:1520`). The meaningful handoff is `MixedStreamerReducer::index_build` (`src/core/mixed_reducer/mixed_streamer_reducer.cc:742-777`):

- Line **744**: the selected pool is wrapped in `BorrowedSingleQueueIndexThreads(*thread_pool_)` — a non-owning adapter whose `count()`/`submit()` delegate to the underlying pool (`src/include/zvec/core/framework/index_threads.h:174-225`, `count()` at `:184-186`). So the builder-visible worker count is 4 (A, global pool) or 2 (B, local pool).
- Lines **745-747**: if a `target_builder_converter_` exists, `IndexConverter::TrainAndTransform(converter, target_holder, threads)` runs **immediately before** the builder calls, and forwards the same `threads` to `converter->train(two_pass_holder, std::move(threads))` (`src/core/framework/index_converter.cc:27-36`; the subsequent `transform` takes no threads).
- Line **760**: `target_builder_->train(threads, target_holder)`.
- Line **768**: `target_builder_->build(std::move(threads), target_holder)`.

The threads-taking virtuals are declared at `src/include/zvec/core/framework/index_trainer.h:92-93` (train) and in `index_runner.h` (build); DiskAnnBuilder overrides both (`src/core/algorithm/diskann/diskann_builder.h:45`, `:52`; implementations `diskann_builder.cc:633`, `:697`).

**Passing vs. consuming:** the source proves the same borrowed pool object is *passed* to conversion-train, train, and build. It does not prove every implementation consumes it — e.g., the base converter's `train(holder, threads)` explicitly discards threads: `(void)threads; return train(std::move(holder));` (`src/include/zvec/core/framework/index_converter.h:185-189`). Whether a given converter/builder actually schedules work on the pool is per-implementation; DiskAnnBuilder demonstrably uses it (below).

## 3. DiskANN PQ training: the outer chunk-dispatch pool is *not* reused — it is rebuilt, bounded by both counts

`DiskAnnBuilder::train(threads, holder)` keeps the caller's `threads` when non-null (it creates its own `SingleQueueIndexThreads(build_thread_count_, false)` only as a null-fallback, `diskann_builder.cc:657-663`), then calls `train_quantized_data(threads)` (`:665`). There:

- `build_thread_count_` comes from `PARAM_DISKANN_BUILDER_THREAD_COUNT`; 0 → `max(1, hardware_concurrency)`, and values above hardware concurrency are warned/clamped (`diskann_builder.cc:51-59`).
- The quantizer's thread setting is computed at `diskann_builder.cc:391-394`, with the in-source comment *"The quantizer creates its own pool, so bound it by the caller's pool"*:
  `pq_thread_count = max(1, min(build_thread_count_, threads->count()))`, passed as the `"thread_count"` init param (`:394`). `threads->count()` is 4 under A and 2 under B (via `BorrowedSingleQueueIndexThreads::count()`).
- `PqInt8Quantizer` stores that param (`src/turbo/quantizer/pq_int8_quantizer/pq_int8_quantizer.cc:142`) and, in `train_all_chunks`, **creates a brand-new pool**: `std::make_shared<SingleQueueIndexThreads>(thread_count_, false)` (`:322-323`). Chunks are dispatched round-robin across `pool_count = threads->count()` workers (`m = i; m < num_chunk_; m += pool_count`, `:328-341`) with `task_group->wait_finish()` (`:356`). Per-chunk k-means is then single-threaded — `train_chunk` makes a 1-worker local pool ("parallelism is at the chunk level", `:199-200`).

So the PQ outer pool is *sized from* the caller's pool (its `count()`) intersected with the builder's own `build_thread_count_`, floored at 1 — but the caller's pool object itself is never reused for chunk dispatch; a separate pool with that many workers is constructed for the training stage.

## 4. What these settings establish — and what they don't

**Established (pool capacity only):**
- A runs its optimize-side work on the global pool with exactly 4 workers (`optimize_threads=4`, validated positive at `python_config.cc:156` and `config.cc:83-86`, clamped ≤ hardware concurrency at `thread_pool.cc:93-100`).
- B runs on a private 2-worker pool for the duration of that merge; the global pool remains a 4-worker pool, untouched.
- DiskANN PQ training's outer pool has `max(1, min(build_thread_count_, caller_pool_count))` workers — 4-capped under A, 2-capped under B — and each chunk's k-means is single-threaded.

**Not established:**
- **Whole-process thread count.** `optimize_threads`/`concurrency` say nothing about the separate global *query* pool (`global_resource.cc:25-26`, sized from `query_thread_count`, default `CgroupUtil::get_cpu_limit()`, `config.cc:38`), the DiskANN null-fallback pool, the quantizer's own pool, the per-chunk 1-worker k-means pools, or any non-zvec threads. Several of these are created per stage, so instantaneous thread counts exceed any single configured number.
- **Actual CPU utilization.** Pool sizes are *capacity ceilings*, not activity. Workers idle when no tasks are queued; PQ chunk parallelism is additionally bounded by `num_chunk_` (round-robin over `pool_count` leaves workers idle if chunks are fewer); train and build are sequential phases; requested sizes above hardware concurrency are silently clamped (`thread_pool.cc:93-100`); and with binding off by default, the OS decides placement. Proving CPU busy-ness or throughput would require runtime measurement, which this source-reading scenario explicitly excludes.
