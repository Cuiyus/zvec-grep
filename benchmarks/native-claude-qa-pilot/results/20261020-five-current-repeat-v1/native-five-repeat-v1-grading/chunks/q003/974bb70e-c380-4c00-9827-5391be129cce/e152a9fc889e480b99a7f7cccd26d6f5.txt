## Root cause

**The invariant in this codebase:** within a segment, a persisted vector-index block is keyed by *segment-local row ordinals*. Insert assigns the key as the writing block's row count (`SegmentImpl::InsertVector`, `src/db/index/segment/segment.cc:702-705`), and every read path interprets an index key as a local row id: search translates block-local keys to segment ids via `block_offset + doc.key()` (`src/db/index/column/vector_column/combined_vector_column_indexer.cc:58-66`, offsets built from block-meta `doc_count_` at `:279-283`), then those ids are used directly as forward-store row indices to fetch pk/scalars (`VectorRecallNode::State::collect_batch`, `src/db/sqlengine/planner/vector_recall_node.cc:225,231`), and `Fetch` maps `g_doc_id → segment_doc_id → block_doc_id` and calls `vector_indexer->Fetch(block_doc_id)` (`segment.cc:1040-1051, 1276-1300`; `src/db/index/column/vector_column/vector_column_indexer.cc:150-165`).

**What breaks it:** deleting doc-0000..0002 only marks *global* doc ids in the shared bitmap and removes pks from the IDMap (`SegmentImpl::internal_delete`, `segment.cc:933-937`; `src/db/index/common/delete_store.h:96-104`; `src/db/index/common/id_map.cc:115-117`). Nothing rewrites data. Then `optimize()` computes delete ratio 3/28 ≈ 0.107 < `COMPACT_DELETE_RATIO_THRESHOLD = 0.3` (`src/db/common/constants.h:41`), so `rebuild=false` (`CollectionImpl::build_compact_task`, `src/db/collection.cc:1093-1104`). With one persisted segment inside the size limit, the tail branch creates a **`CreateVectorIndexTask`** — an *in-place index build* with **no compaction** (`collection.cc:1160-1171`; the task struct carries no filter at all, `src/db/index/segment/segment_helper.h:71-97`).

That task runs `SegmentImpl::create_all_vector_index → create_vector_index → merge_vector_indexer` (`src/db/index/segment/segment_helper.cc:1121-1133`; `segment.cc:1466-1489, 1519-1578, 1491-1517`), which merges the segment's persisted Flat block(s) into a new HNSW file, passing the segment's live delete filter: `vector_indexer->Merge(to_merge_indexers, filter_, ...)` (`segment.cc:1511`; `filter_` = `SegmentIndexFilter`, mapping local id → `doc_ids_[id]` → delete bitmap, `segment.cc:464-476, 482-483`).

The engine merge is where keys are destroyed: `Index::merge` builds a `MixedStreamerReducer` with `ENABLE_PK_REWRITE=true` (`src/core/interface/index.cc:1016-1077`, esp. `:1048-1050`; the flag is parsed at `src/core/mixed_reducer/mixed_streamer_reducer.cc:30-31` but the renumbering is in fact unconditional). In `read_vec`, filtered (deleted) rows are **skipped** (`mixed_streamer_reducer.cc:288-292`) and each surviving row is produced with a **fresh sequential key** `(*next_id)++` instead of `iterator->key()` (`:318`), which `add_vec` inserts as the target key via `add_with_id_impl` (`:375-377`). So the new HNSW holds 25 entries keyed 0..24 where key *j* contains the vector of local doc *j+3*.

Meanwhile the segment is otherwise untouched: the forward store still has 28 rows, `doc_ids_` still has 28 global ids, and the new block meta even *claims* `doc_count = doc_ids_.size() = 28`, min/max from `doc_ids_` (`segment.cc:1568-1576`). `reload_vector_index` then destroys the correctly-keyed Flat indexers and installs the mis-keyed HNSW as the only block (`segment.cc:1752-1810`; committed via `collection.cc:1028-1032, 1063-1070`), and the index file plus meta are flushed to the manifest — so a read-only reopen reloads exactly this state (`load_vector_index_blocks`, `segment.cc:3979-4048`; `doc_ids_` rebuilt from the forward GLOBAL_DOC_ID column, `segment.cc:3874-3923`).

**Resulting symptoms (28 docs, first 3 deleted):**
- Query with doc-0006's reference vector → nearest key 3 → forward row 3 → pk "doc-0003": **wrong live ID** (off by the 3 deleted predecessors).
- Query with doc-0003's vector → key 0 → `DocFilter`'s delete filter (`src/db/sqlengine/planner/doc_filter.h:38,43`; `segment.cc:464-476`) treats key 0 as deleted local id 0 → the true hit is **dropped**; doc-0003/4/5 become unreachable.
- Keys 25-27 don't exist → local docs 25-27 (**live tail**) can never be returned; their vectors sit at keys 22-24 and are attributed to doc-0022..24.
- `Fetch(include_vector)` for local ids 25-27: `index->fetch` finds no key → the whole `Fetch` returns nullptr (`segment.cc:1294-1300`) and `FetchVectorOp`/`fetch_dense_vector` fails (`vector_recall_node.cc:251-263`) — **vector payload fetch fails while scalar forward data is intact** (scalars were read successfully at `segment.cc:1096-1131` before the vector step).

## Why counts and scalar enumeration agree

`doc_count(filter)` iterates `doc_ids_` against the delete bitmap (`segment.cc:616-627`), and scans/queries read the forward store plus bitmap — none of these touch the vector index. The in-place build rewrote *only* the vector index file, so every scalar-side check reports a correct 25; only vector search and vector fetch consult the corrupted key space.

## The two controls

- **Optimize-before-first-insert doesn't help:** with no records, phase 1 seals nothing and `persist_segments` is empty → `optimize()` returns immediately (`collection.cc:929-942`). No index is built, so the post-delete optimize still takes the buggy in-place path.
- **Optimize before deleting avoids it:** that run merges with an empty delete store, so nothing is filtered and the renumbering is the identity (source Flat keys are dense 0..27 in insertion/iteration order, `segment.cc:702-705`, `finish_memory_components` `:4383-4396`). The meta is marked indexed (`segment.cc:1485`, persisted at `collection.cc:1028-1032`). The *second* optimize (after deletes) again builds a `CreateVectorIndexTask`, but `create_vector_index` early-returns because `segment_meta_->vector_indexed(column)` with identical params (`segment.cc:1534-1539`; cf. `all_vector_index_ready`, `:1819-1826`, `collection.cc:1135`). The correctly-keyed HNSW survives and deletes keep being applied at query time — correct results. The bug only manifests when the in-place build runs *while deletions exist*.

## The larger-delete-fraction path (contrast)

At >30% deleted rows, `rebuild=true` and `build_compact_task` emits a **`CompactTask` carrying the delete filter** (`collection.cc:1119-1127, 1166-1168`). `ExecuteCompactTask` (`segment_helper.cc:100-175`) rewrites *everything together*: `ReduceScalar` scans rows in order, `FilterRecordBatch` drops deleted rows from the forward batch and records deleted **input-scan positions** in `delete_row_id_bitmap` (`:934-997`, esp. `:969`), then `ReduceVectorIndex`/`MergeWithOptionalReuse` feed that bitmap as a `RowIdFilter` (`:85-98, 146-153, 638-759, 794-853`). The reducer again renumbers `next_id++` — but here it is correct *by construction*, because the new segment's forward rows are the live rows in the same scan order, so new key *j* == new local id *j* (and `min/max_doc_id` are recomputed from the surviving GLOBAL_DOC_IDs, `:962-967`). The scalar and vector sides are compacted consistently; the failing path compacts only the vector side.

## Invariant a fix must preserve

For every persisted vector-index block: **key *k* in the block must hold the vector of the document at segment-local row `block_offset + k`** (equivalently, forward row ordinal == index key), and the block meta's `doc_count_/min_/max_doc_id` must describe exactly the row span the keys cover. Any merge that skips rows must either keep original keys, rewrite the surrounding segment (scalar side) in the same order, or persist an explicit key→local-id mapping. (Note `enable_pk_rewrite_` is read at `mixed_streamer_reducer.cc:30-31` but never consulted — honoring it, i.e. emitting `iterator->key()` instead of `(*next_id)++` when the caller needs key preservation, is the minimal source-level hook; `read_vec:318`, `read_sparse_vec:530`, `add_vec:375-377`.)

## Regression check (association, not counts)

Insert N docs whose pk↔vector binding is unambiguous (distinct unit basis vectors, as in the report); delete a subset **below the 0.3 ratio** (e.g. the first 3 of 28); flush; `optimize()`; reopen. Then, for every live pk: (1) search with its saved reference vector and assert top-1 returns **that pk** (identity check — the bug returns shifted pks like doc-0003 for doc-0006); (2) `fetch(pk, include_vector=true)` succeeds for **all** live pks including the tail (doc-0025..27) and the returned vector **equals the saved basis vector bit-for-bit** (catches both missing keys and wrong-vector keys); (3) optionally assert the persisted block's index doc count matches `doc_count - deleted` or block meta `doc_count`, catching the meta/content mismatch at `segment.cc:1573-1575`. Count-only assertions (`count()==25`, scalar scan listing 25 pks) pass despite the corruption, since the scalar side is never rewritten on this path.
