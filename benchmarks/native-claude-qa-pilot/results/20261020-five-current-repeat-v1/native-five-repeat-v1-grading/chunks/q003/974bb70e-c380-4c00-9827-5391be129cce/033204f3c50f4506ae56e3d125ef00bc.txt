All the evidence is in hand. Here is the source-level diagnosis, limited to what this checkout establishes.

# Root cause: the low-delete-ratio optimize path filters vectors out of the index without compacting anything else

## 1. The healthy ID/key model

A segment keeps three parallel structures, all keyed by **segment-local row position**:

- `doc_ids_` — "Maps segment-local doc ID (array index) to global doc ID" (`src/db/index/segment/segment.cc:397-398`), filled on insert (`segment.cc:914`).
- The forward (scalar) store — row *r* holds doc `doc_ids_[r]`'s scalar fields.
- The per-column vector indexer blocks — "vector index (uses block-local doc ID, each indexer starts from 0)" (`segment.cc:367-369`); insert keys the vector by the writing block's current row count (`segment.cc:702-705`).

Reads depend on this alignment everywhere:

- Search results are translated back with `doc.set_key(block_offset + doc.key())` (`src/db/index/column/vector_column/combined_vector_column_indexer.cc:66`, offsets from block-meta `doc_count_` at :279-284), then used directly as forward-store row indices: `indices.push_back(iter_->doc_id()); segment_->fetch(columns, indices)` (`src/db/sqlengine/planner/vector_recall_node.cc:225-231`).
- Vector payload fetch computes `block_doc_id = segment_doc_id - block_offset; vector_indexer->Fetch(block_doc_id)` (`segment.cc:1279-1294`, and `CombinedVectorColumnIndexer::Fetch` at combined_vector_column_indexer.cc:427-451).
- Deletions never renumber anything: `DeleteStore::mark_deleted(doc_id)` just sets a bit in a global-doc-id bitmap (`src/db/index/common/delete_store.h:96-100`), and queries filter at read time (`vector_recall_node.cc:169`; segment-level filter conversion at combined_vector_column_indexer.cc:349-361).

**So deleted rows must keep occupying their vector keys until a compaction rewrites the whole segment.**

## 2. What the reported sequence actually executes

Insert 28 → flush seals one persisted segment (28 rows, flat writing vectors, keys 0–27). Delete doc-0000…0002 → only the delete-store bitmap changes. Then `optimize()` (`src/db/collection.cc:910`):

1. Phase 1 snapshots persisted segments (`collection.cc:918-938`); one segment, 28 rows.
2. `build_compact_task` computes `current_doc_count=28`, `current_actual_doc_count=25` via `doc_count(filter)` (`collection.cc:1093-1099`, `segment.cc:616`). The rebuild test is
   `actual < count * (1 - COMPACT_DELETE_RATIO_THRESHOLD)` (`collection.cc:1100-1104`) with `COMPACT_DELETE_RATIO_THRESHOLD = 0.3f` (`src/db/common/constants.h:41`). 25 ≥ 28·0.7 = 19.6 → **`rebuild = false`**.
3. Single-segment group + `!rebuild` → **`CreateVectorIndexTask`** (`collection.cc:1160-1164`), i.e. `SegmentImpl::create_all_vector_index` (`segment_helper.cc:1121-1133`, `segment.cc:1466`).
4. `create_vector_index` → `merge_vector_indexer` (`segment.cc:1491-1517`) builds the HNSW index by calling

   ```
   vector_indexer->Merge(to_merge_indexers, filter_, merge_options);   // segment.cc:1511
   ```

   where `filter_` is the `SegmentIndexFilter` that maps a **segment-local row id** to its global doc id and consults the delete store (`segment.cc:464-476`, `4444-4450`; constructed at `segment.cc:482-483`).
5. `VectorColumnIndexer::Merge` hands that filter to the engine (`vector_column_indexer.cc:103-134`) → `Index::merge` → `MixedStreamerReducer` with PK rewrite enabled (`src/core/interface/index.cc:1016-1077`, esp. :1049-1050).
6. **The reducer drops filtered rows and compacts the keys of everything after them**: `read_vec` skips any source key for which `filter(key + id_offset)` is true (`src/core/mixed_reducer/mixed_streamer_reducer.cc:288-292`) and re-keys each surviving row with a fresh sequential id `VectorItem((*next_id)++, …)` (`:318`), inserted via `add_with_id_impl(pkey, …)` (`:375-377`).
7. `reload_vector_index` swaps the old flat indexer for the new 25-key HNSW file (`segment.cc:1752-1810`), and phase 3 commits the new segment meta (`collection.cc:1028-1040`) whose `VECTOR_INDEX` block still records `min/max/doc_count` from the **uncompacted** `doc_ids_` (28 docs, `segment.cc:1569-1576`).

Crucially, nothing else in the segment was touched: forward rows, `doc_ids_`, inverted/scalar structures all still have 28 rows. The new index file has keys 0–24 where **key *k* holds the vector of source row *k+3***.

## 3. Why the symptoms follow mechanically

With rows 0,1,2 deleted and live rows 3…27 re-keyed to 0…24:

- **Wrong live IDs**: querying the saved vector of doc-000*k* (k ≥ 6) matches key *k−3*, which `AddBlock` reports as segment row *k−3* (combined_vector_column_indexer.cc:66), and `fetch` resolves to `doc_ids_[k−3]` = doc-000(k−3) — a live but wrong ID, shifted by the delete count.
- **Omitted live docs (two ways)**: for k = 3,4,5 the match lands on rows 0–2, which the query-time delete filter suppresses (`vector_recall_node.cc:169`) — so doc-0003…0005 become unreachable by vector search. For k ≥ 25 no key exists at all (index holds only 25 vectors) — doc-0025…0027, the live tail, are never returned.
- **Vector payload fetch failures**: `Fetch` for segment rows 25–27 asks the engine for keys 25–27, which don't exist → `index->fetch` error (`vector_column_indexer.cc:150-165`); rows 3–24 return the shifted (wrong) vectors. The scalar side of `SegmentImpl::Fetch` still works because the forward block is intact and row-indexed (`segment.cc:1028-1051`).
- **Counts/scalars agree**: the live count and scalar enumeration apply the delete-store bitmap keyed by *global doc id* to the untouched 28-row forward store (`doc_count(filter)` at `segment.cc:616`; filtering readers in `src/db/index/segment/filtering_reader.cc`). They never consult the vector index, so they correctly report 25 while the vector mapping is corrupt.
- **Reopen doesn't help**: the 25-key file and the meta claiming `doc_count=28` were committed to the version (`collection.cc:1036-1040`); `SegmentImpl::Open` reloads exactly that state (`segment.cc:478-533`, `load_vector_index_blocks` at :497-499).

## 4. The two controls

- **Optimizing the empty collection first (no effect)**: `optimize()` seals the writing segment only `if (writing_segment_->has_record())` and then returns `Status::OK()` when `persist_segments.size() == 0` (`collection.cc:929-942`). It is a pure no-op; the later insert→delete→optimize still lands on the `CreateVectorIndexTask` path above.
- **Optimizing the initial non-empty data before deleting (avoids the bug)**: the first optimize runs the same `CreateVectorIndexTask`, but with an empty delete store `SegmentIndexFilter::is_filtered` is false for every row (`segment.cc:464-476`), so the reducer keeps all 28 rows and keys 0–27 stay aligned with `doc_ids_`. The segment is marked vector-indexed (`create_vector_index` at `segment.cc:1534-1540`, `create_all_vector_index` at :1485). After the deletes, the second optimize again builds a `CreateVectorIndexTask` (ratio still < 0.3), but `create_vector_index` **early-returns** — "if segment is already indexed and index params are same, skip create" (`segment.cc:1534-1539`; see also `skip_task = all_vector_index_ready()` at `collection.cc:1135`, `segment.cc:1819-1826`). The aligned 28-key index survives, and the three deletes are handled purely by query-time filtering — correct results. The bug only fires when the index is *first materialized while deletions are already pending*.

## 5. The high-delete-ratio path is different — and consistent

If the deleted fraction exceeds 30% (`constants.h:41`), `rebuild = true` (`collection.cc:1100-1104`) and the group becomes a **`CompactTask` carrying the collection-level filter** (`collection.cc:1119-1127`, :1166-1168). `ExecuteCompactTask` (`segment_helper.cc:100-175`) then renumbers *both sides by the same permutation*:

- `ReduceScalar` scans input segments in ascending-min_doc_id order, drops deleted rows from the new forward store, and records their positions in `delete_row_id_bitmap` (`FilterRecordBatch`, `segment_helper.cc:934-997`, add at :969).
- `ReduceVectorIndex` merges the source vector indexers with a `RowIdFilter` over that same bitmap (`segment_helper.cc:85-98`, :127-153), so the reducer's drop-and-rekey (`mixed_streamer_reducer.cc:288-318`) produces exactly the same 0…24 numbering as the rewritten forward rows; the new segment is opened fresh with 25-row `doc_ids_` (`collection.cc:986-996`).
- `CanReuseFirstIndexer` is disabled whenever a filter is present (`segment_helper.cc:767-771`), preventing a copied base index from retaining deleted vectors.

(Also note the multi-segment, `rebuild=false` compact passes `nullptr` as the filter — `collection.cc:1137-1140` — which is consistent too, because deleted rows are then kept on both sides. The single-segment `CreateVectorIndexTask` path via `merge_vector_indexer`'s `filter_` at `segment.cc:1511` is the one place a delete filter is applied to vectors without a matching storage compaction.)

## 6. The invariant a fix must preserve

> For every segment and vector column, for every segment-local row *r* ∈ [0, `doc_ids_.size()`): the vector of global doc `doc_ids_[r]` must be stored under key *r − block_offset(b)* in the block *b* whose meta `doc_count_` range covers *r* (offsets as computed in combined_vector_column_indexer.cc:279-284), and each block meta's `doc_count` must equal the number of keys the block's file actually holds.

Equivalently: deleted-but-not-compacted rows must keep occupying their keys (visibility is the query-time delete filter's job); renumbering vector keys is legal **only** as part of an atomic rewrite of forward rows, `doc_ids_`, all block metas, and every row-keyed index under one shared permutation — which is exactly the contract the `CompactTask`/`ReduceScalar`+`ReduceVectorIndex` path upholds via the shared `delete_row_id_bitmap` (`segment_helper.cc:108-111`). A minimal fix would stop passing `filter_` in `merge_vector_indexer` (`segment.cc:1511`) so segment-level index materialization indexes all rows; the alternative is routing any optimize-with-pending-deletes through the compact path.

## 7. Regression check that catches wrong associations, not counts

Count-only assertions (25 docs) pass on the broken state, so the test must assert **identity** between the saved vector and the returned ID:

1. Configure FP32 HNSW/COSINE, dim 32; insert doc-0000…doc-0027 where doc-000*k*'s vector is basis vector *e_k* (kept outside the collection). No explicit index build.
2. Delete doc-0000…0002 (≈10.7% < 30%, forcing the `CreateVectorIndexTask` path), flush, `optimize()`.
3. Assert for **every live** k ∈ {3…27}: top-1 search with *e_k* returns exactly ID doc-000*k* with cosine ≈ 1 (this catches the off-by-3 shift — on the broken build, *e_6* returns doc-0003 — the doc-0003…0005 suppression, and the doc-0025…0027 tail loss); and vector-payload fetch by ID returns bytes equal to *e_k* (catches the shifted `Fetch` and the out-of-range failures for rows 25–27 via `vector_column_indexer.cc:158-160`).
4. Assert searches with *e_0…e_2* never return the deleted IDs.
5. Repeat with (a) a delete fraction above the 0.3 threshold and (b) the optimize-before-delete control, so both maintenance paths (`CompactTask` rebuild vs. skip/create) are pinned; existing tests like `SegmentCompactReuseTest` (`tests/db/index/segment/segment_helper_test.cc:656`) exercise merge/reuse mechanics but the ID↔vector identity assertion is what detects this class of mis-association.
