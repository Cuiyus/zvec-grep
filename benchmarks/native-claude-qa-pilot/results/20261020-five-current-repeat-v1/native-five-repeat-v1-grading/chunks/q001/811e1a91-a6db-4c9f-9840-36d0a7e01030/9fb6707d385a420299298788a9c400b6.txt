# Root cause: WAL replay leaves the segment's `wal_file_` handle null, and `SegmentImpl::flush()` uses that handle as its "is there anything to persist?" test

Everything below is established by static reading of the frozen tree. **I did not build or run anything, and did not execute a reproduction**; the boundary between source-established facts and claims needing execution is stated at the end.

## 1. Recovery path vs. ordinary insertion path

**Ordinary insertion** (process A): `CollectionImpl::write_impl` → `handle_insert` → `writing_segment_->Insert(doc)` (`src/db/collection.cc:1416-1418`, `1420-1470`). `SegmentImpl::Insert` (`src/db/index/segment/segment.cc:903-918`) does two things:

- `append_wal(doc)` (`segment.cc:913-915`), which **lazily opens the member handle `wal_file_`** via `open_wal_file()` on first write (`segment.cc:4324-4340`, `4303-4322`), then appends the serialized doc;
- `internal_insert(doc)` (`segment.cc:837-881`): allocates the global doc id (838), writes the RocksDB-backed `id_map_` (853), the in-RAM forward store `memory_store_` (857), scalar/FTS/vector indexers (861-872), bumps the writing-block meta counters `max_doc_id_`/`doc_count_` (874-876), and appends to `doc_ids_` (878).

No version/manifest commit happens per insert; the manifest on disk still describes the writing segment as it was at creation.

**Recovery** (process B): `CollectionImpl::Open` → `recovery()` (`collection.cc:308-329`, `1836-1892`) loads the manifest (`src/db/index/common/version_manager.cc:190-241`), reopens idmap/delete store from the committed suffixes (`collection.cc:1894-1917`), and opens the writing segment. `SegmentImpl::Open` calls `recover()` because the meta has a writing forward block (`segment.cc:484-501`). `SegmentImpl::recover()` (`segment.cc:4193-4301`):

- derives the WAL path from the *meta's writing block*: `<coll>/<seg_id>/<block_id>.wal` (`segment.cc:4198-4199`; `src/db/common/file_helper.h:74-78`);
- opens the WAL into a **local variable** `recover_wal_file` (`segment.cc:4206-4214`) and closes it on exit via `AILEGO_DEFER` (`4215`);
- replays each record through the *same* `internal_insert/internal_update/internal_upsert/internal_delete` (`4234-4283`).

So after recovery the RAM state is equivalent to post-insert state — `memory_store_`, `doc_ids_`, indexers, idmap entries, and the in-memory writing-block counters are all populated — **but the member `wal_file_` is still `nullptr`** (declared so at `segment.cc:401`; only `append_wal` ever assigns it). The recovered data exists on disk *only* as the old WAL file; the manifest is unchanged.

**Why reads work in process B:** all read paths are served from RAM plus the (in-memory-updated) writing-block meta: `doc_count()` returns `doc_ids_.size()` (`segment.cc:589-600`); scalar fetch falls back to `memory_store_->fetch` for rows inside the writing block (`segment.cc:2744-2756`); vector fetch falls back to `memory_vector_indexers_` while `has_writing_forward_block()` (`segment.cc:1468-1499`); scans include `memory_store_` rows (`segment.cc:2825-2841`); `SegmentMeta::doc_count()` counts the writing block (`src/db/index/common/meta.h:307-318`), keeping the gate at `segment.cc:2684` satisfied.

Two secondary defects in `recover()` (not the loss mechanism): the per-op `Status status;` at `segment.cc:4249` is **never assigned** from the `internal_*` calls, and default-constructed `Status` is OK (`src/include/zvec/db/status.h:61-62`), so the error branch (4274-4280) is dead and replay failures would be silently counted as successes; and `mem_block.max_doc_id_ += added_docs` (`4285-4288`) double-counts, because `internal_insert` already set `max_doc_id_` per doc (`874-875`) — this only inflates the next segment's `min_doc_id` (`collection.cc:1527-1531`), creating a doc-id gap.

## 2. The optimize sequence and the exact condition

`CollectionImpl::Optimize` (`collection.cc:779-915`):

1. `writing_segment_->doc_count() != 0` is **true** (replay filled `doc_ids_`), so it calls `switch_to_new_segment_for_writing()` (`collection.cc:794-800`).
2. `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`):
   - `writing_segment_->dump()` (`1519`) → `SegmentImpl::dump()` (`segment.cc:2197-2215`) → `flush()`.
   - **The exact condition:** `SegmentImpl::flush()` begins with
     `if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();` (`segment.cc:2220-2222`; `has_record` = "file bigger than header", `src/db/index/storage/wal/local_wal_file.h:75-77`).
     After a recovery-only open, `wal_file_ == nullptr` (nothing was inserted in process B), so flush **returns OK having persisted nothing**. Skipped: `memory_store_->flush()` (2233-2236), `id_map_->flush()` (2266-2269), `finish_memory_components()` (2288-2298 → 4342-4412 — the *only* place that turns the memory block into persisted `SCALAR`/`VECTOR_INDEX` `BlockMeta`s), `update_version()` (2301 → 4414-4426), and WAL removal (2304-2315).
   - `dump()` then seals the inverted indexers / dumps FTS (`segment.cc:2204-2210`), sets `sealed_`, returns OK.
   - The switch proceeds: old segment added to `segment_manager_` (`1522`); a new empty writing segment is created (`1527-1534`); the old segment's meta is stripped of its writing block via `remove_writing_forward_block()` (`1537-1538`; `meta.h:263-265`) and recorded as a **persisted** segment (`1539`); then `version_manager_->apply(version)` + `flush()` (`1546-1549`) **commits a new manifest** (`version_manager.cc:260-301`, `77-116`, old manifest deleted at `296-298`).
   - **This manifest commit is the point of no return**: the committed version now references the old segment with *zero data blocks* (no `SCALAR` block was ever added, the writing block was removed), and a fresh empty writing segment.
3. Back in `Optimize`: `persist_segments` = [old segment] (`802-803`). With one segment and no deletes, `build_compact_task` emits a single-`CreateVectorIndexTask` (`collection.cc:991-1001`), executed via `SegmentHelper::ExecuteCreateVectorIndexTask` → `create_all_vector_index` (`src/db/index/segment/segment_helper.cc:1113-1125`; `segment.cc:1617-1640`). Per field, `create_vector_index` (`segment.cc:1670-1730`) either skips (FLAT fields already marked indexed at creation, `segment.cc:534-538`, skip branch `1685-1690`) or calls `merge_vector_indexer` (`1642-1668`), which merges **only `vector_indexers_[column]` (persisted indexers)** — empty here, because `finish_memory_components` never moved `memory_vector_indexers_` across (`segment.cc:4371-4384`). `Merge` with an empty input list returns OK immediately (`src/db/index/column/vector_column/vector_column_indexer.cc:111-113`), so an empty index is flushed and — note — a `VECTOR_INDEX` `BlockMeta` claiming `doc_ids_.size()` docs is added from RAM (`segment.cc:1720-1727`).
4. Second version commit (`collection.cc:863-877`) records that output meta; `reload_vector_index` (`902-909` → `segment.cc:1882-1940`) swaps the segment's meta/indexers in RAM. `Optimize` returns OK (`914`).

**Reopen (process C):** `recovery()` opens the old segment read-only from the manifest; with no writing block, `SegmentImpl::Open` skips `recover()` entirely (`segment.cc:490-510`), so the still-existing WAL file `<coll>/<old_seg>/<block>.wal` is never read again — it is orphaned, not deleted (only compact-input segments get `destroy_segment`→`cleanup`→`RemoveDirectory`, `collection.cc:898-901`, `segment.cc:2326-2338`). `doc_ids_` is rebuilt **only from persisted `SCALAR` blocks** (`segment.cc:3913-3960`); there are none, so doc count is 0 and every fetch misses. The new writing segment's WAL path doesn't exist → "WAL recovery skipped" (`segment.cc:4200-4204`). The documents are gone.

**Why the control doesn't fail:** in process A, `wal_file_` is non-null with records, so `flush()` inside `dump()` runs the full path: forward data written, `finish_memory_components()` adds real `SCALAR`/`VECTOR_INDEX` blocks to the meta, `update_version()` commits them, and the WAL is removed (`segment.cc:2217-2324`). The switch then commits a manifest that *does* reference the data. Also note the failure requires **zero writes between recovery-open and optimize**: a single new insert re-arms `wal_file_` via `append_wal`/`open_wal_file` (`segment.cc:4327-4330`), and `has_record()` is true because the pre-crash records are still in the file — flush would then persist everything correctly.

## 3. Why "success" and same-handle statistics prove nothing here

- **The success return is real but hollow.** Every step checks `Status`, and `flush()` genuinely returned `Status::OK()` from `segment.cc:2221`. The guard conflates "no open WAL handle" with "no unflushed data" — an invariant the recovery path breaks, since replay produces dirty RAM state while leaving `wal_file_` null. OK propagates up through `dump()` (`2201-2202`), the switch (`1519-1520`), and `Optimize` (`796-799`).
- **Statistics are pure RAM.** `CollectionImpl::Stats` sums `segment->doc_count(filter)` (`collection.cc:403-442`) = `doc_ids_.size()` (`segment.cc:589-600`) — `doc_ids_` is never cleared on this path (only the skipped `finish_memory_components` would consume/reset the memory state, `segment.cc:4346-4348`). `index_completeness` is computed from the in-RAM flag `meta()->vector_indexed(field)` (`collection.cc:431-438`; `meta.h:340-354`), which `create_all_vector_index` *sets* (`segment.cc:1636`, `1691`) — so post-optimize stats can even report completeness 1.0 against a manifest that references zero forward rows. Nothing in `Stats` reads the manifest or verifies that referenced files/blocks exist.
- **Durability is defined solely by the committed manifest** (`Version::Save`, `version_manager.cc:77-116`) plus the files it references. The optimize *did* durably commit a manifest — one that excludes the recovered data. Additionally, replayed `id_map_->upsert` entries are not durable either: the RocksDB context runs with `write_opts_.disableWAL = true` (`src/db/common/rocksdb_context.cc:93`) and `id_map_->flush()` was inside the skipped region (`segment.cc:2266-2269`) — consistent total loss, with no ghost `AlreadyExists` on re-insert.
- A same-handle *fetch* after optimize actually degrades (meta gate `segment_meta_->doc_count() == 0` at `segment.cc:2684`, and vector fetch requires `has_writing_forward_block()` at `1469`), which is why the scenario only observes "statistics look healthy" — but nothing surfaces the loss as an error.

## 4. Smallest repair principle and regression test (described, not implemented)

**Repair principle — restore the invariant "after recovery, the segment is exactly as dirty as after an insert."** The minimal change is at the end of `SegmentImpl::recover()` (or in `Open` right after it, `segment.cc:499-501`): when at least one record was replayed, call `open_wal_file()` so the member `wal_file_` points at the existing WAL (it opens append-style since the file exists, `segment.cc:4308-4312`; `has_record()` is true). Then `flush()`'s guard at `2220` passes, and the ordinary persistence machinery (`memory_store_->flush` → `finish_memory_components` → `update_version` → WAL removal) runs unchanged during `dump()`/optimize — no changes needed in `Optimize` or the version layer. A more robust variant replaces the handle-based heuristic with a data-based dirty test (e.g., skip only if `memory_store_` is empty/null **and** the writing block's `doc_count_ == 0`, or track an explicit dirty flag set by `internal_insert`/`recover`). While there, fix the two hygiene defects in `recover()`: capture the `internal_*` return statuses into `status` (`segment.cc:4249-4272`) and drop the double-counting `max_doc_id_ +=` (`4285-4288`).

**Regression test** — the harness already exists in `tests/db/crash_recovery/` (fork/exec + SIGKILL machinery in `write_recovery_test.cc` and `optimize_recovery_test.cc:52-100`, shared schema in `utility.h`, helper binaries `data_generator.cc` / `collection_optimizer.cc`). The uncovered sequence — existing tests only cover crash-during-insert→reopen (`write_recovery_test.cc:164-362`) and crash-during-optimize→reopen (`optimize_recovery_test.cc:144`) — is:

1. **Process A:** create collection, insert N docs (pk + forward fields + vector), then die abruptly (SIGKILL / `_exit`) **before** any `Flush()`/clean `Close()`.
2. **Process B:** open the collection (WAL replay); assert `Stats().doc_count == N` and fetch a sample of pks; call `Optimize()` and assert it returns OK; then kill B abruptly too (strongest form — guarantees nothing leaks to disk from RAM after the manifest commit).
3. **Process C:** open again; assert `Stats().doc_count == N`, fetch every pk and compare field values, and run a vector query with expected neighbors. Optionally assert the manifest now lists ≥1 `SCALAR` block with `doc_count == N` and that the old `<seg>/<block>.wal` file was removed (positive evidence flush actually ran).
4. Keep the control: insert + optimize in one process, no crash → reopen → N docs (passes today).

On current code this test fails at step 3 with doc count 0 (per the trace above); after the repair it should pass, and step 3's WAL-removal assertion also guards against regressing to "data survived only because the orphan WAL was never cleaned up."

## Source-established vs. needs execution; edge notes

- **Established from source:** the entire causal chain — null `wal_file_` after replay, the `flush()` early return, the lossy manifest commit in the switch, the empty-merge vector task succeeding, the reopen loading zero docs, stats being RAM-only, idmap non-durability.
- **Needs execution to confirm:** end-to-end behavior (that `Optimize` truly returns OK on a real replayed segment — e.g., `invert_indexers_->seal()`/`dump_fts_indexers()` at `segment.cc:2204-2210` running on replay-only state is traced as benign but unverified; that `Merge`-empty + `Flush` writes a valid empty index file; that process C reports 0). I ran nothing.
- **Edge behavior (traced, not exercised):** if deletes pushed `rebuild=true` or multiple persisted segments existed, `build_compact_task` would emit a `CompactTask` whose `ReduceScalar` calls `segment->scan()` (`segment_helper.cc:233`); the scan path dereferences `writing_forward_block().value()` (`segment.cc:2837`) *after* the switch removed it — a `std::bad_optional_access` crash rather than silent loss. The described scenario (small collection, single writing segment, no deletes) takes the silent `CreateVectorIndexTask` branch. Also, an explicit `Flush()` or clean `Close()` in the recovery process (`collection.cc:380-395`, `331-361`) is itself a silent no-op for the same reason — recovered data stays WAL-only until some new write re-arms `wal_file_`; optimize is merely what converts that latent state into permanent loss.
