## Summary of the finding (established entirely by reading the frozen source)

The loss is caused by an asymmetry between the WAL-replay path and the normal write path inside `SegmentImpl`: after recovery the segment's member `wal_file_` handle is never opened, and `SegmentImpl::flush()` uses exactly that handle as its "is there anything to persist?" gate. `Optimize()` then treats the replayed segment as dumped, commits a new manifest that removes the segment's writing-forward-block — the only pointer that makes the next open replay the WAL — while no forward data was ever written to disk. Every step returns `Status::OK()`.

---

## 1. What differs between the recovery path and the ordinary insertion path

**Ordinary insertion (process A, before the crash):**
- `CollectionImpl::write_impl` → `handle_insert` → `SegmentImpl::Insert` (`src/db/collection.cc:1416-1418`, `src/db/index/segment/segment.cc:903-918`).
- `Insert` calls `append_wal` (`segment.cc:4324-4340`), which **lazily opens the member `wal_file_`** via `open_wal_file()` (`segment.cc:4303-4322`) and appends the serialized doc to `<collection>/<seg_id>/<block_id>.wal` (`src/db/common/file_helper.h:74-78`).
- `internal_insert` (`segment.cc:837-881`) then populates the in-memory components: `memory_store_` (lazily created by `init_memory_components`, `segment.cc:846-850`, `4119-4191`), scalar/vector indexers, `doc_ids_`, and the writing-block meta counters.
- Crash before `Flush()`: the rows exist **only** in the WAL file; the manifest (`manifest.N`, written at create time, `src/db/collection.cc:1960-1971`) still describes segment X with a `writing_forward_block` and zero persisted SCALAR blocks.

**Recovery (process B):**
- `Collection::Open` without a schema dispatches to `recovery()` (`src/db/collection.cc:308-329`, `1836-1892`). It reloads the manifest (`VersionManager::Recovery`, `src/db/index/common/version_manager.cc:190-241`) and reopens the writing segment from `v.writing_segment_meta()`.
- `SegmentImpl::Open` calls `recover()` **only because the meta still has a writing forward block** (`segment.cc:484-501`).
- `SegmentImpl::recover()` (`segment.cc:4193-4301`) opens the WAL through a **local** handle `recover_wal_file` (`segment.cc:4206-4215`, closed by `AILEGO_DEFER`), replays each record through `internal_insert/internal_update/internal_upsert/internal_delete` (`segment.cc:4249-4272`), and bumps `mem_block.max_doc_id_` in memory only (`segment.cc:4285-4288`). It never assigns the member `wal_file_` and sets no "dirty" flag.

**The differing state:** after recovery the segment is byte-for-byte as readable as after ordinary insertion — `doc_ids_`, `memory_store_`, id map and indexers are populated — but `wal_file_ == nullptr`. Reads work because scan/fetch/count consult those in-memory structures directly: `doc_count()` is `doc_ids_.size()` (`segment.cc:589-600`), `scan()` merges `memory_store_` batches (`segment.cc:2825-2841`), `Fetch` reads `memory_store_` (`segment.cc:2531-2532`, `2755`), and `CollectionImpl::Stats`/`get_all_segments` just iterate the live segment objects (`collection.cc:403-442`, `2076-2082`). Nothing on the read path touches disk state, so the recovered data "can initially be read" while its only durable copy is the WAL file.

Note the rows never hit disk by themselves: `MemForwardStore` buffers rows in `cache_`/`batches_` and only writes them in `flush()`/`close()` (`src/db/index/storage/memory_forward_store.cc:212`, `305-315`), which are reached only through `SegmentImpl::flush()`.

## 2. The call sequence and exact condition that let `Optimize()` succeed without preserving the data

`CollectionImpl::Optimize` (`collection.cc:779-915`), with the recovered segment X (N docs in memory, `wal_file_ == nullptr`) as the only segment:

1. **Gate:** `writing_segment_->doc_count() != 0` is true (`collection.cc:794`) → `switch_to_new_segment_for_writing()` (`collection.cc:1517-1552`).
2. **`dump()`** (`segment.cc:2197-2215`) calls **`flush()`**, which hits the guard at `segment.cc:2220-2222`:
   ```cpp
   if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();
   ```
   **This is the exact condition.** After recovery `wal_file_` is null, so `flush()` returns OK *immediately*, skipping everything that would make the data durable: `memory_store_->flush()` (`2233-2236`), `finish_memory_components()` which converts memory blocks into persisted `BlockMeta`s in the segment meta (`2288-2298` → `4342+`), `update_version()` (`2300-2302` → `4414-4426`), and WAL removal (`2304-2315`). `dump()` then seals indexers (null-guarded / no-FTS no-ops, `segment.cc:2204-2210`, `4570-4575`), sets `sealed_ = true`, and returns OK. The gate is only correct on the ordinary path, where the first `Insert` opened `wal_file_` and `has_record()` (`local_wal_file.h:75-77`, file size > header) is true.
3. **Point of no return** — still inside `switch_to_new_segment_for_writing`: X is added to `segment_manager_` as a *persist* segment (`collection.cc:1522`); X's meta has its writing block erased, `remove_writing_forward_block()` (`collection.cc:1538`, `meta.h:263-265`); X is recorded as a persisted segment (`1539`); a new empty writing segment Y is installed (`1527-1531`, `1542-1543`); and the version is **applied and flushed** (`1546-1549`), which writes `manifest.N+1` and deletes `manifest.N` (`version_manager.cc:282-301`). The WAL file still exists at `<path>/<X>/<block>.wal`, but replay at the next open is conditional on a writing forward block in the meta (`segment.cc:490-501`) — the committed manifest no longer contains one, so the WAL is orphaned.
4. **Optimize proper:** `persist_segments = [X]` (`collection.cc:802-803`); `build_compact_task` with a single group and no deletes (`rebuild=false`, `collection.cc:927-935`) produces a `CreateVectorIndexTask` (`991-1002`), which routes to `create_all_vector_index` (`segment_helper.cc:1113-1125`, `segment.cc:1617-1640`). With the default index (`FlatIndexParams`, `src/include/zvec/db/index_params.h:437`, marked indexed at segment creation, `segment.cc:534-539`), `create_vector_index` takes the "already indexed with same params" skip (`segment.cc:1685-1690`) — **no data is rewritten anywhere**. The output meta is committed (`collection.cc:863-877`) and `reload_vector_index` swaps it in (`905-908`, `segment.cc:1882-1940`). `Optimize` returns OK (`914`).
5. **Close cannot rescue it:** `close_unsafe` flushes only the *current* writing segment Y (`collection.cc:340-349`, `389-395`), and X's destructor `close()`→`flush()` hits the same null-WAL guard (`segment.cc:112-117`, `551-552`, `2220`).
6. **Next open (process C):** the manifest lists X as a persisted segment with **zero persisted SCALAR blocks and no writing block**, so `Segment::Open` skips `recover()`, `SegmentMeta::doc_count()` (persisted SCALAR blocks + writing block, `meta.h:302-312`) is 0, and the docs are gone. X's directory is not even deleted (cleanup only runs for `destroy()`-marked segments, `segment.cc:2326-2338`), so the WAL sits there unread.

The control case works because in-process insertion opened `wal_file_`; step 2's `flush()` then runs the full ordering — memory store to file, `finish_memory_components` adds persisted blocks to the meta, version flush, and only then WAL removal (`segment.cc:2224-2315`) — so the manifest commit in step 3 describes data that genuinely exists on disk.

A secondary variant, established from source: if multiple persisted segments existed, Optimize would build a `CompactTask`; its scalar reduce reads `segment->scan()`, which *does* include `memory_store_` (`segment_helper.cc:232-282`), so forward rows would survive — but the vector merge collects indexers via `get_vector_indexer`, which returns only the *persisted* `vector_indexers_` map, never `memory_vector_indexers_` (`segment.cc:1586-1593`; `segment_helper.cc:656-674`). So a recovered-only segment's vectors would be silently dropped even on that path.

## 3. Why success + same-handle statistics do not establish durability

- **Every status is genuinely OK.** The no-op `flush()` is not an error — it is indistinguishable from "segment already clean." The manifest writes succeed. The defect is that the committed manifest *misdescribes* X as fully persisted (persisted blocks: none; writing block: removed) while X's rows exist only in process B's heap and in an orphaned WAL file.
- **`Stats()` never consults disk.** It sums `SegmentImpl::doc_count()` over the live segment objects (`collection.cc:403-442`, `2076-2086`), i.e. `doc_ids_.size()` in RAM (`segment.cc:589-600`); `index_completeness` reads `meta()->vector_indexed(...)`, and FLAT was pre-marked indexed (`segment.cc:534-539`), so it reports 1.0. Fetch/scan similarly read `memory_store_` (`segment.cc:2531-2532`, `2755`, `2825-2841`). The same-handle view is therefore healthy by construction, independent of what the manifest says.
- **The durability contract lives in the flush ordering**, which the healthy path obeys: persist blocks → commit a version referencing them → only then remove the WAL (`segment.cc:2288-2315`). Durability can only be observed by re-reading through that contract (reopen in a fresh process, which loads the manifest and replays WALs only for metas that still carry a writing block, `segment.cc:484-501`). Optimize inverted the contract: it removed the WAL reference from the committed version without ever persisting the blocks.

## 4. Smallest repair principle and a regression test (described, not implemented)

**Repair principle:** *WAL replay must re-establish exactly the state an ordinary insert would have — a WAL-backed, dirty writing segment — and a segment's writing block (the WAL pointer) may be removed from a committed version only after the replayed rows exist in persisted blocks.*

Smallest concrete repair, reusing the existing lifecycle unchanged: in `SegmentImpl`'s recovery branch (`Open` → after `recover()` replayed ≥1 record, `segment.cc:499-501`/`4193-4301`), open the member `wal_file_` on the same WAL path — `open_wal_file()` already does exactly this (opens the existing file for append, `segment.cc:4303-4322`). Then the existing `flush()` gate at `segment.cc:2220` passes (`has_record()` is size-based, `local_wal_file.h:75-77`), and Optimize's `dump()` persists the memory store, records persisted blocks in the meta, commits the version, and only then removes the WAL — the identical ordering the control path uses. Crash-before-that-point remains safe because the WAL is untouched. An equally small alternative is to change the guard to test actual in-memory dirt (e.g. `memory_store_ && memory_store_->num_rows() > 0`, or a `recovered_dirty_` flag) instead of the WAL handle; re-attaching the WAL handle is preferable because it also preserves flush()'s WAL-removal step. Optional defense-in-depth: `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`) should refuse to `remove_writing_forward_block()` + commit unless the dumped meta's persisted SCALAR blocks cover the segment's `doc_count()`.

**Regression test sequence** (fits the existing `tests/db/crash_recovery` harness, which already fork/execs helper binaries and SIGKILLs them — `write_recovery_test.cc:58-130`, `optimize_recovery_test.cc:53-130`):

1. **Writer process:** `CreateAndOpen`; insert N docs (small N so no buffer/segment rollover); terminate via `_exit`/SIGKILL with **no** `Flush()`/`Close()`. (The current `data_generator.cc` flushes before exiting, `data_generator.cc:245-247`, so a no-flush variant is needed.)
2. **Optimizer process:** `Collection::Open` (triggers WAL recovery); assert `Stats().doc_count == N`; call `Optimize()` and assert OK; then SIGKILL this process too (so a destructor-time flush can't mask the bug).
3. **Verifier process:** `Collection::Open` again; assert `Stats().doc_count == N`; fetch each pk; issue a vector query and assert N results / `index_completeness == 1`.

Useful variants: (a) control — same sequence with `Flush()` before the crash (passes today and must keep passing); (b) one extra insert after recovery before `Optimize` (passes today via lazy `append_wal` open — guards against regressing that); (c) multiple persisted segments so the `CompactTask` path runs, checking vector recall after reopen (would also catch the `get_vector_indexer` memory-indexer gap, `segment.cc:1586-1593`); (d) a non-FLAT (e.g. HNSW) schema. The existing tests cover crash-*during*-optimize and crash-during-insert-then-reopen (`optimize_recovery_test.cc:144-175`, `write_recovery_test.cc:164-219`) but none covers crash-before-flush → recover → clean `Optimize` → reopen, which is precisely the failing sequence.

**Established from source vs. requiring execution.** Everything above — the null `wal_file_` after replay, the `flush()` early-return, the manifest commit removing the writing block, the FLAT skip in `CreateVectorIndexTask`, the in-memory-only reads behind `Stats`/fetch, and the coverage gap in the existing tests — is established by reading the frozen tree. I did not build or run anything, so the end-to-end loss (doc_count 0 at step 3) is a source-derived prediction, not an observed repro; confirming it, and corner details such as whether `ChunkedFileWriter::Open` leaves an empty block file on disk or how FTS/inverted-index side files behave across the sequence, would require executing the described test.
