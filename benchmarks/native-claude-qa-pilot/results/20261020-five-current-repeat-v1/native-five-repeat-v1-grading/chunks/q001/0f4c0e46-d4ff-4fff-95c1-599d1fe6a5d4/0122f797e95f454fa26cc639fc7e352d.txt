# Root-cause analysis: crash-recovered documents silently dropped by `Optimize()`

All statements below are derived from reading the frozen tree; I did not build or run anything. Paths are repo-relative; the short names `collection.cc` = `src/db/collection.cc`, `segment.cc` = `src/db/index/segment/segment.cc`.

**Summary.** WAL recovery replays documents into memory through a *local* WAL handle and never re-attaches the segment's member `wal_file_`. `SegmentImpl::flush()` uses "`wal_file_` is null or has no records" as its *nothing-to-persist* predicate (`segment.cc:2220`), so after recovery-without-new-writes every flush/dump is a silent no-op. `Optimize()` then promotes the recovered writing segment to a "persisted" segment and commits a new manifest that no longer references the old WAL — orphaning the only on-disk copy of the data while the same in-memory `Segment` object keeps serving reads on the live handle.

---

## 1. State difference: recovery path vs. ordinary insertion path

**Ordinary insertion path.** `SegmentImpl::Insert/Upsert/Update/Delete` (`segment.cc:903–989`) call `append_wal(doc)` *before* mutating memory. `append_wal` (`segment.cc:4324–4340`) lazily attaches the member handle `wal_file_` (declared `segment.cc:400–401`) via `open_wal_file()` (`segment.cc:4303–4322`), then appends the record. The invariant maintained is: **memory holds unpersisted docs ⇒ member `wal_file_` is attached and its file contains those records** (`has_record()` = `file_.size() > sizeof(header_)`, `src/db/index/storage/wal/local_wal_file.h:75–77`).

**Recovery path.** On reopen, `CollectionImpl::recovery()` (`collection.cc:1836–1892`) opens the writing segment from the manifest's `writing_segment_meta` (`collection.cc:1880–1887`); `SegmentImpl::Open` calls `recover()` because a `writing_forward_block` exists (`segment.cc:484–501`). `SegmentImpl::recover()` (`segment.cc:4193–4301`):

- opens the WAL file `<collection>/<seg_id>/<block_id>.wal` (`segment.cc:4198–4199`; layout in `src/db/common/file_helper.h:74–78`) into a **local** `recover_wal_file` (`segment.cc:4206–4214`),
- replays each record by calling `internal_insert/internal_update/internal_upsert/internal_delete` **directly** (`segment.cc:4249–4272`) — these never call `append_wal`,
- closes the local handle on scope exit (`AILEGO_DEFER`, `segment.cc:4215`).

The member `wal_file_` therefore stays `nullptr`, while all other state is rebuilt **in memory only**: `doc_ids_.push_back` (`segment.cc:878`), idmap `upsert` (`segment.cc:853`), `memory_store_` insert (`segment.cc:857`, components created by `init_memory_components`, `segment.cc:4119–4191`), memory vector indexers, and `mem_block.max_doc_id_ += added_docs` (`segment.cc:4285–4288`).

**Why the recovered data is initially readable.** Every read path consults those in-memory structures: `doc_count()` is `doc_ids_.size()` (`segment.cc:589–600`); `Fetch` resolves pk→doc_id through the IDMap RocksDB (memtable reads, `src/db/index/common/id_map.cc:120–134`) and then reads `memory_store_`; vector search uses `get_combined_vector_indexer`, which appends `memory_vector_indexers_` (`segment.cc:1510–1531`); `scan()` unions persisted stores with `memory_store_` (`segment.cc:2825–2841`). Crucially, at this point the on-disk WAL is still intact and still referenced by the manifest's writing-segment meta, so a *plain* reopen would simply replay it again — nothing is lost yet.

## 2. The exact sequence that lets `Optimize()` succeed while orphaning the data

1. `CollectionImpl::Optimize` (`collection.cc:779–915`): `writing_segment_->doc_count() != 0` is true (recovered docs in `doc_ids_`) → `switch_to_new_segment_for_writing()` (`collection.cc:794–800`, body `1517–1552`).
2. `switch_to_new_segment_for_writing` first calls `writing_segment_->dump()` (`collection.cc:1519`). `SegmentImpl::dump()` (`segment.cc:2197–2215`) calls `flush()` — and here is the **exact condition**:

   ```cpp
   // segment.cc:2220–2222
   if (wal_file_ == nullptr || !wal_file_->has_record()) {
     return Status::OK();
   }
   ```

   After recovery `wal_file_ == nullptr`, so `flush()` returns OK having done nothing: no `memory_store_->flush()` (`segment.cc:2233–2236`), no `finish_memory_components()` — the *only* place the memory forward block is closed, its file materialized, and a persisted `BlockMeta` added (`segment.cc:2288–2298`, `4342–4412`) — no `update_version()` (`segment.cc:2301`, `4414–4426`), and no WAL removal (`segment.cc:2305–2315`). `dump()` then merely seals indexers and sets `sealed_ = true`, still returning OK.
3. The same in-memory `Segment` object is registered as a persisted segment (`collection.cc:1522`), its writing block is stripped from its meta (`remove_writing_forward_block()`, `collection.cc:1538`), that meta is added to a new version (`1539`), a **new empty writing segment with a fresh segment id and fresh WAL path** is created (`1527–1531`, `1542–1544`), and `version_manager_->apply()` + `flush()` (`1546–1549`) writes a new manifest file **and deletes the previous one** (`src/db/index/common/version_manager.cc:282–301`). This commit is the point of no return: WAL replay happens only when a segment meta carries a `writing_forward_block` (`segment.cc:484–501`), and no manifest entry references `<old_seg>/<block>.wal` anymore. The WAL file is orphaned (its bytes may even remain on disk, since only `CompactTask` inputs get `destroy_segment`/`cleanup`, `collection.cc:898–901`, `segment.cc:2334–2338`).
4. The rest of `Optimize` also succeeds honestly-looking: with one persisted segment, `build_compact_task` emits a single `CreateVectorIndexTask` (`collection.cc:991–1002`). With default params (`DefaultVectorIndexParams` is **FLAT**, `src/include/zvec/db/index_params.h:437`; FLAT fields are marked indexed at segment `Create`, `segment.cc:534–539`), `create_vector_index` early-returns OK (`segment.cc:1685–1690`). Even for non-FLAT params it would "succeed" while writing an **empty** index: `merge_vector_indexer` merges only `vector_indexers_[column]` (persisted indexers — empty here, since the data lives in `memory_vector_indexers_`; `get_vector_indexer` likewise returns only persisted ones, `segment.cc:1586–1593`), yet stamps the block meta with `doc_ids_.front()/back()/size()` (`segment.cc:1642–1668`, `1719–1727`). Final `apply` + `flush` of the manifest (`collection.cc:872–877`) → `Optimize` returns OK.
5. **Third open:** `VersionManager::Recovery` picks the newest manifest (`version_manager.cc:190–241`). The ex-recovered segment opens with **zero SCALAR blocks**, so `load_persist_scalar_blocks` leaves `doc_ids_` empty (`segment.cc:3913–3960`) and `doc_count()` is 0; the new writing segment finds no WAL ("WAL recovery skipped", `segment.cc:4200–4204`). The documents are gone. (Fetch fails either way: pk absent from the on-disk IDMap → `collection.cc:1769–1774`, or — if process 2's clean exit flushed the RocksDB memtable, since IDMap Puts use `disableWAL = true` (`src/db/common/rocksdb_context.cc:93`) but `close()` flushes (`rocksdb_context.cc:309–324`) — pk maps to a doc_id no segment range covers, `collection.cc:1780–1785`, `2054–2074`, because meta min/max doc id derive from SCALAR blocks, `src/db/index/common/meta.h:277–300`.)

**Why the control doesn't lose data.** Without the crash, the member `wal_file_` is attached and `has_record()` is true, so `dump()`→`flush()` runs the full path: memory store flushed, `finish_memory_components()` adds the persisted forward block to the meta, version updated and manifest flushed, and only *then* is the WAL removed (`segment.cc:2233–2315`).

**Why the "small collection" assumption matters.** (a) A buffer rollover during replay (`ready_for_dump_block()` → `flush()` inside `internal_insert`, `segment.cc:837–844`, `2959–2962`) would hit the same no-op, so the scenario is cleanest without it; (b) had there been enough persisted segments to trigger a real `CompactTask`, `ReduceScalar` scans via `scan()`, which *includes* `memory_store_` (`segment_helper.cc:232–282`; `segment.cc:2825–2841`), and the forward data would accidentally be re-persisted. The loss is specific to the no-op-flush + manifest-orphaning path.

## 3. Why "success" and same-handle stats prove nothing here

- **Every step legitimately returns OK.** The no-op `flush()` returns OK by design (`segment.cc:2220–2222`); `dump()` returns OK; manifest `apply/flush` succeed; the index task succeeds. Nothing asserts the invariant "a segment listed in `persisted_segment_metas` has ≥1 persisted block / its counted docs exist in a file."
- **Same-handle reads never touch the committed disk state.** `Stats()` sums `segment->doc_count(...)` over `get_all_segments()` (`collection.cc:403–442`, `2076–2086`), which is the *same in-memory Segment object* that `switch_to_new_segment_for_writing` moved into `segment_manager_` — its `doc_ids_`, `memory_store_`, and `memory_vector_indexers_` are untouched (`dump()` doesn't clear memory; `sealed_` only blocks re-dump). So healthy stats, counts, fetches, and queries on the live handle are fully consistent with an empty on-disk representation. Durability here means "manifest + block files + WAL are self-consistent for the *next* open," and only a reopen (or inspecting persisted metas) observes that.
- Note also that an explicit `Collection::Flush()` after recovery is the same silent no-op (`collection.cc:380–395` → `segment.cc:2220`) — benign by itself (the WAL stays referenced, so a reopen still recovers), which underlines that OK returns carry no persistence semantics in this state. The destructive step is any operation that commits a manifest orphaning the WAL: `Optimize`, and equally `CreateIndex`/`DropIndex`/`AddColumn`/`DropColumn`/`AlterColumn`, which all funnel through `switch_to_new_segment_for_writing` when the writing segment is non-empty (`collection.cc:501–504`, `674–677`, `1154–1157`, `1226–1229`, `1310–1313`).

## 4. Smallest repair principle and a regression test (described, not implemented)

**Repair principle.** *Recovery must re-establish the write path's core invariant: a writing segment holding unpersisted documents has its WAL handle attached, with the records in the file.* The minimal change is at the end of `SegmentImpl::recover()` (`segment.cc:4193–4301`): instead of leaving `wal_file_` null, attach the member handle by calling `open_wal_file()` — which already handles the "file exists" case (`create_new = false`, `segment.cc:4308–4312`) and positions at end-of-file for appending (`local_wal_file.cc:92–106`). Then the guard at `segment.cc:2220` sees `has_record() == true`, `Optimize`'s `dump()` materializes the recovered block *before* the manifest switch, and the WAL is removed only after the persisted block and new manifest are on disk (`segment.cc:2305–2315`). This matches what already happens today if a single new insert arrives after recovery (`append_wal` attaches the same existing file) — the fix just makes recovery itself honor the invariant.

Equivalent alternatives, slightly larger: (a) change `flush()`'s dirtiness predicate to consult actual memory state (e.g., `memory_store_ && num_rows() > 0`, or writing-block `doc_count_ > 0`) rather than the WAL handle; (b) run one full `flush()` immediately after replay in `Open` (materialize-at-recovery; costs eager I/O). A cheap defensive assertion complements any of these: in `switch_to_new_segment_for_writing`, after `dump()`, require the segment's meta to actually carry a persisted SCALAR block (or the segment to be genuinely empty) and fail with `InternalError` before committing the manifest — converting silent loss into a failed call.

**Regression test.** The repo already has the right harness (`tests/db/crash_recovery/`: fork + `SIGKILL` of child binaries, e.g. `ExecuteOptimizer` in `optimize_recovery_test.cc:51–118`). The missing sequence is:

1. **Process A:** create collection, insert N docs (single writing segment, no flush), `SIGKILL` before exit.
2. **Process B:** open (WAL replay); assert `Stats().doc_count == N` and `Fetch` of every pk — passes today.
3. **Process B:** call `Optimize()` **with zero intervening inserts**; assert OK; exit cleanly.
4. **Fresh open:** assert `Stats().doc_count == N`, every `Fetch(pk_i)` returns the exact doc, and a vector query returns expected hits. **This is the detector** — on current code it fails (count 0, fetches null).

Variants worth adding: step 3 = explicit `Flush()` instead of `Optimize()` (passes today since the WAL isn't orphaned — guards against over-fixing); step 3 = `CreateIndex` (same switch path, should fail pre-fix); a control without the crash (insert → optimize → reopen); and optionally a manifest-level invariant check after step 3 (every persisted segment meta has ≥1 SCALAR block, doc_counts sum to N, and no `.wal` exists that isn't referenced by a `writing_forward_block`). Note why existing tests miss this: `CrashDuringOptimize` (`optimize_recovery_test.cc:145–262`) crashes *during* optimize and, after the recovery open, **inserts 500 more batches before the next optimize** (`:207–221`) — the first insert re-attaches the member WAL and masks the bug.

**Source-established vs. execution-dependent.** The entire mechanism — null `wal_file_` after replay, the `segment.cc:2220` guard, the manifest commit orphaning the WAL, empty `doc_ids_` on the third open — is directly readable from the code and I'm confident in it. The end-to-end symptom was *derived*, not executed; I ran no reproduction. Two details a test would pin down rather than assume: whether the IDMap's RocksDB memtable flush at process-B close (`rocksdb_context.cc:309–324`) leaves stale pk→doc_id entries (shifting Fetch's failure mode from "pk not found" to "segment not found"), and the non-FLAT variant where Optimize additionally writes an empty vector-index file and marks the field indexed (`segment.cc:1719–1727`).
