## Summary of the mechanism

The writing segment's durability lifecycle is: every write appends to a per-segment WAL (`append_wal`), and `flush()` converts the in-memory block into registered persisted blocks, commits a new manifest, and only then removes the WAL. After a crash, `recover()` replays the WAL **into memory only** and leaves the member WAL handle `wal_file_` null. `flush()` treats a null WAL handle as "nothing to flush" and silently returns OK — so when `Optimize()` rotates the writing segment into a persisted segment, it commits a manifest describing that segment as fully persisted (writing block removed, zero data blocks) while the replayed rows were never written to any block file and the WAL is orphaned. Everything below is established by reading the frozen tree; I did not run a reproduction.

## 1. State difference: recovery path vs ordinary insertion path

**Ordinary insertion (no crash):** `CollectionImpl::write_impl` → `Segment::Insert` (`src/db/collection.cc:1364-1470`, `src/db/index/segment/segment.cc:903-918`). `Insert` calls `append_wal(doc)` first, which lazily creates the member `wal_file_` (`segment.cc:4324-4340`), then `internal_insert` populates the in-memory structures (`segment.cc:837-881`). So the segment ends up with: in-memory rows **plus** a non-null `wal_file_` whose file contains records (`has_record()` is size-based: `file_.size() > sizeof(header_)`, `src/db/index/storage/wal/local_wal_file.h:75-77`).

**Recovery path:** `CollectionImpl::recovery()` (`collection.cc:1836-1892`) loads the manifest, reopens persisted segments read-only, and reopens the writing segment via `Segment::Open` with the version's writing-segment meta (`collection.cc:1879-1887`). `SegmentImpl::Open` sees a writing forward block in the meta and calls `recover()` (`segment.cc:484-501`). `recover()` (`segment.cc:4193-4301`):

- opens the WAL through a **local** handle `recover_wal_file` (`create_new = false`, lines 4206-4215) and closes it on scope exit (`AILEGO_DEFER`, line 4215);
- replays each record via `internal_insert`/`internal_update`/`internal_upsert`/`internal_delete` (lines 4249-4272);
- **never assigns the member `wal_file_`** (declared at `segment.cc:401`) — neither `recover()` nor `Segment::Open` calls `open_wal_file()`; only a subsequent *new* write's `append_wal` would.

So the distinguishing internal state is: **rows are in memory exactly as after live inserts, but `wal_file_ == nullptr` even though a record-bearing WAL file exists on disk.**

**Why the data is initially readable:** replay rebuilds every in-memory structure reads consult — `doc_ids_` and the mem-block `doc_count_`/`max_doc_id_` (`segment.cc:874-878`, `4285-4288`), `id_map_->upsert` (line 853), `memory_store_->insert` (line 857), and the memory vector indexers (line 869). `Stats()` sums `SegmentImpl::doc_count()`, which is just `doc_ids_.size()` (`segment.cc:589-600`, `collection.cc:403-442`); `Fetch` resolves pk→doc_id via the in-memory id_map and reads `memory_store_` (the meta still has its writing block at this point, so the memory-store branches at `segment.cc:2484-2497` and `2744-2757` are live). All reads are satisfied from RAM plus the still-intact WAL file; nothing needs the manifest to describe the rows yet.

## 2. Call sequence and exact condition for the silent loss

Process 2 calls `Optimize()` with no intervening inserts (`collection.cc:779-915`):

1. `writing_segment_->doc_count() != 0` is **true** (in-memory count from replay), so Optimize calls `switch_to_new_segment_for_writing()` (`collection.cc:794-800`).
2. `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`) first calls `writing_segment_->dump()` (line 1519). `dump()` calls `flush()` (`segment.cc:2197-2215`).
3. **The exact failure condition** — `flush()`'s guard at `segment.cc:2220-2222`:
   ```cpp
   if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();
   ```
   `wal_file_` is null (state difference #1), so `flush()` is a silent no-op that returns success. Skipped: `memory_store_->flush()` (2233-2236), `finish_memory_components()` (2290; defined 4342-4412) which is the *only* thing that turns the memory block into `add_persisted_block(...)` entries in the meta, `update_version()` (2301; 4414-4426), and the WAL removal (2304-2315). `dump()` then just seals the scalar/FTS indexers and returns OK (`segment.cc:2204-2214`).
4. `switch_to_new_segment_for_writing` proceeds unconditionally: it adds the old segment to `segment_manager_` (1522), creates a new empty writing segment (1527-1531), calls `remove_writing_forward_block()` on the old segment's meta (1538), registers it via `version.add_persisted_segment_meta(...)` (1539), and **persists that version**: `version_manager_->apply()` + `flush()` (1546-1549). `VersionManager::flush()` writes a new `MANIFEST.N` file and deletes the previous one (`src/db/index/common/version_manager.cc:282-301`). From this instant the on-disk truth says: segment S is a persisted segment with **no writing block and no SCALAR data blocks**; the writing segment is a fresh empty one. S's WAL file still exists (path keyed by segment id + mem-block id, `MakeWalPath`, `src/db/common/file_helper.h:74`) but is now unreferenced.
5. Optimize continues and still succeeds. `get_all_persist_segments()` returns `[S]` (`collection.cc:802-803`, `2084-2086`); with a single segment and no significant deletes, `build_compact_task` produces a `CreateVectorIndexTask` (`collection.cc:991-1001`). For the default schema, vector fields get `DefaultVectorIndexParams`, which is **FLAT** (`src/include/zvec/db/index_params.h:437`), and FLAT fields are marked `indexed_vector_fields` at segment creation (`segment.cc:534-539`). So `create_vector_index` hits the early return "already indexed with same params" (`segment.cc:1685-1690`) via `create_all_vector_index` (`segment.cc:1617-1640`) — the task succeeds **without reading or writing any forward data**; its output meta is a copy of S's meta with the writing block removed (1624-1625). Optimize commits it (`update_persisted_segment_meta`, apply, flush — `collection.cc:863-877`) and returns `Status::OK()` (914).
6. Process 2's exit saves nothing either: `close_unsafe` → `flush_unsafe` flushes only the *new, empty* writing segment (no-op, null WAL) (`collection.cc:340-361`, `389-395`); the old segment's destructor `close()` → `flush()` hits the same null-WAL no-op (`segment.cc:551-552`).

**Process 3 reopen:** `recovery()` opens S from the manifest as a persisted, read-only segment (`collection.cc:1861-1874`). In `SegmentImpl::Open`, `writing_forward_block()` is empty, so the `recover()`/WAL-replay branch is **not taken** (`segment.cc:484-510`), and `load_persist_scalar_blocks()` finds no SCALAR blocks, leaving `doc_ids_` empty (`segment.cc:3913-3960`). The new writing segment's `recover()` finds no WAL file and skips (`segment.cc:4198-4204`). The recovered documents are gone — even though S's old WAL file is likely still sitting on disk, orphaned (and it would be physically deleted later if S is ever compacted: `destroy_segment` → `destroy()` → destructor `cleanup()` removes the whole segment directory, `segment_manager.cc:45-56`, `segment.cc:2326-2338`).

**Why the control doesn't lose data:** with inserts performed in-process, `wal_file_` is non-null and `has_record()` true, so step 3's `flush()` runs the full lifecycle in the correct order — write block data (`memory_store_->flush()`, `finish_memory_components()` registers persisted blocks in the meta), commit the version (`update_version()`), and only then remove the WAL (`segment.cc:2217-2324`). By the time `switch_to_new_segment_for_writing` commits S as a persisted segment, the manifest references real block files.

## 3. Why "success" and same-handle statistics prove nothing here

- `Optimize()`'s `Status::OK()` only means each step returned OK. The load-bearing step (`dump()`→`flush()`) returns OK on the no-op path (`segment.cc:2220-2222`); there is no distinction in the return value between "persisted N docs into blocks and committed" and "did nothing." The destructive manifest commit happens inside `switch_to_new_segment_for_writing` (`collection.cc:1546-1549`) *before* any compaction work, so even a later task failure would not undo it.
- `Stats()` on the same handle is computed from live in-memory objects: `doc_count` sums `doc_ids_.size()` (`collection.cc:421-423`, `segment.cc:589-600`), and for FLAT fields `index_completeness` reads `meta()->vector_indexed(...)` (`collection.cc:431-438`), which the optimize output meta happily sets (`segment.cc:1636`). No read path consults the manifest or block files. (If anything, the same handle is *more* broken than the stats suggest: `remove_writing_forward_block()` mutates the shared meta in place, so the memory-store fetch guards at `segment.cc:2484`/`2744` no longer fire for S after the switch.)
- In this design, durability means: the committed manifest references persisted block files that contain the rows, and the WAL is removed only after that commit. The only way to observe that invariant is a fresh `Collection::Open` (or direct inspection of the manifest and segment directory) — which is exactly where the loss shows up.

## 4. Smallest repair principle and a regression test

**Repair principle (describe only):** make recovery leave the segment's WAL state consistent with on-disk reality, so the existing flush lifecycle runs. Concretely, the minimal change is at the end of `SegmentImpl::recover()` (or in `Open` when a writing block exists, `segment.cc:484-501`): call `open_wal_file()` (which reopens the existing WAL for append when present, `segment.cc:4303-4322`) so `wal_file_` is non-null and `has_record()` is true after replay. Then `dump()`→`flush()` inside `switch_to_new_segment_for_writing` performs the real work — persist memory block → register persisted blocks in the meta → commit version → remove WAL — *before* the meta is committed as a persisted segment, restoring the invariant "a writing segment becomes a persisted segment only after its writing block has actually been converted into persisted blocks." A defensive complement (not the minimal fix) would be for `flush()`/`dump()` to signal "nothing was flushed" and for the switch to refuse, or force-persist, when the meta still shows unflushed rows.

**Regression-test sequence:** the harness already exists in `tests/db/crash_recovery/` (SIGKILL'd child `data_generator`, and `collection_optimizer.cc` which does Open→Optimize→Flush). The current `optimize_recovery_test.cc` misses this bug because after reopening it **inserts more documents** (reopening the WAL via `append_wal`, which masks the null-handle state) and cleanly closes the collection before running the optimizer child. The detecting sequence is:

1. Process A: create collection, insert N docs (small enough to avoid buffer/segment rollover), `SIGKILL` before any `Flush`/clean close (as in `write_recovery_test.cc`).
2. Process B: `Collection::Open`; assert `Stats().doc_count == N` and spot-check `Fetch`; then call `Optimize()` **without inserting anything**; assert OK.
3. Close B cleanly; Process C: `Collection::Open` again; assert `doc_count == N`, `Fetch` every pk and compare field-for-field, and a vector `Query` returns the expected topk.
4. Variants: (a) one doc inserted between steps 2's open and Optimize (passes before and after the fix — documents why the old test missed it); (b) a non-default (e.g., HNSW) vector index; (c) Optimize twice in process B.

On the current source, step 3 should fail with `doc_count == 0`; after the repair it should pass.

## What is source-established vs. what needs execution

- **Established from source:** the entire causal chain — null `wal_file_` after replay (`segment.cc:4193-4301`, `4324-4340`), the no-op `flush()` guard (`2220-2222`), the unconditional meta/version commit in `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`), manifest persistence (`version_manager.cc:282-301`), the FLAT-default trivial success of the vector-index task (`index_params.h:437`, `segment.cc:534-539`, `1685-1690`), and the reopen path that skips WAL replay without a writing block and rebuilds `doc_ids_` only from SCALAR blocks (`segment.cc:484-510`, `3913-3960`).
- **Would require executing a test:** end-to-end confirmation (process 3 observing 0 docs); whether process A's WAL bytes reliably reach disk under SIGKILL without an explicit flush (depends on `ailego::File` buffering — the scenario stipulates recovery works, and `write_recovery_test.cc` implies it); and whether a non-FLAT (HNSW) configuration also returns OK from Optimize in this state — `merge_vector_indexer` would be invoked with an empty `vector_indexers_[column]` (`segment.cc:1642-1668`), and `VectorColumnIndexer::Merge`'s behavior on empty input is not something I verified. The FLAT-default path is the confirmed success route. I did not run any reproduction; this was a read-only analysis.
