All the causal links are now verified in source. Here is the analysis.

# Root cause: WAL-replay recovery leaves `wal_file_ == nullptr`, so the next `flush()`/`dump()` is a silent no-op — and `Optimize()` then rewrites the manifest past the un-persisted data

## 0. What the crash leaves on disk (baseline)

A writer that inserts and is killed before any flush leaves: the manifest from `create()` (writing segment 0 with an empty mem-block meta), the segment WAL `<path>/0/<block_id>.wal` (records are written into the file on every `append`, `src/db/index/storage/wal/local_wal_file.cc:29-50,161-195`), **no** forward-block files, and an idmap RocksDB whose memtable died with the process (`write_opts_.disableWAL = true`, `src/db/common/rocksdb_context.cc:93,199`). Durability of the inserted docs exists *only* as the WAL file plus the manifest's writing-segment meta that points at it.

## 1. Recovery path vs. ordinary insertion path

**Ordinary insert** — `SegmentImpl::Insert` (`src/db/index/segment/segment.cc:903-918`) calls `append_wal(doc)`, which lazily opens the member `wal_file_` via `open_wal_file()` (`segment.cc:4303-4322, 4324-4340`), then `internal_insert` (`segment.cc:837-881`) populates `memory_store_`, `id_map_`, in-memory indexers, `doc_ids_`, and the mem-block meta. The invariant the persistence code relies on is: **`wal_file_ != nullptr && has_record()` ⇔ the segment holds un-persisted data** (`has_record()` = file bigger than header, `src/db/index/storage/wal/local_wal_file.h:75-77`).

**Recovery** — `CollectionImpl::recovery()` (`src/db/collection.cc:1836-1892`) opens the writing segment via `Segment::Open` → `SegmentImpl::Open` (`segment.cc:461-517`), which calls `recover()` (`segment.cc:4193-4301`). `recover()` opens the WAL into a **local** `recover_wal_file`, replays each record by calling `internal_insert/internal_upsert/internal_update/internal_delete` directly (lines 4250-4272 — deliberately bypassing `append_wal` so records aren't duplicated), then closes and discards that handle (`AILEGO_DEFER`, line 4215). **It never assigns the member `wal_file_`** — that only ever happens inside `append_wal`. So after recovery the segment's RAM state is fully populated but the dirty-state flag the flush guard consults (`wal_file_`) says "clean."

**Why the data is readable in process 2** — every read path is memory-first on the same handle: `get_all_segments()` includes the writing segment whenever `doc_count() > 0` (`collection.cc:2076-2082`); `doc_count()` is `doc_ids_.size()` (`segment.cc:589-599`); `Fetch` resolves pk→doc_id through `id_map_` (RocksDB `Get` sees the memtable entries the replay re-`Put`, `src/db/index/common/id_map.cc:97-134`) and reads `memory_store_`. Meanwhile the data is *still* durable across reopens the old way: the on-disk WAL is intact and the manifest still names segment 0's writing block, so any reopen replays it again (`recover()` computes the WAL path from the writing segment's own meta, `segment.cc:4198-4199`).

## 2. The sequence that lets `optimize()` succeed while dropping the data

In process 2, `CollectionImpl::Optimize` (`src/db/collection.cc:779-915`):

1. `writing_segment_->doc_count() != 0` (recovered docs in RAM) → `switch_to_new_segment_for_writing()` (`collection.cc:1517-1552`), line 794-799.
2. `writing_segment_->dump()` (`segment.cc:2197-2215`) → `flush()` (`segment.cc:2217-2324`) → **the exact enabling condition, `segment.cc:2220-2222`:**
   ```cpp
   if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();
   ```
   `wal_file_` is nullptr (recovery never opened it, no new writes happened), so `flush()` returns OK having done **nothing**: no `memory_store_->flush()`, no `finish_memory_components()` (the only code that writes the forward-block file and appends the `SCALAR` `BlockMeta` to `persisted_blocks_`, `segment.cc:4342-4368`), no `update_version()` (`segment.cc:4414-4426`), and no WAL removal (`segment.cc:2304-2315` — unreachable). `dump()` proceeds to seal indexers and return OK.
3. `switch_to_new_segment_for_writing` then treats the segment as safely persisted: adds it to `segment_manager_`, **`writing_segment_meta->remove_writing_forward_block()`** (`collection.cc:1538`; `meta.h:263-265` — just nulls the optional, it does *not* convert the block to a persisted block), commits it via `add_persisted_segment_meta`, creates a fresh empty writing segment (id 1), and `version_manager_->apply()` + `flush()` (`collection.cc:1536-1549`). `VersionManager::flush()` writes a new manifest file and **deletes the previous one** (`src/db/index/common/version_manager.cc:282-301`). This destroys the only metadata pointer (segment id + mem-block id) by which reopen could find the WAL. The WAL file itself is now an orphan on disk — still present, never referenced again.
4. Compaction planning: one small persisted segment, no deletes → `rebuild=false` → the tail branch of `build_compact_task` creates a single `CreateVectorIndexTask`, **not** a `CompactTask` (`collection.cc:991-1002`). This matters: a real `CompactTask` would read inputs through `scan()`, which *includes* `memory_store_` (`segment.cc:2825-2841`; `segment_helper.cc:232-236`), and would incidentally rescue the data into a new persisted forward file. `CreateVectorIndexTask` never rewrites forward data — and with the default schema (`DefaultVectorIndexParams` = `FlatIndexParams(IP)`, `src/include/zvec/db/index_params.h:437`; FLAT fields are marked indexed at segment creation, `segment.cc:534-539`) `create_vector_index` early-returns OK at `segment.cc:1685-1690`, with output meta = a copy of the input meta minus the writing block (`segment.cc:1624-1625, 1679-1683`).
5. Optimize commits that meta (`update_persisted_segment_meta`), `apply()`s and `flush()`es the manifest again (`collection.cc:863-877`), reloads indexers, and returns `Status::OK()` (line 914). Every step legitimately succeeded; no step ever verified the docs reached a forward-block file.

On the **third open**: `VersionManager::Recovery` loads the newest manifest (`version_manager.cc:190-241`). Persisted segment 0 now has no writing block, so `SegmentImpl::Open` skips `recover()` entirely (`segment.cc:484-510` — WAL replay happens *only* for the current writing segment); `load_persist_scalar_blocks` finds zero `SCALAR` blocks, so `doc_ids_` is empty (`segment.cc:3913-3960`). The writing segment is the fresh, empty segment 1. Result: 0 documents. (The idmap actually still maps pk→doc_id — `RocksdbContext::close()` flushes the memtable, `rocksdb_context.cc:309-324` — but no segment covers those ids, so `Fetch` yields nullptrs.)

**Control case (no crash)**: the first `Insert` opened `wal_file_` via `append_wal`, so at `Optimize` the guard at `segment.cc:2220` is passed: `flush()` persists the memory store, `finish_memory_components()` records the `SCALAR` block, `update_version()` persists the meta, and the WAL is removed. The manifest then references real files. Nothing is lost.

Note the blast radius: the same guard makes an explicit `Flush()` (`collection.cc:389-395`) and the destructor-time flush (`collection.cc:340-361`) equally silent no-ops in a recovered-but-not-written-to process. The loss is triggered by whatever first rewrites the manifest (`Optimize`, `CreateIndex`, segment switch, …).

## 3. Why success + same-handle stats prove nothing here

- `Optimize`'s OK is composed of task execution + manifest writes; the one step that would have persisted the docs (`flush()`) short-circuits with OK *by design* for a "clean" segment, and nothing downstream cross-checks that the committed manifest's blocks actually cover the documents counted in RAM.
- `Stats()` (`collection.cc:403-442`) sums `doc_count()` = in-memory `doc_ids_.size()`; `Query`/`Fetch` hit `memory_store_` and the idmap memtable of the same handle. After optimize, the seg-0 object still lives in `segment_manager_` with its `memory_store_` intact (the no-op flush never closed it; `reload_vector_index` doesn't touch the forward store). So the handle keeps serving the recovered docs from RAM.
- Durability in this design is defined solely by what a *future* `VersionManager::Recovery` will load: the newest manifest, plus the WAL keyed by the manifest's writing-segment meta. No same-handle API re-derives that view; only a reopen observes it. The healthy statistics and the durable state diverged at `collection.cc:1546-1549`.

## 4. Smallest repair principle and a regression test (described, not implemented)

**Repair principle — restore the invariant the flush guard depends on:** after replaying the WAL, the recovered writing segment must again *own* an open WAL handle. Concretely, at the end of `SegmentImpl::recover()` (after the local replay handle is closed), call the existing `open_wal_file()` (`segment.cc:4303-4322`): the file exists, so it reopens with `create_new=false` and seeks to End (`local_wal_file.cc:92-106`). Then `wal_file_ != nullptr && has_record()` is true exactly when replayed-but-unpersisted data exists, and the untouched `dump()`→`flush()` path does the right thing: persist memory store → `finish_memory_components()` adds the `SCALAR` block → `update_version()` → remove the WAL. One state-restoration change; no lifecycle reordering. (An equivalent alternative is to make the guard at `segment.cc:2220` consult segment state — e.g. `memory_store_` non-empty or mem-block `doc_count_ > 0` — instead of the handle pointer; the ownership fix is smaller and also repairs explicit `Flush()`/close-time flush after recovery.)

**Regression test** — the repo already has the right harness: `tests/db/crash_recovery/write_recovery_test.cc` (fork + SIGKILL child, lines ~101-126) and `tests/db/crash_recovery/optimize_recovery_test.cc`. The uncovered sequence is *crash → reopen → clean optimize → reopen*:

1. **Process A** (forked child): `CreateAndOpen` a collection, `Insert` N docs (small: one segment, no rollover), then die via SIGKILL/`_exit` without `Flush()` or destructor.
2. **Process B**: `Collection::Open`; assert `Stats().doc_count == N` and `Fetch(all pks)` returns all docs.
3. Still in B, **without inserting anything**, call `Optimize()`; assert OK; close cleanly.
4. **Process C**: `Collection::Open` again; assert `Stats().doc_count == N` and `Fetch` returns all N docs with identical fields/vectors. On the current source this assertion fails (0 docs); after the repair it must pass.
5. Harden: after step 3 assert the old WAL (`<path>/0/*.wal`) is *gone* and segment 0's directory contains a forward-block file (direct evidence flush consumed the WAL); add a control arm where A calls `Flush()` before dying (must pass before and after the fix), and an arm that inserts one doc in B before `Optimize()` (exercises the reopened-WAL append path).

**Established from source vs. requiring execution.** Everything above — the nullptr `wal_file_` after replay, the early-returning flush guard, the meta/manifest rewrite, the orphaned WAL, the single-segment `CreateVectorIndexTask` planning, and the reopen behavior — is traced directly from the frozen tree with the cited lines. I did **not** build or run anything, so the end-to-end manifestation (exact reopen symptoms, e.g. pk→nullptr vs. "Segment not found" warnings in process 3) is a prediction from code reading, not an observed reproduction; confirming it needs the test in §4.

**Non-causal aside** (observed while tracing, verifiable from source): `recover()` bumps `mem_block.max_doc_id_ += added_docs` (`segment.cc:4285-4288`) even though `internal_insert` already set it per doc (`segment.cc:874-876`), so the recovered writing block's `max_doc_id` is double-counted. It doesn't cause this loss (lookups go through the idmap and the range still covers the ids), but it would leave doc-id gaps when the next segment's `min_doc_id` is derived from it (`collection.cc:1527-1531`).
