# Analysis: recovered-then-optimized data loss in zvec

All findings below come from reading the frozen tree at `/workspace`; **I did not build or run anything**, so no reproduction is claimed. Paths are repo-relative.

## 1. What differs between the recovery path and the ordinary insertion path

**Ordinary insert path.** `CollectionImpl::Insert` → `write_impl` → `writing_segment_->Insert(doc)` (`src/db/collection.cc:1364-1418`). `SegmentImpl::Insert` (`src/db/index/segment/segment.cc:903-918`) does two things per document:

- `append_wal(doc)` (`segment.cc:4324-4340`), which **lazily opens the member `wal_file_`** via `open_wal_file()` (`segment.cc:4303-4322`) on the first write and appends the serialized record;
- `internal_insert(doc)` (`segment.cc:837-881`), which populates the *memory* components: `memory_store_->insert` (forward rows), scalar/FTS indexers, `memory_vector_indexers_`, `doc_ids_.push_back` (line 878), and bumps the writing-forward-block meta (lines 874-876).

**Recovery path.** On reopen, `CollectionImpl::recovery()` (`src/db/collection.cc:1836-1892`) loads the version, then opens the writing segment from `v.writing_segment_meta()` (lines 1880-1887). `SegmentImpl::Open` sees a writing forward block and calls `recover()` (`segment.cc:484-501`). `SegmentImpl::recover()` (`segment.cc:4193-4301`):

- opens the WAL through a **separate local handle** `recover_wal_file` (lines 4206-4215) that is closed on scope exit;
- replays each record by calling `internal_insert / internal_update / internal_upsert / internal_delete` **directly** (lines 4250-4266) — i.e., it deliberately skips `append_wal`;
- fixes up `mem_block.max_doc_id_` (lines 4285-4288).

The state difference is therefore exactly one member: after recovery the segment holds all rows in memory components and on disk **only in the WAL**, but `wal_file_` is still `nullptr` (declared so at `segment.cc:401`). Any handle that accepted at least one public write has a non-null `wal_file_` with records.

**Why the data is initially readable.** All read paths on the recovering handle are memory-inclusive:

- `Stats()` sums `segment->doc_count(filter)` over live `Segment` objects (`collection.cc:403-442`), and `doc_count()` is `doc_ids_.size()` minus deletions (`segment.cc:589-599`) — populated by replay.
- `get_all_segments()` appends the writing segment when `doc_count() > 0` (`collection.cc:2076-2082`).
- Document fetch resolves rows that fall in the writing block from `memory_store_` (`segment.cc:2483-2498`, "Check memory store") and vectors from `memory_vector_indexers_` (`segment.cc:1468-1499`).
- `Fetch` by pk works because replay re-ran `id_map_->upsert` inside `internal_insert` (`segment.cc:853`).

## 2. The call sequence and exact condition that lose the data

`CollectionImpl::Optimize` (`src/db/collection.cc:779-915`):

1. **Gate passes**: `writing_segment_->doc_count() != 0` (line 794) is true because replay filled `doc_ids_`, so it calls `switch_to_new_segment_for_writing()` (line 796; defined at 1517-1552).
2. **`dump()` is a silent no-op**: `switch_to_new_segment_for_writing` first calls `writing_segment_->dump()` (line 1519). `SegmentImpl::dump()` (`segment.cc:2197-2215`) delegates to `flush()`, and `SegmentImpl::flush()` begins with:
   ```cpp
   if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();
   ```
   (`segment.cc:2220-2222`; `has_record()` is `file_.size() > sizeof(header_)`, `src/db/index/storage/wal/local_wal_file.h:75-77`). On the recovered handle no public write occurred, so `wal_file_ == nullptr` → **flush returns OK without doing anything**. Skipped inside flush: `memory_store_->flush()` (2233-2236), `finish_memory_components()` (2288-2298), `update_version()` (2301), WAL removal (2304-2315). `finish_memory_components()` (`segment.cc:4342-4411`) is the **only** code that writes the forward-block file and records a persisted `SCALAR` `BlockMeta` into the segment meta — so nothing on disk ever represents the replayed rows.
3. **The version launders the segment to "persisted, 0 docs"**: still in `switch_to_new_segment_for_writing`, the old segment is added to the segment manager (line 1522), a new empty writing segment is created (1527-1534), then `writing_segment_meta->remove_writing_forward_block()` (1538) and `version.add_persisted_segment_meta(writing_segment_meta)` (1539), the version is switched to the new writing segment and **applied + flushed to disk** (1543-1549). With the writing block removed and zero persisted SCALAR blocks, `SegmentMeta::doc_count()` is now 0 (`src/db/index/common/meta.h:307-318`). No meta anywhere references the old WAL's block anymore.
4. **The optimize work itself succeeds trivially**: `persist_segments = get_all_persist_segments()` (lines 802-803, 2084-2086) returns the old segment (in memory it still reports N docs). For a small collection with no deletes, `build_compact_task` (917-1005) makes one group, `rebuild=false`, and emits a `CreateVectorIndexTask` (991-995). `SegmentHelper::ExecuteCreateVectorIndexTask` (`src/db/index/segment/segment_helper.cc:1113-1125`) runs `create_all_vector_index`/`create_vector_index` (`segment.cc:1617-1640`, 1670-1826), which either early-skips for FLAT fields already marked indexed at `SegmentImpl::Create` (`segment.cc:534-539`, skip at 1685-1690) or calls `merge_vector_indexer` (1642-1668) — which merges `vector_indexers_[column]`, the **persisted** indexer list. That list is empty because `finish_memory_components()` never moved `memory_vector_indexers_` into it, so the merge builds an empty index and returns OK. Optimize then updates the version with the output meta (863-867), applies and flushes it (871-877), and returns `Status::OK()` (914).
5. **Reopen finds nothing**: in the next process, `recovery()` opens the old segment as a persisted segment (`collection.cc:1861-1874`). In `SegmentImpl::Open`, `writing_block.has_value()` is false, so `recover()` is **skipped** (`segment.cc:490-510`) — the orphaned WAL file is never replayed again (its path is keyed to the old segment/block IDs via `FileHelper::MakeWalPath`, `segment.cc:4198-4199`, and nothing scans for orphans). `load_persist_scalar_blocks` (`segment.cc:3913-3960`) finds zero SCALAR blocks, so `doc_ids_` is empty and the segment reports 0 documents. The new writing segment is empty. The documents are gone.

**Exact enabling condition**: `SegmentImpl::flush()` is invoked (here via `dump()` from `switch_to_new_segment_for_writing`) on a writing segment whose rows arrived through WAL replay rather than through this process's public write API — i.e., memory rows exist (`writing_forward_block().doc_count_ > 0`) but `wal_file_ == nullptr`. The gate at `segment.cc:2220` conflates "this handle never appended to the WAL" with "there is nothing to persist." The same hazard exists for every other caller of `switch_to_new_segment_for_writing`: `CreateIndex` (collection.cc:501-504), `DropIndex` (674-676), `AddColumn` (1154-1157), `DropColumn` (~1226-1229), `AlterColumn` (~1310-1313). The control case is safe because a process that inserted has a non-null `wal_file_` with records, so `dump()`→`flush()` really persists via `finish_memory_components()` before the version switch. (Variant: with deletes or many segments, a `CompactTask` runs instead and `destroy_segment` at `collection.cc:898-901` / `segment_manager.cc:45-56` marks the segment destroyed; `~SegmentImpl` then runs `cleanup()` which removes the segment directory, `segment.cc:112-117`, 2334-2338 — physically deleting the orphaned WAL too. In the small-collection variant the WAL file remains on disk but unreachable.)

## 3. Why "OK" plus same-handle statistics prove nothing

- **Every step returns OK by construction.** The no-op flush returns `Status::OK()` (`segment.cc:2221`), the empty vector-index merge succeeds (`segment_helper.cc:1113-1125`), and `Optimize` returns OK at `collection.cc:914`. Nothing in the return value distinguishes "persisted N rows" from "skipped."
- **Stats are computed from live in-memory objects, not disk.** `Stats()` (`collection.cc:403-442`) sums `doc_count()` over the `Segment` pointers held by the handle; after Optimize the old segment object is still in `segment_manager_` (added at `collection.cc:1522`; only CompactTask inputs are removed at 898-901) with its replayed `doc_ids_` and `memory_store_` intact. So the same handle still counts and fetches N documents from RAM while the flushed version file already claims that segment has 0 (`meta.h:307-318`).
- **The version promotion is unchecked.** `switch_to_new_segment_for_writing` never verifies that after `dump()` the meta it is promoting to "persisted" actually contains the rows (`writing_segment_meta->doc_count()` at meta level vs. runtime `writing_segment_->doc_count()`). Durability here is only observable from the persisted version/forward-block files or from a fresh reopen — exactly what the reporter did.

## 4. Smallest repair principle and a regression test (described, not implemented)

**Repair principle — gate the dump on memory/version state, not on the WAL handle.** The intended lifecycle invariant is: *a writing segment may only be retired into the persisted version after all rows in its writing forward block have been dumped to a persisted SCALAR block; the WAL may only be removed after that dump.* The minimal change consistent with that invariant is in `SegmentImpl::flush()` (`segment.cc:2217-2222`): the early-return must not fire when the writing block holds rows (e.g., when `memory_store_ != nullptr`, or `writing_forward_block().doc_count_ > 0`, or `!doc_ids_.empty()`); the WAL-specific steps (fsync at 2224-2229, removal at 2304-2315) stay conditional on `wal_file_` being non-null. An equally targeted alternative is to have `recover()` adopt the replayed WAL into `wal_file_` (or set a "dirty-recovered" flag) so the existing gate sees `has_record()==true`; the flush-gate fix is preferable because it makes the invariant independent of how rows entered memory. A cheap secondary guard: in `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`), fail (or force a real dump) if after `dump()` the promoted meta's `doc_count()` doesn't match the segment's runtime `doc_count()` — this catches any future no-op-dump regression at the exact point where data would be laundered.

**Regression-test sequence** (fits `tests/db/crash_recovery/`, which already has fork/kill plumbing):

1. **Populate + crash without flush**: a generator process creates the collection, inserts N docs (small: one writing segment, no rollover), then exits abruptly *without* `Flush()` or destructor flush — note the existing generator deliberately flushes before `_exit(0)` (`tests/db/crash_recovery/data_generator.cc:244-254`), so a new no-flush exit mode (or a parent-side `SIGKILL` as in `RunGeneratorAndCrash`, `write_recovery_test.cc:144`, 191) is required. Optionally assert the segment WAL file exists on disk.
2. **Recover and verify readable**: `Collection::Open`; assert `Stats().doc_count == N` and `Fetch` returns all N docs (this is the WAL-replay path, already partly covered by `write_recovery_test.cc`).
3. **The missing step — optimize with zero new inserts on the recovered handle**: call `Optimize({})`, assert OK. (Post-fix, additionally assert the old segment's forward-block file now exists / the WAL was removed only after the dump.)
4. **Reopen again and verify durability**: close the handle, `Collection::Open` in a fresh process (the existing `collection_optimizer`/fork pattern in `optimize_recovery_test.cc:53-118` shows how), assert `Stats().doc_count == N`, byte-compare all N docs via `Fetch`, and run one vector query to check index coherence.

Why current tests miss it: `CrashDuringOptimize` (`optimize_recovery_test.cc:144-261`) inserts in a process that closes cleanly (Close → `flush_unsafe` → real flush, `collection.cc:331-395`) and crashes *during* optimize; the `write_recovery_test.cc` cases crash during writing and verify a reopen but never run optimize on a recovered handle that performed no inserts. The bug requires precisely that middle state: memory-only recovered rows + a version-transition operation + a second reopen.

**Established from source vs. requiring execution.** The entire causal chain — the `wal_file_ == nullptr` gate, `recover()`'s local WAL handle, the unconditional version promotion in `switch_to_new_segment_for_writing`, the meta-level `doc_count()==0`, and the reopen skipping WAL replay — is established by reading the code. What would require actually running a test: observing the end-to-end loss (reopen → 0 docs); which branch of `create_vector_index` executes for a given schema (FLAT-skip vs empty-merge — both succeed without persisting forward data); whether the orphaned WAL file physically remains in the small-collection variant; and whether stale pk→doc_id entries survive in the id-map file (I did not audit `src/db/index/common/id_map.cc` persistence timing).
