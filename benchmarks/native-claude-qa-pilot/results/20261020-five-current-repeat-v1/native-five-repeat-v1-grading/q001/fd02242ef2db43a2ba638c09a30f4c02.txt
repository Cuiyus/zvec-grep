Investigation complete — every causal link is verified in the frozen tree, and I ran nothing (all findings are from source reading). Here is the analysis.

# Root cause in one sentence

WAL replay in `SegmentImpl::recover()` restores a writing segment's *logical* state but leaves its member `wal_file_` handle **null**, and `SegmentImpl::flush()` uses exactly that handle as its "is there anything to persist?" probe — so a later `Optimize()` performs a no-op "flush," strips the WAL reference from the persisted version, and returns OK while the recovered documents were never written to any persisted block.

---

## 1. State that differs between the recovery path and the insertion path

**Ordinary insertion** (`src/db/index/segment/segment.cc:903-918`): `Insert()` calls `append_wal(doc)` **before** `internal_insert(doc)`. `append_wal` (`segment.cc:4324-4340`) lazily opens the member `wal_file_` via `open_wal_file()` (`segment.cc:4303-4322`). So an inserted-into writing segment always has `wal_file_ != nullptr`, and `has_record()` is file-size based (`src/db/index/storage/wal/local_wal_file.h:75-77`: `file_.size() > sizeof(header_)`), hence true.

**Recovery** (`CollectionImpl::Open` → `recovery()`, `src/db/collection.cc:308-329, 1836-1892`): the version's writing-segment meta is reopened; `SegmentImpl::Open` calls `recover()` only when a `writing_forward_block` exists (`segment.cc:484-501`). `SegmentImpl::recover()` (`segment.cc:4193-4301`) opens a **separate local** `recover_wal_file` handle (4206-4215, closed by `AILEGO_DEFER`), replays each record through `internal_insert/internal_update/internal_upsert/internal_delete` (4250-4266), and returns. It never assigns the member `wal_file_` and never calls `open_wal_file()` — the **only** caller of `open_wal_file()` is `append_wal`, i.e., the first *new* write. This is the single differing piece of state.

**Why reads still work:** replay rebuilds exactly what inserts would have built in memory — `memory_store_` rows, id-map upserts, in-memory scalar/vector/FTS indexers, `doc_ids_`, and writing-block counters (`internal_insert`, `segment.cc:837-881`, esp. 853-878). Queries and counts on that handle are served from these in-process structures (`collection.cc:1587`; `Stats()` at `collection.cc:403-438` → `SegmentImpl::doc_count` = `doc_ids_.size()`, `segment.cc:589-600`). Durability at this point is still intact *on disk*: the WAL file (`<collection>/<seg_id>/<block_id>.wal`, `src/db/common/file_helper.h:74-79`) exists and is still referenced by the writing block in the persisted version — a plain reopen would replay it again.

## 2. Call sequence and exact condition allowing silent loss

`CollectionImpl::Optimize` (`collection.cc:779-915`) on the recovered handle, with no intervening writes:

1. `writing_segment_->doc_count() != 0` (true — recovered docs are in `doc_ids_`) → `switch_to_new_segment_for_writing()` (`collection.cc:794-800`).
2. `switch_to_new_segment_for_writing` (`collection.cc:1517-1552`):
   - `writing_segment_->dump()` (`segment.cc:2197-2215`) → `flush()`. **Exact condition:** `flush()`'s first statement (`segment.cc:2220-2222`) is `if (wal_file_ == nullptr || !wal_file_->has_record()) return Status::OK();`. Because recovery left `wal_file_` null, the entire body is skipped: no `memory_store_->flush()`, no `finish_memory_components()` (which is what converts the memory block into persisted forward/vector blocks and records their `BlockMeta`s, `segment.cc:2288-2298, 4342-4412`), no `update_version()`, no WAL removal (2304-2315). `dump()` then seals and returns OK.
   - The old segment is added to the segment manager; a new empty writing segment is created (`collection.cc:1522-1534`).
   - **The point of no return:** `writing_segment_meta->remove_writing_forward_block()` (`collection.cc:1538`; sets the optional to `nullopt`, `src/db/index/common/meta.h:263-265`), the hollow meta is added as a *persisted* segment meta, and `version_manager_->apply()` + `flush()` write this version to disk (`collection.cc:1539-1549`). The on-disk version now asserts "this segment is fully persisted, no writing block, no WAL" — while zero data blocks exist for it.
3. The rest of Optimize succeeds trivially. With one persisted segment and no deletes, `build_compact_task` emits a `CreateVectorIndexTask` (`collection.cc:991-1002`); `create_all_vector_index` clones the hollow meta and skips work for absent/FLAT/already-indexed vector fields (FLAT is pre-marked indexed at `Segment::Create`, `segment.cc:534-539`; skip at `segment.cc:1685-1690`), returning OK (`segment.cc:1617-1640`). The version is updated and flushed again (`collection.cc:863-877`) and `Status::OK()` is returned (914).
4. **Third process reopens:** `recovery()` opens persisted segments read-only from version metas and the (new, empty) writing segment (`collection.cc:1861-1887`). WAL replay is triggered *only* by a `writing_forward_block` in the meta (`segment.cc:484-501`); the old segment's was removed, so the orphaned WAL — even though it physically remains in the segment directory on this single-segment path — is never read again. (On multi-segment `CompactTask` paths it is deleted outright: inputs are destroyed, `collection.cc:898-901`, and `~SegmentImpl` → `cleanup()` → `RemoveDirectory(seg_path)` wipes the directory including the WAL, `segment.cc:112-117, 2334-2336`; note also `ExecuteCompactTask` treats "0 docs read" as success with a null output meta, `src/db/index/segment/segment_helper.cc:138-141`, while Optimize still removes/destroys the inputs.)

**Control case:** without the crash, `Insert` had opened `wal_file_`, so at step 2 `flush()` passes the guard, persists the memory block, updates the version, and only then removes the WAL — reopen finds real persisted blocks. The same trigger applies to every other caller of `switch_to_new_segment_for_writing`: `CreateIndex` (`collection.cc:501-503`), `DropIndex` (674-677), `AddColumn`/`DropColumn`/`AlterColumn` (1155, 1227, 1311), and write-path rollover (1446, excluded by the scenario's assumptions).

## 3. Why OK returns and same-handle statistics prove nothing here

- **Every step legitimately returned OK.** `flush()` collapses "nothing to persist" and "persisted successfully" into the same `Status::OK()` (segment.cc:2220-2222). The version `apply()/flush()` succeeded — it faithfully persisted metadata that is *false* (a "persisted" segment with no blocks). Zero-doc compaction is also OK by design (segment_helper.cc:138-141). No layer cross-checks the version's claim against actual persisted data.
- **Same-handle statistics are process-resident.** `Stats()` sums `segment->doc_count()` = `doc_ids_.size()` (collection.cc:403-438; segment.cc:589-600), and fetches are served from `memory_store_`/in-memory indexers of the *old* segment object, which the buggy optimize never invalidated in memory. Nothing on the same handle ever re-reads the on-disk version; the disk state is consulted only by `recovery()` on a fresh open. Durability here is observable **only** by reopening.
- Corollary worth noting: even an explicit `Flush()` on the recovered handle is a silent no-op (`CollectionImpl::Flush` → `flush_unsafe` → `writing_segment_->flush()`, collection.cc:380-395 → the same guard). And a latent secondary defect: post-optimize, any `scan()` of the hollow old segment on the same handle would dereference `writing_forward_block().value()` while `memory_store_` still has rows (segment.cc:2825-2841) — per standard `std::optional` semantics that is `std::bad_optional_access`; the scenario's "statistics look healthy" is consistent because `doc_count` never scans.

## 4. Smallest repair principle and regression test (described, not implemented)

**Repair principle — recovery must restore durability state, not just logical state.** After a recovered writing segment finishes replay, it must be indistinguishable from one that reached the same contents via `Insert()`: the member WAL handle must be attached and reporting records. Minimal change: at the end of `SegmentImpl::recover()` (segment.cc:4193-4301), once the local read handle is closed, call `open_wal_file()` — it opens the existing WAL with `create_new=false` and seeks to end for future appends (local_wal_file.cc:92-106), and `has_record()` is size-based, so it immediately reports true (local_wal_file.h:75-77). Then `flush()`/`dump()` take the full path (persist memory block → update version → remove WAL only after data is durable, segment.cc:2224-2315), preserving crash-ordering. Optional hardening (beyond minimal): make the flush guard data-driven (writing-block `doc_count_`/`memory_store_` rows/WAL-file-exists rather than handle non-null), and guard the `scan()` memory branch at segment.cc:2837.

**Regression test sequence** (harness pattern already exists in `tests/db/crash_recovery/` — fork/exec a generator and `SIGKILL` it, `optimize_recovery_test.cc:53-128`; `write_recovery_test.cc:274-359`):

1. **Crash arm:** child process creates the collection, inserts N docs (N and doc size below rollover thresholds so no auto-switch), and is `SIGKILL`ed (or `_exit`s) without `Flush`/`Close`.
2. Reopen in the test process → assert count == N and spot-fetch by pk (passes today).
3. Call `Optimize()` with no intervening writes → assert OK (passes today).
4. Close, reopen a third time → **assert count == N and every pk fetches**. This is the oracle; it fails today (0 docs) and passes after the repair.
5. **Control arm:** identical sequence but graceful close instead of kill in step 1 — passes before and after, pinning the defect to recovery state.
6. **Sharper single-process check (optional):** after step 2, call `Flush()` and assert structural durability directly — a persisted SCALAR `BlockMeta` appears in the writing segment's meta and the `<block>.wal` file is gone. Pre-repair, `Flush()` returns OK but the WAL remains and no block appears, catching the no-op flush without a second reopen.
7. **Coverage extension (optional):** repeat the crash arm triggering `CreateIndex`/`DropIndex`/`AddColumn` instead of `Optimize` — same `switch_to_new_segment_for_writing` mechanism.

## Established from source vs. requires execution

**Established from source:** the null-`wal_file_` recovery state; the flush guard and everything it skips; the version rewrite in `switch_to_new_segment_for_writing`; reopen replaying WAL only via `writing_forward_block`; in-memory-only statistics; silent-OK single-segment optimize for absent/FLAT/already-indexed vector schemas; orphaned-vs-deleted WAL file outcomes.

**Would require running (I did not run anything):** (a) whether `Optimize` returns OK for *every* schema shape on a recovered handle — with a non-FLAT vector index, `merge_vector_indexer` would merge the (empty) persisted `vector_indexers_` and the outcome (error vs. empty index) is not determinable by reading alone; likewise `dump_fts_indexers` on unflushed recovered FTS indexers; (b) whether the post-optimize same-handle `scan()` actually throws `bad_optional_access`; (c) the precise third-process count (0 vs. partial) for a given schema. The scenario's stipulation that optimize succeeds matches the source-verified silent path (single segment, no vector-index work needed).
