# Root cause: `optimize()`'s low-delete-ratio path builds the vector index with the delete filter applied, but keeps unfiltered positional metadata

## 1. The path this sequence takes

- Delete is tombstone-only: `SegmentImpl::internal_delete` (`src/db/index/segment/segment.cc:933-937`) calls `delete_store_->mark_deleted(doc_id)` and `id_map_->remove(pk)`. It never touches the segment's row array `doc_ids_` (`segment.cc:398`), the persisted forward (scalar) block, or the dumped vector block. Positions 0–27 remain occupied; rows 0–2 are just marked dead.
- `CollectionImpl::optimize` (`src/db/collection.cc:910`) seals the writing segment (`collection.cc:929-934`), snapshots persisted segments, clones the delete store into a filter (`collection.cc:945-948`), and calls `build_compact_task` (`collection.cc:1086`).
- Delete-ratio decision (`collection.cc:1093-1104`): `rebuild` is set only when `actual < total * (1 - COMPACT_DELETE_RATIO_THRESHOLD)`, and `COMPACT_DELETE_RATIO_THRESHOLD = 0.3f` (`src/db/common/constants.h:41`). Here 3/28 ≈ 0.107 < 0.3 → **rebuild = false**.
- With one persisted segment and `rebuild=false`, the tail branch (`collection.cc:1160-1164`) creates a **`CreateVectorIndexTask`** — an in-place index build on the existing segment, *not* a rewrite. HNSW is not marked indexed at create time (only FLAT is, `segment.cc:551-556`), so `all_vector_index_ready()` (`segment.cc:1819-1824`) is false and the task runs.
- `SegmentHelper::ExecuteCreateVectorIndexTask` (`src/db/index/segment/segment_helper.cc:1121-1133`) → `SegmentImpl::create_all_vector_index` (`segment.cc:1466-1489`) → `create_vector_index` (`segment.cc:1519`, non-quantized FP32 branch at 1545-1578) → `merge_vector_indexer` (`segment.cc:1491-1517`).

## 2. The defect: filtered merge + unfiltered metadata

- `merge_vector_indexer` passes the segment's live delete filter into the merge: `vector_indexer->Merge(to_merge_indexers, filter_, merge_options)` (**`segment.cc:1511`**). `filter_` is a `SegmentIndexFilter` (`segment.cc:482-483`, `538-539`) whose `is_filtered(id)` treats `id` as a *segment-local position*, resolves it via `get_global_doc_id` → `doc_ids_[id]` (`segment.cc:464-476`, `4444-4451`), and checks the delete store. So positions 0, 1, 2 are filtered.
- `VectorColumnIndexer::Merge` (`src/db/index/column/vector_column/vector_column_indexer.cc:103-129`) → `Index::merge` (`src/core/interface/index.cc:1016-1075`, `reducer->reduce(filter)` at 1071) → `MixedStreamerReducer::reduce/read_vec` (`src/core/mixed_reducer/mixed_streamer_reducer.cc:131-229`, `255-326`): filtered source keys are **skipped** (`mixed_streamer_reducer.cc:288-292`) and survivors are re-added with **fresh dense ids** `VectorItem((*next_id)++, ...)` (`mixed_streamer_reducer.cc:318`). The new HNSW block therefore holds 25 vectors, and its position *j* contains the vector of original row *j+3*.
- But the BlockMeta recorded for the new index declares the **unfiltered** range: `block.set_min_doc_id(doc_ids_.front()); block.set_max_doc_id(doc_ids_.back()); block.set_doc_count(doc_ids_.size())` (**`segment.cc:1573-1575`**) — i.e. min 0, max 27, count 28. The forward block is not rewritten and `doc_ids_` still has 28 entries. `reload_vector_index` (`segment.cc:1752-1810`, invoked from `collection.cc:1063-1070`) swaps in the 25-vector indexer and the 28-row metadata, and phase 3 flushes it into the version manifest (`collection.cc:1036-1040`) — so the corrupted state is durable and a read-only reopen reloads exactly this pairing.

## 3. Why scalar/count checks pass while vector reads are wrong

Everything downstream is **positional**, and the two sides now disagree:

- Search: `VectorRecallNode` searches the combined indexer (`src/db/sqlengine/planner/vector_recall_node.cc:209`); block-local hit ids are translated to segment positions by adding `block_offsets_[i]` derived from `BlockMeta.doc_count_` (`src/db/index/column/vector_column/combined_vector_column_indexer.cc:279-284`, `404`, `411`). `collect_batch` then uses those positions both to read scalar fields from the forward store (`vector_recall_node.cc:225-231`) and to fetch vectors (`vector_recall_node.cc:251-259` → `fetch_vector_op.cc:35,91` → `CombinedVectorColumnIndexer::Fetch`, `combined_vector_column_indexer.cc:426-450`).
- Concrete effect: a query with doc-0007's saved basis vector matches merged-index position 4, which is reported as segment position 4 → forward row 4 → **"doc-0004"** (a live but wrong ID, shifted by the 3-row deleted prefix). Queries for doc-0003/4/5 land on positions 0–2, which the query-time `SegmentIndexFilter` (wired via `vector_recall_node.cc:169`, applied per-block at `combined_vector_column_indexer.cc:352-361`) drops as "deleted" → those live docs silently vanish. Positions 25–27 no longer exist in the 25-vector index, so **doc-0025…doc-0027 can never be returned** — the omitted live tail.
- Vector payload fetch: fetch-by-id resolves pk → global doc id → position via `std::lower_bound(doc_ids_...)` (`segment.cc:1041-1049`). For doc-0025…27, `CombinedVectorColumnIndexer::Fetch` finds the block (its meta claims doc_count 28, `combined_vector_column_indexer.cc:432-441`) and calls `indexer->Fetch(25..27)` on an index with only 25 slots → out-of-range failure, **while scalar columns for the same IDs fetch fine** from the intact 28-row forward block. (Fetches for positions 0–24 succeed but return the vector of document +3 — silent payload corruption.)
- Counts/scalars agree because they never consult the vector block: `doc_count` and scalar enumeration read the forward store filtered by delete-store tombstones (28 − 3 = 25 live). The corruption exists only in the position↔vector association.

## 4. The two controls

- **Optimizing the empty collection first doesn't help**: in `optimize`, the writing segment has no records, so nothing is sealed, and `persist_segments` is empty → early `return Status::OK()` (`collection.cc:929`, `936-942`). No index or metadata is established; the later delete→optimize hits the identical buggy path.
- **Optimizing the non-empty data before deleting avoids it**: that first optimize also takes the `CreateVectorIndexTask` path, but the delete store is empty, so `SegmentIndexFilter::is_filtered` is false for every key; the merged HNSW keeps all 28 vectors at their original positions, making BlockMeta doc_count 28 (`segment.cc:1573-1575`) *correct*, and the fields get marked indexed (`segment.cc:1540`, `1485`). Deletes afterwards are tombstone-only. The post-delete optimize re-enters `create_vector_index` but early-returns at `segment.cc:1534-1539` (`vector_indexed(column)` and same params) — no re-merge — so the position mapping stays aligned and deleted rows are excluded at query time by the tombstone filter. (The multi-segment variant of the same decision even skips explicitly via `skip_task = all_vector_index_ready()`, `collection.cc:1135`.)

## 5. The different path at high delete ratio (≥ 0.3)

When `actual < total * 0.7`, `rebuild = true` (`collection.cc:1100-1104`) and the task becomes a **`CompactTask` carrying the delete filter** (`collection.cc:1166-1168`) — a full segment rewrite in `SegmentHelper::ExecuteCompactTask` (`segment_helper.cc:100-175`): `ReduceScalar` rewrites the forward data *dropping* deleted rows (`FilterRecordBatch`, `segment_helper.cc:934-998`, bitmap add at 969) and computes fresh `min_doc_id`/`max_doc_id`/`doc_count` over survivors; `ReduceVectorIndex` receives a matching `RowIdFilter` (`segment_helper.cc:89-98`, `127-153`) and its output BlockMeta uses the filtered counts (`segment_helper.cc:717-724`). The new segment's `doc_ids_` is re-derived from the rewritten `GLOBAL_DOC_ID` column (`segment.cc:3875-3914`). Because scalar rows, `doc_ids_`, and vector slots are all compacted **together** into a new segment, the positional mapping stays consistent — which is why the failure only appears below the threshold, on the in-place build path. The intended discipline is even documented at `segment_helper.cc:143-145`: leave the row filter null when `rebuild=false` "so downstream merge can take a faster per-doc path that skips the filter callback entirely." The single-segment in-place path violates that by passing the live `filter_` at `segment.cc:1511`. (Corroborating test commentary: `python/tests/test_collection_fts.py:154-158` on the 0.3 threshold and the rebuild path.)

## 6. The mapping invariant a fix must preserve

For every persisted segment: for every row position *i* ∈ [0, `doc_ids_.size()`), and for every block (scalar forward, vector index, quantized vector, FTS), **block_offset + block-local position = segment position i ↔ `doc_ids_[i]` ↔ forward row i**, and each block's `BlockMeta.doc_count_` must equal the segment's forward row count. Equivalently: a vector index block must contain exactly one slot per forward row — including tombstoned rows, which stay positionally addressable and are excluded only at query time by the delete-store filter. Positions may be compacted/renumbered only by a whole-segment rewrite that renumbers forward data, `doc_ids_`, and all index blocks atomically (the `ExecuteCompactTask` rebuild path). The minimal consistent repair of the buggy path is to stop filtering in the in-place merge (`segment.cc:1511` passing `nullptr`, matching `segment_helper.cc:143-145`'s stated contract) or to route segments with deletes through the rebuild `CompactTask`; either way the invariant above is what must hold.

## 7. A regression check that detects wrong associations, not counts

Count-only assertions (`doc_count == 25`) pass under this bug, so the test must do per-ID round-trips, exploiting the saved unit-basis vectors:

1. Insert `doc-0000…doc-0027` where doc-k's vector is e_k (1.0 at dimension k) plus a scalar label k; delete `doc-0000…0002`; flush; `optimize()` (asserting conditions that force the low-ratio path: single persisted segment, delete ratio < 0.3).
2. **Query→ID direction**: for every live k ∈ 3…27, search with saved e_k, topk=1, and assert the hit ID is exactly `doc-000k` (and score ≈ 1.0 cosine). The bug fails this three ways: k=3…5 return no hit (mapped onto deleted positions), k≥6 return `doc-00(k−3)`, and k=25…27 are unreachable.
3. **ID→vector direction**: fetch the vector field by ID for every live k and assert the bytes equal e_k (bitwise/float-exact). The bug makes fetch fail for k=25…27 (`CombinedVectorColumnIndexer::Fetch` → `NotFound`/range error despite the meta claiming 28) and return e_(k+3) for k ≤ 24.
4. Repeat with a delete fraction ≥ 0.3 (e.g., delete 9 of 28) to cover the rebuild `CompactTask` path with the same ID/vector-association assertions, and re-run steps 2–3 after a read-only reopen to catch the persisted-meta variant.

Natural homes: `tests/db/collection_test.cc` (alongside `Feature_Optimize_Compacted_Segment_Directories_Removed`, line 3272) or a Python test mirroring `python/tests/test_collection_fts.py::test_optimize_rebuilds_fts`.

## Scope note

The quantized branches (`segment.cc:1580-1693`), sparse/FTS columns, multi-segment grouping, and concurrent-writer behavior were not audited beyond the call sites cited, and no claim is made about them.
