# Root cause: `optimize()` renumbers vector-index keys past a forward store it never compacts

This is the **zvec** checkout (`/workspace`). The failure is a key↔row desynchronization introduced by the lazy HNSW build path in `optimize()` when deletes exist but fall below the rebuild threshold. Analysis below is limited to paths in this checkout (non-quantized FP32 HNSW branch); nothing was built or executed.

## The mechanism, step by step

**Insert (key ≡ row is established).** Vectors go into an in-memory FLAT indexer keyed by insertion offset: `SegmentImpl::InsertVector` → `indexer->Insert(vector_data, block_doc_id)` where `block_doc_id` is the writing block's current `doc_count_` (`src/db/index/segment/segment.cc:675–712`, esp. 702–705; `vector_column_indexer.cc:136–148`). For an HNSW field the segment is *not* marked indexed at create time — only true FLAT fields are (`segment.cc:553–554`) — so after flush/seal (`segment.cc:2067–2135`) the persisted segment holds a FLAT block keyed 0..27 and `all_vector_index_ready()` is false (`segment.cc:1819–1826`). The real HNSW build is deferred to `optimize()`.

**Delete (rows stay put).** Deletes only mark global doc ids in `delete_store_`. `doc_ids_` (segment-local row → global doc id, `segment.cc:4444–4450`) still has 28 entries; the forward store still has 28 rows.

**Optimize picks the lazy-build path.** `CollectionImpl::optimize` (`src/db/collection.cc:910`) seals the writing segment, snapshots persisted segments, and calls `build_compact_task` with a delete filter (`collection.cc:945–948`). 3/28 ≈ 10.7% deleted < `COMPACT_DELETE_RATIO_THRESHOLD = 0.3` (`src/db/common/constants.h:41`, applied at `collection.cc:1100–1104`), so `rebuild=false`; with a single persisted segment the last-group branch creates a **`CreateVectorIndexTask`**, not a compaction (`collection.cc:1159–1165`). That runs `SegmentImpl::create_all_vector_index` → `create_vector_index` → `merge_vector_indexer` (`src/db/index/segment/segment_helper.cc:1121–1133`; `segment.cc:1466–1517`).

**The filter + renumber combination is the bug.** `merge_vector_indexer` passes the segment's delete filter into the merge: `vector_indexer->Merge(to_merge_indexers, filter_, merge_options)` (`segment.cc:1511`). `filter_` is a `SegmentIndexFilter` whose `is_filtered(row)` resolves row → `doc_ids_[row]` → `delete_store_->is_deleted` (`segment.cc:464–474`, created at 481–483/537–539). `Merge` funnels into `core_interface::Index::merge`, which drives a `MixedStreamerReducer` with **PK rewrite enabled** (`vector_column_indexer.cc:103–134`; `src/core/interface/index.cc:1016–1077`, param at 1049–1050). In `MixedStreamerReducer::read_vec`, filtered rows are skipped (`src/core/mixed_reducer/mixed_streamer_reducer.cc:288–292`) and every *surviving* row is written under a fresh dense key `VectorItem((*next_id)++, …)` (`mixed_streamer_reducer.cc:318`). Result: the new HNSW file holds **25 vectors keyed 0..24**, where key *k* physically stores row *k+3*'s vector.

**The misalignment is committed.** `create_vector_index` never rewrites the forward store or `doc_ids_` (still 28 rows), yet stamps the block meta with `doc_count = doc_ids_.size()` = 28 (`segment.cc:1568–1576`), and `reload_vector_index` swaps the 25-entry index in under the collection commit (`segment.cc:1752–1810`; `collection.cc:1064–1071`, manifest at 1035–1040).

**Every reader assumes key ≡ row.**
- *Search*: `CombinedVectorColumnIndexer` derives block offsets by summing `block_meta.doc_count_` and adds them to hit keys (`combined_vector_column_indexer.cc:279–283`, 58–66); `VectorRecallNode::State::collect_batch` uses the key directly as the forward-row index — `indices.push_back(iter_->doc_id())` (`src/db/sqlengine/planner/vector_recall_node.cc:225`) — then fetches IDs/scalars from that row (`vector_recall_node.cc:231`). So a hit at key *k* reports row *k*'s pk: with rows 0–2 deleted, querying doc‑0006's basis vector hits key 3 → reports **doc‑0003** (wrong live ID). Querying doc‑0003's vector hits key 0 → row 0 → doc‑0000, which the query-time delete filter drops (`vector_recall_node.cc:169`); since distinct basis vectors all tie at cosine 0, arbitrary tie-break results surface. Rows 25–27 live at keys 22–24, so **doc‑0025..27 can never be returned** (they alias to doc‑0022..24).
- *Vector fetch*: `SegmentImpl::Fetch` computes `block_doc_id = segment_doc_id - block_offset` (`segment.cc:1282`) and calls `vector_indexer->Fetch(block_doc_id)` (`segment.cc:1294`). Rows 25–27 → keys 25–27 don't exist in a 25-key index → engine fetch fails (`vector_column_indexer.cc:150–165`) → `Fetch` returns `nullptr` (`segment.cc:1295–1300`) **while the scalar columns of the same rows fetch fine** from the intact forward store. Rows < 25 silently return the wrong vector (row *k+3*'s).
- *Read-only reopen*: `SegmentImpl::Open` → `load_vector_index_blocks` merely re-opens the persisted file read-only, with no consistency validation or rebuild (`segment.cc:475–498`, 3979–4048; open flags at ~4023). The corruption is on disk, so reopening doesn't help.

## Why scalar/count checks agree

Counts and scalar enumeration never consult the vector index: `stats.doc_count += segment->doc_count(delete_store_->make_filter())` (`collection.cc:543`) just walks `doc_ids_` minus delete-store hits (`segment.cc:616–627`) → 25. Scalar scans read the forward store (all 28 rows intact) and filter deleted global IDs, so pks and labels are self-consistent → 25 documents. The corruption exists *only* in the vector-index key-space ↔ row-space correspondence, so any check confined to scalar space passes.

## The two controls

- **Optimizing the empty collection first** changes nothing: phase 1 finds no records to seal and `get_all_persist_segments()` is empty, so `optimize()` returns OK at `collection.cc:940–942` without creating any task. No index is built; the buggy deferred build still runs later, after the deletes.
- **Optimizing the 28 live rows before deleting** takes the *same* `CreateVectorIndexTask` path, but with an empty `delete_store_` the filter rejects nothing, so the reducer's `(*next_id)++` renumbering is the identity over rows 0..27 → the HNSW is aligned, and the column is marked indexed (`segment.cc:1540`). After the deletes, the next `optimize()` hits `create_vector_index`'s early return `segment_meta_->vector_indexed(column) && params equal` (`segment.cc:1534–1539`; grouped-segment analogue `skip_task = all_vector_index_ready()`, `collection.cc:1135`) — no rebuild occurs, the aligned index stands, and deletes are excluded at query time by the delete filter. Correct results.

## The contrasting high-delete-ratio path

When the deleted fraction exceeds 30%, `build_compact_task` sets `rebuild=true` (`collection.cc:1100–1104`) and issues a **`CompactTask` carrying the delete filter**. `SegmentHelper::ExecuteCompactTask` (`segment_helper.cc:100–175`) rewrites *both sides of the mapping into a new segment*: `ReduceScalar` (177–322) scans forward rows in order, `FilterRecordBatch` drops deleted rows and records their physical ids in `delete_row_id_bitmap` (934–997, add at 969), and the 25 survivors are written to a new forward block in scan order; `ReduceVectorIndex` (638–759) then merges with a `RowIdFilter` over the *same* bitmap (85–98, 146–153), so the reducer's dense renumbering (key *k* ↔ *k*-th survivor) matches the new forward store exactly, and `doc_ids_` is rebuilt from the new GLOBAL_DOC_ID column. Block metas carry the compacted `doc_count` (138–141, 295–303), and the file-reuse shortcut is disabled whenever a filter is present (`CanReuseFirstIndexer`, 767–771). Filtering *and* row compaction happen in one atomic commit — which is precisely what the low-ratio `CreateVectorIndexTask` path fails to do: it filters the index without compacting the rows.

## Invariant a fix must preserve

**For every persisted vector-index block, the vector stored under block-relative key (r − block_offset) must be the vector of the document at physical segment row r, for every row r the block covers; and `BlockMeta.doc_count` must equal both the index's key count and the number of rows the block covers.** In other words, index key space ≡ segment row space (modulo block offsets) — exactly what `CombinedVectorColumnIndexer::AddBlock` (`combined_vector_column_indexer.cc:58–77`, 279–283), `collect_batch` (`vector_recall_node.cc:225–231`), and `SegmentImpl::Fetch` (`segment.cc:1276–1301`) assume. Equivalently: deleted rows may be skipped during a rebuild **only** if forward rows and `doc_ids_` are compacted in the same commit (as `ExecuteCompactTask` does). The minimal fix on this path is to merge without the delete filter in `merge_vector_indexer` (`segment.cc:1511`) so renumbering stays identity over all 28 physical rows (deleted vectors remain and are filtered at query time), or to route `create_vector_index` through a full compact whenever `delete_store_` is non-empty — plus making the block meta report the true key count.

## Regression check that catches wrong associations, not counts

A count-only test (`doc_count == 25`, 25 IDs enumerated) passes under any permutation of the mapping, so the oracle must be the distinct basis vectors — any misassociation changes either a top-1 identity or fetched bytes. Concretely (fits the existing optimize/compact conventions in `tests/db/collection_test.cc` or `python/tests/test_collection.py`):

1. Insert doc‑0000..doc‑0027, each with a distinct unit basis vector e_i in 32-d, keeping references outside the collection; delete doc‑0000..0002; flush; `optimize()`; optionally close and reopen read-only before asserting.
2. **Per-doc query identity**: for every live doc, query with its stored reference and assert top‑1 pk == that doc's ID *and* score == self-similarity (1.0 for COSINE) — the score clause also rules out tie-break noise.
3. **Coverage/bijection**: assert the set of top‑1 pks across all 25 queries equals the 25 live IDs (catches the omitted tail doc‑0025..27 and the aliased doc‑0003..24).
4. **Payload round-trip**: fetch every live ID with vector included and compare element-wise to the stored reference (catches silent wrong-vector fetches for rows < 25 and the hard `nullptr` fetch for rows 25–27); also fetch a scalar-only projection for the same IDs to show the asymmetry.
5. Optionally assert the internal invariant directly: vector block `doc_count` meta == engine key count == segment row count for the block.

**Scope caveats.** Conclusions cover the FP32/HNSW `quantize_type() == UNDEFINED` branch established above; the quantized branch passes the filter in the same shape (`segment.cc:1560`, 1625, 1674; `ReduceVectorIndex` at `segment_helper.cc:686–755`) but was not traced end-to-end. Multi-segment grouping, FTS, and concurrent-writer behavior are outside the reported sequence and were not audited.
