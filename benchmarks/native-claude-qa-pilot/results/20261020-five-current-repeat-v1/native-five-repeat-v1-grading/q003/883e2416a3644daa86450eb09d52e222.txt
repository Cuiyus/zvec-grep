# Root cause: the low-delete-ratio “in-place index build” renumbers vector keys while the scalar side keeps its original row positions

## 1. Which path this scenario takes

- 3/28 ≈ 10.7% deletes is below `COMPACT_DELETE_RATIO_THRESHOLD = 0.3f` (`src/db/common/constants.h:41`), so in `CollectionImpl::build_compact_task` the rebuild flag stays false (`src/db/collection.cc:1100-1104`).
- After `flush()`, there is exactly one persisted segment, so the final-group branch creates a **`CreateVectorIndexTask`**, not a `CompactTask` (`src/db/collection.cc:1160-1164`).
- `SegmentHelper::ExecuteCreateVectorIndexTask` (`src/db/index/segment/segment_helper.cc:1121-1133`) → `SegmentImpl::create_all_vector_index` → `SegmentImpl::create_vector_index` (`src/db/index/segment/segment.cc:1466-1489`, `1519`). Because the collection was never indexed (`segment_meta_->vector_indexed(column)` is false, so the skip at `segment.cc:1534-1539` does not fire), it calls `merge_vector_indexer` (`segment.cc:1560-1561`), which does `vector_indexer->Merge(to_merge_indexers, filter_, …)` (`segment.cc:1491-1517`, esp. line 1511). `filter_` is the `SegmentIndexFilter` over the delete store (`segment.cc:482-483`, `538-539`).
- `VectorColumnIndexer::Merge` (`src/db/index/column/vector_column/vector_column_indexer.cc:103-134`) → `Index::merge` (`src/core/interface/index.cc:1016-1077`), which sets `PARAM_MIXED_STREAMER_REDUCER_ENABLE_PK_REWRITE = true` (index.cc:1049-1050) and runs `MixedStreamerReducer::reduce(filter)` (index.cc:1071).

## 2. The defect

In `MixedStreamerReducer::read_vec` (`src/core/mixed_reducer/mixed_streamer_reducer.cc:255-326`):

- The delete filter is applied correctly against the source key: `filter(iterator->key() + id_offset)` (line 288). Source keys are **segment row positions**: the segment filter resolves them via `get_global_doc_id(id) → doc_ids_[id]` (`segment.cc:464-475`, `4444-4451`), and rows 0-2 are skipped.
- But each survivor is then produced with a **fresh sequential key**: `mt_list_.produce(VectorItem((*next_id)++, std::move(bytes)))` (line 318, with `next_id` starting at 0 for a builder target, lines 151-161), and `add_vec` inserts it under that new key via `add_with_id_impl(vector_item.pkey_, …)` (lines 375-377).
- The `enable_pk_rewrite_` flag that is supposed to govern this renumbering is **stored but never read** (`mixed_streamer_reducer.cc:30-31`, `mixed_streamer_reducer.h:88`; the only writer is `index.cc:1049`). The renumbering is unconditional.

Meanwhile, nothing on the scalar side moves: the forward store still holds 28 rows, `doc_ids_` still has 28 entries, the delete store still marks g_doc_ids 0-2 (`SegmentImpl::internal_delete`, `segment.cc:933-936`), and the new block meta even declares `doc_count = doc_ids_.size()` = 28 with min/max from `doc_ids_` (`segment.cc:1569-1576`). So the dumped HNSW file contains 25 vectors under keys 0-24, where key *k* actually holds the vector of row *k+3*.

## 3. Why counts/scalars agree while vectors are wrong

Reads treat engine keys as block-relative row positions (`CombinedVectorColumnIndexer`: result keys become `block_offset + doc.key()`, lines 58-66/134-147; pk routing `pk - block_offsets_[i]`, lines 306-310; block offsets accumulate `block_meta.doc_count_`, lines 279-286). With block_offset = 0 and rows 0-2 deleted:

- **Wrong live IDs**: the query with doc-0008's saved basis vector matches the node now keyed 5 → the DB reports `doc_ids_[5]` = doc-0005. Every hit at original position *p ≥ 3* is reported as doc-000(p−3).
- **Omitted tail**: no key maps to positions 25-27, so doc-0025…doc-0027 can never be returned; hits mapped to positions 0-2 resolve to deleted g_doc_ids and are filtered out by the delete store — so some queries (e.g., using doc-0003…doc-0005's own vectors) return nothing or only the next-nearest wrong IDs.
- **Fetch failures**: `SegmentImpl::Fetch` computes `block_doc_id = segment_doc_id - block_offset` and calls `VectorColumnIndexer::Fetch(block_doc_id)` (`segment.cc:1276-1300`; `vector_column_indexer.cc:150-165`). For positions 25-27 the key doesn't exist in the rebuilt index → `index->fetch` fails → error log and `nullptr` doc, while the scalar columns for the same IDs enumerate fine.
- **Counts agree** because live count and scalar enumeration read only the forward store + delete store (`doc_count(filter)`), which the `CreateVectorIndexTask` path never touches.
- **Read-only reopen doesn't help** because the wrong keys are persisted in the dumped index file and the segment meta/version (`segment.cc:1551-1576`; reload via `load_vector_index_blocks`, `segment.cc:498`; and `optimize` itself is refused read-only, `collection.cc:911`).

## 4. The two controls

- **Optimizing the empty collection first**: Phase 1 finds no records to seal and `persist_segments.size() == 0`, so `optimize()` returns immediately (`collection.cc:929-942`). No index is built, `vector_indexed` stays false, and the later insert → delete → flush → optimize sequence takes exactly the buggy path above. Hence no prevention.
- **Optimizing the non-empty data before deleting**: that optimize also goes through `CreateVectorIndexTask` → `merge_vector_indexer`, but with an empty delete store nothing is filtered, so `next_id++` assigns keys 0-27 to rows 0-27 — coincidentally the **identity mapping**, and the index is correct. The segment meta is then marked indexed and reloaded (`collection.cc:1028-1033`, `1063-1071`). After the deletes, the second `optimize()` again builds a `CreateVectorIndexTask` (ratio still < 0.3), but `SegmentImpl::create_vector_index` early-returns at `segment.cc:1534-1539` (`vector_indexed(column) && params equal`), so no renumbering occurs; the deletes remain purely query-time delete-store filtering, which is correct. (The multi-segment branch has the analogous guard `all_vector_index_ready()`, `collection.cc:1131-1135`.)

## 5. The much-larger-delete-fraction path (contrast)

Above the 0.3 threshold, `rebuild = true` and a **`CompactTask` with the filter** is created (`collection.cc:1100-1104`, `1166-1168`) → `SegmentHelper::ExecuteCompactTask` (`segment_helper.cc:100-175`):

- `ReduceScalar` re-scans all segments and `FilterRecordBatch` physically drops deleted rows from the forward/inverted data while recording deleted **scan positions** `i + row_id_offset` into `delete_row_id_bitmap` (`segment_helper.cc:224-282`, `934-999`; position-space semantics also documented at `fts_rocksdb_reducer.cc:237-239`).
- `ReduceVectorIndex` then merges the vector indexers with a `RowIdFilter` over that same position space (`segment_helper.cc:143-154`, `638-674`); reuse of the first indexer is disabled whenever a filter exists (`CanReuseFirstIndexer`, `segment_helper.cc:767-790`).
- Here the reducer's sequential renumbering is **correct by construction**: survivors are emitted in ascending position order, so new key *j* equals new scalar row *j*; the output block metas get the filtered `doc_count` (`segment_helper.cc:677-685`). Scalar and vector sides are renumbered in lockstep, so the invariant holds. (The FTS test comments confirm this split: `python/tests/test_collection_fts.py:154-163`.)

The bug is specific to the low-ratio path, where the same renumbering merge is applied **in place** while the scalar rows keep their old positions.

## 6. The mapping invariant a fix must preserve

For every `VECTOR_INDEX` block and every segment row position *p* it covers (`block_offset ≤ p < block_offset + block_meta.doc_count_`): **the engine key stored for that row's vector must equal `p − block_offset`**, and every consumer — search-key translation (`combined_vector_column_indexer.cc:66`), fetch (`segment.cc:1282`, `combined_vector_column_indexer.cc:427-443`), and the delete/segment filter (`segment.cc:464-475` via `doc_ids_`) — relies on that single position key space. Equivalently: renumbering vector keys is only legal when the scalar/forward rows (and block `doc_count`) are renumbered identically in the same operation (the compact path); an in-place rebuild over unchanged scalar rows must preserve source keys (`iterator->key() + id_offset`) for surviving rows, leaving holes for deleted positions — or such segments must be routed to the full compaction path. Honoring the dead `enable_pk_rewrite_` flag (`mixed_streamer_reducer.cc:30-31`) at `read_vec`'s produce site (line 318) is the natural seam.

## 7. Regression check that catches wrong associations (not counts)

Because the scalar side stays perfectly consistent, any count/enumeration assertion passes. The test must pin **vector↔ID pairing**, using the distinct unit-basis setup (each doc is its own exact unique nearest neighbor under COSINE):

1. Insert doc-0000…doc-0027; delete a *prefix below the threshold* (e.g., doc-0000…doc-0002 → 10.7% < 0.3) so `build_compact_task` provably takes the `CreateVectorIndexTask` path; flush; `optimize()`.
2. For every live ID `d`: `knn_search(ref_vector[d], topk=1)` must return exactly `d` (catches both the off-by-3 mislabeling and tail omission — doc-0025…0027 currently can never appear).
3. For every live ID `d`: fetch with the vector field included must succeed and the returned vector must equal `ref_vector[d]` (cosine similarity 1.0) — catches payload shifts and the `Fetch` failures at positions 25-27.
4. Searching with deleted IDs' reference vectors must never return a deleted ID, and the live-doc count must be 25 (the control assertion that alone is insufficient).
5. Repeat steps 2-4 after close + read-only reopen, since the corruption is persisted in the dumped index file and segment meta.
