All evidence is gathered. Here is the full analysis, limited to the paths this checkout establishes (non-quantized FP32 HNSW, single small segment).

## Root cause: filtered in-place vector-index rebuild renumbers labels while the segment's row space stays put

**The invariant on the write path.** A segment assigns each doc a global id (`segment.cc:869`) and appends it to `doc_ids_` (`segment.cc:914`); the internal segment doc id is the forward-store row offset (`segment.cc:644`). Vectors are inserted into the column indexer keyed by that same offset (`segment.cc:702–705` → `VectorColumnIndexer::Insert`, `vector_column_indexer.cc:136–148`). Deletes only flip bits: `Delete(pk)` marks the *global* id in `delete_store_` and removes the id-map entry (`segment.cc:986–1009`, `933–935`) — forward rows and vector keys are untouched, and `SegmentIndexFilter` translates internal row id → global id → bitmap (`segment.cc:85–96`, `464–476`).

**What optimize() does with 3/28 deleted.** In `CollectionImpl::optimize` (`collection.cc:910–951`), the delete ratio 3/28 ≈ 10.7% is below `COMPACT_DELETE_RATIO_THRESHOLD = 0.3f` (`src/db/common/constants.h:41`), so `build_compact_task` keeps `rebuild = false` (`collection.cc:1100–1104`) and, for the single segment, emits a `CreateVectorIndexTask` (`collection.cc:1160–1164`) — a vector-index-only, in-place rebuild. That runs `SegmentImpl::create_all_vector_index` → `create_vector_index` (`segment_helper.cc:1121–1131`, `segment.cc:1466–1489`, `1519–1578`; FP32 non-quantized branch at `1545`), which calls `merge_vector_indexer` — and there, at `segment.cc:1511`, passes the segment's **delete filter** `filter_` into `VectorColumnIndexer::Merge` (`vector_column_indexer.cc:103–134`).

`Merge` reaches core `Index::merge` (`src/core/interface/index.cc:1016–1077`), which builds a `MixedStreamerReducer` with `ENABLE_PK_REWRITE = true` (`index.cc:1049–1050`) and calls `reduce(filter)`. In `MixedStreamerReducer::read_vec` (`src/core/mixed_reducer/mixed_streamer_reducer.cc:255–326`), deleted keys are skipped (line 288) and every survivor is re-labeled with a fresh sequential id `(*next_id)++` starting at 0 (line 318; init at 151–161), which becomes the stored key via `add_with_id_impl`/`PushToDocCache`+`IndexBuild` (lines 375–377, 410–411, 552–621). Note `enable_pk_rewrite_` is parsed (`mixed_streamer_reducer.cc:30–31`, header line 88) but **never consulted** — renumbering is unconditional. So the rebuilt HNSW holds 25 vectors under labels 0–24, where label *L* physically holds the vector of original internal id *L+3*. Meanwhile the forward store still has 28 rows, `doc_ids_` still has 28 entries, the delete bitmap still marks old internal ids 0–2, and the new `BlockMeta` even records `doc_count = doc_ids_.size() = 28` (`segment.cc:1568–1576`). Phase 3 persists this meta (`collection.cc:1028–1040`) and swaps the indexers in via `reload_vector_index` (`collection.cc:1063–1071`, `segment.cc:1752–1810`), without touching the delete store.

## Why counts agree while vector results are wrong

Counts and scalar enumeration never consult the vector index: `doc_count(filter)` walks `doc_ids_` against the bitmap (`segment.cc:616–627`) → 25. The vector read path does the opposite — it treats index labels as row offsets: `VectorRecallNode::State::collect_batch` pushes `iter_->doc_id()` into `segment_->fetch(columns, indices)` and `FetchVectorOp` (`vector_recall_node.cc:216–232`, `253–259`), and pk resolution is `doc_ids_[label]` (`segment.cc:4444–4451`). Hence: querying doc-0027's basis vector returns label 24 → reported as doc-0024 (**wrong live ID**); labels 0–2 (holding doc-0003/4/5's vectors) are suppressed by the stale delete bitmap, so those live docs are unreachable; no label maps to doc-0025–0027 (**omitted tail**). `Fetch` of doc-0025–27 finds the block (meta claims 28 docs) but `vector_indexer->Fetch(block_doc_id)` fails for absent keys 25–27 (`segment.cc:1276–1301`, `vector_column_indexer.cc:150–165`) — vector payload fails while scalar columns, already fetched from the intact forward store, remain. Reopening read-only reloads the persisted compacted index plus the 28-row `doc_ids_` (`segment.cc:478–498`, `3875–3914`), so the corruption is durable.

## The two controls

- **Optimize-before-first-insert does nothing**: `writing_segment_->has_record()` is false and `get_all_persist_segments()` is empty, so `optimize()` returns at `collection.cc:929–942` without building or marking anything. The later post-delete optimize still meets a segment that is *not* `vector_indexed`, so the filtered rebuild runs.
- **Optimize-before-delete avoids it**: with an empty delete store, the same `CreateVectorIndexTask` path runs, but `SegmentIndexFilter` filters nothing, so the reducer's renumbering 0…27 is the identity on source keys — labels stay equal to row offsets — and the segment meta gets marked indexed (`segment.cc:1540`, `1485`). Deletes afterwards just flip bitmap bits. A subsequent post-delete optimize **skips the rebuild** via the early return `segment_meta_->vector_indexed(column) && *field->index_params() == *index_params` (`segment.cc:1534–1539`; also `skip_task = all_vector_index_ready()`, `collection.cc:1135`). Avoidance comes from the skip check, not from the filtered rebuild being correct.

## The large-delete-ratio path (contrast)

With ≥30% deleted, `rebuild = true` (`collection.cc:1100–1104`) and a `CompactTask` carrying the delete filter is created (`collection.cc:1166–1168`). `SegmentHelper::ExecuteCompactTask` (`segment_helper.cc:100–175`) rebuilds *everything together*: `ReduceScalar` writes a new forward store containing only live rows renumbered 0…N−1 and records `delete_row_id_bitmap` (lines 132–135, `~964`); `ReduceVectorIndex` merges vector indexes with a `RowIdFilter` over that same bitmap (lines 143–153, class at 85–98). The same PK-rewrite renumbering occurs, but it now agrees with the new forward numbering because both compact the same ascending live-row sequence; the output segment gets fresh `doc_ids_` and truthful block metas, and inputs are retired (`collection.cc:1048–1062`). The invariant holds — which is why heavy deletion doesn't exhibit the bug.

## Invariant a fix must preserve

**For every vector-index block, index key *L* must equal the segment-internal doc id (forward row offset / position in `doc_ids_`) of that document, and the block's `min/max/doc_count` meta must describe that same key space** — label *L* ↔ `doc_ids_[L]` ↔ forward row *L*, as assumed by `vector_recall_node.cc:225–232`, `segment.cc:4444–4451`, and `segment.cc:1276–1300`. A filtered rebuild may renumber labels only if it renumbers forward rows identically (full `CompactTask`); otherwise it must preserve source keys. Natural fix sites: make the in-place path pass no delete filter (deletions are already handled lazily by the bitmap at query time), or honor the already-parsed-but-ignored `enable_pk_rewrite_` (`mixed_streamer_reducer.cc:30–31`) so `read_vec` emits `iterator->key() + id_offset` instead of `(*next_id)++` (line 318); or force `rebuild = true` whenever the delete filter is non-empty for in-place candidates.

## Regression check that catches wrong associations (not counts)

Extend `tests/db/collection_test.cc` with an identity-based test: insert N=28 unit basis vectors (e_i ↔ doc-i association held externally), delete a prefix below the 30% threshold, flush, `optimize()`. Then assert, for **every live pk**: (1) querying its saved basis vector returns that exact pk as top-1 — an association assertion, not a hit-count assertion; (2) `Fetch(pk, include_vector=true)` succeeds and the returned bytes are bit-identical to the saved vector; (3) the union of top-1 results over all live queries is exactly the live pk set (detects the omitted tail and the bitmap-masked doc-0003/4/5 class); (4) reopen read-only and repeat (1)–(3). Optionally assert the structural invariant directly: after in-place optimize the indexer's key count equals `doc_ids_.size()`, or the segment was replaced with `doc_count == live rows`. Count-only checks pass under this bug because the forward store and delete bitmap are untouched; only pk↔vector identity exposes the label compaction.
