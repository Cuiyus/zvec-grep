## Call chain (shared by A and B)

`collection.optimize(option)` (`python/zvec/model/collection.py:231-238`) → pybind `Optimize` (`src/binding/python/model/python_collection.cc:240-247`) → `CollectionImpl::optimize(OptimizeOptions)` (`src/db/collection.cc:952`, tasks built at 989, 1128-1211 with `options.concurrency_`; `OptimizeOptions{int concurrency_{0}}` at `src/include/zvec/db/options.h:60-62`) → `CompactTask` carrying `concurrency_` (`src/db/index/segment/segment_helper.h:54-80`) → `SegmentHelper::ExecuteCompactTask` → `ReduceVectorIndex(..., concurrency, ...)` (`src/db/index/segment/segment_helper.cc:52-54, 98, 148, 635-645`) → `MergeWithOptionalReuse(..., concurrency, ...)` (`segment_helper.cc:668, 695, 743`, defined 799-858). The single-segment rebuild path `SegmentImpl::merge_vector_indexer` (`src/db/index/segment/segment.cc:1549-1575`) contains identical selection logic (1560-1567).

Separately, `zvec.init(optimize_threads=4)` maps `optimize_threads` → `GlobalConfig::ConfigData::optimize_thread_count = 4` (`python/zvec/zvec.py:162-163`; `src/binding/python/model/common/python_config.cc:154-158`), and `GlobalResource::initialize()` (call-once) creates the global optimize pool `new ailego::ThreadPool(optimize_thread_count(), ...)` (`src/db/common/global_resource.cc:21-33`; accessor `global_resource.h:31-34`). `ThreadPool(size)` clamps to `[1, hardware_concurrency]` and eagerly spawns that many workers (`src/ailego/parallel/thread_pool.cc:85-122`), so with hw ≥ 4 the global optimize pool has exactly **4 workers**.

## 1. Pool selection per invocation

The selection happens twice, consistently — in the DB layer (`segment_helper.cc:804-811`, `segment.cc:1560-1567`) and in the core (`src/core/interface/index.cc:1429-1446`):

- **A (`concurrency=0`)**: `merge_options.pool = GlobalResource::Instance().optimize_thread_pool()` and `write_concurrency = pool->count()` = 4 (`segment_helper.cc:805-808`). In `Index::merge`, since `options.pool != nullptr`, the reducer **borrows the global pool** via `reducer->set_thread_pool(options.pool)` and `effective_write_concurrency = min(4, pool->count()) = 4` (`index.cc:1436-1439`).
- **B (`concurrency=2`)**: `merge_options.pool` stays `nullptr`, only `write_concurrency = 2` (`segment_helper.cc:809-811`). `Index::merge` then creates a **call-local pool**: `local_thread_pool = std::make_unique<ailego::ThreadPool>(2, false)` — 2 workers after clamping — and sets it on the reducer, with `effective_write_concurrency = local_thread_pool->count() = 2` (`index.cc:1433-1446`; the comment at 1433 notes the unique_ptr is declared there so its lifetime covers `reducer->reduce()`).

**B does not change the global pool.** The `concurrency != 0` branch never touches `GlobalResource`; the local pool is destroyed when `Index::merge` returns. The global 4-worker pool created at init persists unchanged (its workers were spawned eagerly at construction, `thread_pool.cc:104-108`).

## 2. Handoff to the target builder's train/build and the conversion-train call

`MixedStreamerReducer::reduce` requires a pool (`mixed_streamer_reducer.cc:206-214`; member/setter in `src/include/zvec/core/framework/index_reducer.h:172-184`) and, when a target builder exists (set by `set_target_streamer_wiht_info`, `mixed_streamer_reducer.cc:114-125`, fed from `Index::merge` at `index.cc:1506-1508`), goes through `reduce_with_builder` (672-740) into **`index_build` (`src/core/mixed_reducer/mixed_streamer_reducer.cc:742-777`)**, the single meaningful handoff point:

- Line 743-744: one `BorrowedSingleQueueIndexThreads(*thread_pool_)` adapter is created over the selected pool (global in A, local in B). It holds the pool **by reference** and its `count()`/`submit()`/`make_group()` delegate straight to it (`src/include/zvec/core/framework/index_threads.h:174-225`, count at 183-186).
- Line 745-747: the **optional conversion-training call** — `core::IndexConverter::TrainAndTransform(target_builder_converter_, target_holder, threads)` → `converter->train(two_pass_holder, std::move(threads))` (`src/core/framework/index_converter.cc:27-36`).
- Line 760: `target_builder_->train(threads, target_holder)`.
- Line 768: `target_builder_->build(std::move(threads), target_holder)`.

So all three builder-side stages receive the *same* `IndexThreads::Pointer` wrapping the one selected pool — 4 workers in A, 2 in B.

**Passing vs. consuming:** the interface only guarantees the pool is offered. The converter's two-arg `train` base implementation explicitly discards `threads` and delegates to the one-arg form (`src/include/zvec/core/framework/index_converter.h:185-190`); the builder virtuals are declared in `IndexRunner` (`src/include/zvec/core/framework/index_runner.h:687-722`), where the one-arg `train(holder)`/`build(holder)` convenience overloads forward `nullptr` threads (687-689, 714-716) — e.g., `DiskAnnIndex::train()`'s direct path `builder_->train(holder_)` (`src/core/interface/indexes/diskann_index.cc:224-246`) reaches `DiskAnnBuilder` with null threads, which then self-provisions a pool (`diskann_builder.cc:657-663, 714-720`). Whether a concrete builder/converter actually submits work to the passed pool is per-implementation; the merge path only proves the selected pool is what arrives. (In the DiskANN merge path, `DiskAnnIndex::merge` → `Index::merge` → reducer → `index_build`, threads is always non-null: `diskann_index.cc:361-374`.)

## 3. DiskANN PQ training: its outer chunk-dispatch pool is *not* reused

`DiskAnnBuilder::train(threads, holder)` (`src/core/algorithm/diskann/diskann_builder.cc:633-681`) calls `train_quantized_data(threads)` (line 665, defined 378-427), which creates a `PqInt8Quantizer` and sizes it:

```cpp
// The quantizer creates its own pool, so bound it by the caller's pool.
const auto pq_thread_count = static_cast<uint32_t>(std::max<size_t>(
    1, std::min<size_t>(build_thread_count_, threads->count())));   // :391-394
qp.set("thread_count", pq_thread_count);
```

- `build_thread_count_` is the builder's own setting: `PARAM_DISKANN_BUILDER_THREAD_COUNT`, defaulting to `hardware_concurrency` when 0 (`diskann_builder.cc:51-55`; exceeding hw concurrency only warns, 57-61).
- `threads->count()` is the caller's selected pool size (4 in A, 2 in B) via the `BorrowedSingleQueueIndexThreads` delegate (`index_threads.h:183-186`).

The quantizer stores it (`params.get("thread_count", &thread_count_)`, `src/turbo/quantizer/pq_int8_quantizer/pq_int8_quantizer.cc:142`; member default 0 at `pq_int8_quantizer.h:217`), and its **outer pool is freshly constructed inside `train_all_chunks`**, not borrowed:

```cpp
auto threads = std::make_shared<SingleQueueIndexThreads>(thread_count_, false);  // :322-323
...
for (size_t i = 0; i < pool_count; ++i)                       // :332-342
  task_group->submit(... for m = i; m < num_chunk_; m += pool_count: train_chunk<T>(...));
task_group->wait_finish();                                    // :356
```

(`pq_int8_quantizer.cc:319-357`; `SingleQueueIndexThreads` owns a private `ailego::ThreadPool`, sized `thread_count_` when > 0 else hardware_concurrency, `index_threads.h:112-116, 166`.) `train_all_chunks` may run more than once per train (inside the `opq_.train` callback and directly, `pq_int8_quantizer.cc:295-305`), each time constructing a new ephemeral pool.

So: the caller's pool is used **only as an upper bound**, never as the dispatch pool. With default `build_thread_count_` = hw ≥ 4: **A's PQ outer pool = min(hc, 4) = 4 workers; B's = min(hc, 2) = 2 workers**. Chunks (PQ subquantizers) are then striped round-robin across that pool's workers.

## 4. What these settings establish — and what they don't

**Established (worker-pool capacity):**
- A: the merge borrows the process-global optimize pool with exactly 4 workers (init value, clamped by hw ≥ 4, `thread_pool.cc:93-101`), and every `IndexThreads` view handed to converter-train/builder-train/build reports `count() == 4`.
- B: the merge runs on a per-call local pool of exactly 2 workers; the global pool is untouched and B's pool dies with the call (`index.cc:1433-1446`).
- DiskANN PQ training's outer pool capacity is bounded by `max(1, min(build_thread_count_, caller count))` (`diskann_builder.cc:391-394`).
- In each pool, at most `count()` submitted tasks execute concurrently.

**Not established:**
- **Process thread count.** These knobs bound only specific pools. Other threads coexist: the separate global query pool (`global_resource.cc:24-26`), each ephemeral PQ pool (`pq_int8_quantizer.cc:322-323`), fallback pools self-created by builders when `threads == nullptr` (`diskann_builder.cc:657-663, 714-720`), the calling/task-executor threads themselves, and anything inside third-party kernels. Notably, B does not shrink the global pool — its 4 eagerly spawned worker threads still exist, just unused by that merge.
- **Actual CPU utilization.** Worker count is a capacity ceiling, not a floor or a measurement. Real parallelism depends on how many tasks are actually submitted (PQ submits exactly `pool_count` tasks, so if `num_chunk_ < pool_count` workers idle, `pq_int8_quantizer.cc:332-342`), sequential phases, blocking/back-pressure (`submit` sleeps while the queue is saturated, `index_threads.h:91-95, 140-143`; `wait_finish` blocks the caller), whether an implementation consumes the passed pool at all (`index_converter.h:185-190` discards it by default), and OS scheduling. Passing a pool proves availability of workers, not busy CPUs.
