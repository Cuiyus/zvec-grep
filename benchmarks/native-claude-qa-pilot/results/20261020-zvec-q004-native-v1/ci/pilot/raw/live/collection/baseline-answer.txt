All source verification is complete. Here is the analysis, grounded in this checkout.

## Setup: what `zvec.init(optimize_threads=4)` establishes

- The Python binding maps `optimize_threads=4` into `ConfigData::optimize_thread_count` (`src/binding/python/model/common/python_config.cc:153-158`) and calls `GlobalConfig::Instance().initialize(data)` (`python_config.cc:192-193`).
- `GlobalConfig::initialize` is one-shot (atomic compare-exchange, `src/db/common/config.cc:119-125`) and then calls `GlobalResource::Instance().initialize()` (`config.cc:140`).
- `GlobalResource::initialize` (`std::call_once`, `src/db/common/global_resource.cc:21-23`) eagerly creates the global `optimize_thread_pool_` with `optimize_thread_count()` = 4 workers (`global_resource.cc:27-29`). `ailego::ThreadPool`'s constructor clamps the requested size to `[1, hardware_concurrency]` and spawns the worker threads immediately (`src/ailego/parallel/thread_pool.cc:93-122`; `count()` returns the worker vector size, `src/include/zvec/ailego/parallel/thread_pool.h:167-170`). With `hardware_concurrency() ≥ 4`, the global pool has exactly 4 workers.

## 1. Pool and worker-count selection per invocation

`collection.optimize(options)` flows: `CollectionImpl::optimize` → `build_compact_task(..., options.concurrency_, ...)` (`src/db/collection.cc:952, 988-990`), which stamps `concurrency` into each `CompactTask`/`CreateVectorIndexTask` (`collection.cc:1160-1163, 1169-1171, 1175-1178, 1201-1207`; struct at `src/db/index/segment/segment_helper.h:54-80`). Task execution reaches the vector merge selection point — identical logic in both the compact path (`SegmentHelper::MergeWithOptionalReuse`, `src/db/index/segment/segment_helper.cc:804-811`, via `ReduceVectorIndex` at `segment_helper.cc:148-150, 668-671, 695-700, 743-745`) and the create-index path (`SegmentImpl::merge_vector_indexer`, `src/db/index/segment/segment.cc:1560-1567`):

- **A (`concurrency=0`)**: `merge_options.pool = GlobalResource::Instance().optimize_thread_pool()` and `write_concurrency = pool->count()` = **4** (`segment_helper.cc:805-808`). The shared, process-global 4-worker pool is selected.
- **B (`concurrency=2`)**: only `merge_options.write_concurrency = 2` is set; `pool` stays `nullptr` (default, `src/db/index/column/vector_column/vector_column_params.h:72-75`) (`segment_helper.cc:809-811`).

The core engine then finalizes the choice in `core::Index::merge` (`src/core/interface/index.cc:1416-1452`): if `options.pool != nullptr`, the reducer borrows that pool and effective concurrency is `min(write_concurrency, pool->count())` (`index.cc:1436-1439`); otherwise it constructs a **local, temporary** `ailego::ThreadPool(write_concurrency, false)` kept alive only until `reduce()` returns (`index.cc:1433-1434, 1440-1446`).

So: **A runs the merge on the global 4-worker optimize pool** (effective concurrency `min(4,4)=4`); **B runs it on a fresh local 2-worker pool** created inside `Index::merge` and destroyed when the merge returns. **B does not change the configured global pool**: it never touches `GlobalResource` (the `concurrency != 0` branch skips it), and both `GlobalConfig::initialize` (`config.cc:119-125`) and `GlobalResource::initialize` (`global_resource.cc:21-23`) are one-shot — the global pool remains the 4-worker pool created at init.

## 2. Handoff to the builder's train/build and conversion-training

`VectorColumnIndexer::merge` forwards `{write_concurrency, pool}` to the engine (`src/db/index/column/vector_column/vector_column_indexer.cc:128-130`; core struct at `src/include/zvec/core/interface/index_param.h:54-57`). `Index::merge` stores the selected pool on the reducer via `set_thread_pool` (`index.cc:1437, 1443`; base member at `src/include/zvec/core/framework/index_reducer.h:172-175, 183`) and passes `effective_write_concurrency` as `NUM_OF_ADD_THREADS` (`index.cc:1448-1452`; read in `MixedStreamerReducer::init`, `src/core/mixed_reducer/mixed_streamer_reducer.cc:80-95`).

When a target builder exists (the assumed rebuild case), `reduce` takes `reduce_with_builder` (`mixed_streamer_reducer.cc:218-232, 672-740`), which ends in `index_build` (`mixed_streamer_reducer.cc:742-777`) — the builder-side stage the question targets:

- The selected pool (global for A, local for B — the reducer only ever sees `thread_pool_`) is wrapped once: `threads = std::make_shared<BorrowedSingleQueueIndexThreads>(*thread_pool_)` (`mixed_streamer_reducer.cc:743-744`). This adapter **borrows** the existing pool — it creates no threads of its own and delegates `submit`/`make_group`/`count` to it (`src/include/zvec/core/framework/index_threads.h:169-225`).
- **Optional conversion-training immediately before train/build**: if `target_builder_converter_` is set, `IndexConverter::TrainAndTransform(converter, target_holder, threads)` (`mixed_streamer_reducer.cc:745-747`), which forwards the same `threads` into `converter->train(two_pass_holder, std::move(threads))` (`src/core/framework/index_converter.cc:27-36`, esp. line 31).
- **Builder train**: `target_builder_->train(threads, target_holder)` (`mixed_streamer_reducer.cc:760`).
- **Builder build**: `target_builder_->build(std::move(threads), target_holder)` (`mixed_streamer_reducer.cc:768`).

All three calls receive the same `shared_ptr` wrapping the one pool selected in step 1.

**Passing ≠ consuming.** The handoff only guarantees the pool is *offered*:
- `IndexConverter::train(holder, threads)`'s default implementation explicitly discards `threads` (`(void)threads; return train(holder)`, `src/include/zvec/core/framework/index_converter.h:185-190`); only converters overriding the two-arg form use it.
- `IndexRunner`'s `train/build(threads, holder)` virtuals are per-implementation (`src/include/zvec/core/framework/index_runner.h:687-695, 714-722`). DiskAnnBuilder, for example, does submit graph-prune work onto the borrowed pool (`threads->count()` tasks, `src/core/algorithm/diskann/diskann_builder.cc:341-352`), but as shown next, its PQ training does not run on it at all.

## 3. DiskANN PQ training: a separate pool, bounded — not reused

`DiskAnnBuilder::train(threads, holder)` (`diskann_builder.cc:633-681`) calls `train_quantized_data(threads)` (line 665). There, the PQ chunk-dispatch pool is **not** the caller's borrowed pool. The builder creates a `PqInt8Quantizer` and passes it a `thread_count` parameter:

```cpp
// The quantizer creates its own pool, so bound it by the caller's pool.
const auto pq_thread_count = static_cast<uint32_t>(std::max<size_t>(
    1, std::min<size_t>(build_thread_count_, threads->count())));
qp.set("thread_count", pq_thread_count);
```
(`diskann_builder.cc:383-396`, comment at 391). The quantizer reads that into `thread_count_` (`src/turbo/quantizer/pq_int8_quantizer/pq_int8_quantizer.cc:141-142`; member default 0 at `pq_int8_quantizer.h:217`), and `train_all_chunks` constructs a **fresh, quantizer-owned** `SingleQueueIndexThreads(thread_count_, false)` (`pq_int8_quantizer.cc:319-324`), which itself owns a new `ailego::ThreadPool` (`index_threads.h:112-116, 162-167`). Chunks are then distributed round-robin across that pool's workers — worker `i` trains chunks `m ≡ i (mod pool_count)` (`pq_int8_quantizer.cc:326-343`) — while each per-chunk k-means is single-threaded ("parallelism is at the chunk level", `pq_int8_quantizer.cc:198-200`).

Worker-count determination: `max(1, min(build_thread_count_, caller_pool_count))`, where
- `caller_pool_count = threads->count()` — **4 under A** (global pool), **2 under B** (local pool); and
- `build_thread_count_` is the builder's own setting from `PARAM_DISKANN_BUILDER_THREAD_COUNT`, defaulting to `hardware_concurrency()` when unset/0 (`diskann_builder.cc:51-55`).

So with the assumed `hardware_concurrency() ≥ 4` and an unconfigured builder setting, PQ training's outer pool gets **4 workers under A and 2 under B** — additional threads beyond the merge pool, deliberately capped by it. (Same pattern at build time: `DiskAnnBuilder::build` uses the passed `threads`, or self-creates `SingleQueueIndexThreads(build_thread_count_)` if none, `diskann_builder.cc:697-720`; `train` likewise at 657-663.)

## 4. What the settings establish — and what they don't

**Established (pool capacities):**
- The global optimize pool has exactly 4 eagerly-created workers (`optimize_threads=4` → `global_resource.cc:27-29`; clamp inert since `hardware_concurrency ≥ 4`, `thread_pool.cc:93-101`), and it is unchanged by B (one-shot initialization, `config.cc:119-125`, `global_resource.cc:21-23`).
- A's core merge borrows that 4-worker pool with effective write concurrency 4 (`index.cc:1436-1439`); B's merge owns a transient 2-worker pool for the duration of one `Index::merge` call (`index.cc:1440-1446`).
- DiskANN PQ chunk-dispatch capacity is `max(1, min(build_thread_count_, 4))` under A and `max(1, min(build_thread_count_, 2))` under B (`diskann_builder.cc:391-394`).

**Not established (process thread count / CPU utilization):**
- **Total thread count**: pools are additive, not budgeted against each other. The same `GlobalResource::initialize` also creates the query pool sized by `query_thread_count` (default: cgroup CPU limit, `global_resource.cc:24-26`, `config.cc:37`); each `concurrency≠0` merge spawns its own local pool; each PQ training spawns the quantizer's pool; builders self-create pools when handed a null `threads` (`diskann_builder.cc:657-663, 714-720`); plus per-chunk single-thread k-means pools (`pq_int8_quantizer.cc:199-200`), Python/main threads, and anything else in the process. Nothing in this configuration path sums or caps these.
- **Actual CPU utilization**: worker count is capacity, not occupancy. Pool workers block on a condition variable when the queue is empty (`thread_pool.cc:162-175`); the number of submitted tasks can be below pool size; `effective_write_concurrency` can cap consumer threads below `pool->count()` (`index.cc:1438-1439`); and the nesting pattern means caller-pool workers can be *parked* in `wait_finish()` (e.g., `pq_int8_quantizer.cc:356`, `diskann_builder.cc:354-373`) while a nested pool does the compute. Binding is off by default (`optimize_thread_binding(false)`, `config.cc:43`), and OS scheduling is orthogonal to these settings. These knobs bound specific pools' worker capacities; they say nothing definitive about instantaneous thread counts or CPU saturation of the whole process.
